# 跨平台路径输入与解析一致性修复方案

> 修复归档引擎在 Linux 上解析 Windows 相对路径的 CI 故障，统一跨平台路径输入契约，并为 CLI、文档工具、模块解析器与虚拟文件系统建立可验证的边界。

## 一、问题与证据

### 1. 已复现故障

Linux CI 执行共享包测试时，`archive-engine.test.ts` 的 Windows 前缀路径用例失败：输入 `.\docs\plans\core\路径容错方案.md`，预期归档至 `docs/archive/2026/core/路径容错方案.md`，实际在 `ArchiveEngine.preflightPlan()` 的目录校验处抛错。

入口位于 [归档引擎](../../../../scripts/docs/lib/archive-engine.mjs)，测试位于 [归档测试](../../../../packages/shared/tests/archive-engine.test.ts)。引擎先执行 `path.resolve(rootDir, planRelPath)`，再对 `path.relative()` 的结果调用 `toPosix()`。Linux 将反斜杠视为普通字符，路径中的层级与点段未被正确解析；文档引擎的 `toPosix()` 又只替换宿主的 `path.sep`，导致目录前缀匹配失败。

日志中共享包测试为 299 项通过、1 项失败。TypeScript sourcemap 缺失警告未触发本次退出。此前本地验证仅覆盖倒计时组件，未覆盖归档功能的 Linux 行为。

### 2. 排查结论的证据等级

以下条目来自源码检查。除 CI 已复现项外，实施前须用最小用例验证具体输入契约与影响；出现 `path.resolve()` 本身不构成缺陷。

| 范围 | 源码证据与触发条件 | 实施处理 |
| --- | --- | --- |
| 归档入口 | Windows 风格相对参数直接进入宿主路径解析；CI 已失败 | 第一批修复 |
| 文档路径转换 | `doc-link-engine.mjs` 的 `toPosix()` 依赖宿主分隔符；显式目标文件与关联文档解析也依赖宿主路径规则 | 补充输入级复现，接入文档路径契约 |
| 两套内存文件系统 | 两者先 resolve 再替换；文档 VFS 将整个键转为小写，共享 VFS 只统一盘符大小写 | 明确宿主路径输入与大小写策略，验证点段、合法文件名和目录枚举一致性 |
| 共享模块解析器 | `module-resolver.ts` 识别反斜杠相对形式及 Windows 绝对形式，后续仍使用宿主 resolve | 明确说明符与文件路径的不同契约并复现 |
| CLI 配置与目标路径 | `ProjectContext` 的 cwd、别名、样式路径、注册表目标路径直接参与 join/resolve | 验证持久配置跨系统复用及入口参数 |
| CLI 命令与报告 | `--cwd`、`--workspace-root`、`--path`、`--output-file`、`--sbom-output` 使用宿主路径语义 | 按参数基准目录统一解析 |
| 工程脚本 | 候选制品、benchmark、性能测试、API manifest 与发布脚本接收原始文件参数 | 纳入同一输入矩阵逐项验证 |
| 通用路径辅助函数 | `normalizeAbsPath()` 的普通路径分支直接 resolve；现有 `toPosixPath()` 已能替换反斜杠 | 保留明确职责，统一实现位置与调用边界 |

## 二、目标与路径契约

目标是让同一份可移植相对路径在 Windows 与 Linux 上定位同一项目资源，同时保留本机文件系统、URL、模块说明符各自的语义。

### 1. 输入分类

| 输入类别 | 示例 | 约定行为 |
| --- | --- | --- |
| 可移植相对路径 | `./docs/plans/a.md`、`.\docs\plans\a.md`、混合分隔符 | 在文件路径入口将分隔符统一，再按明确的基准目录解析点段 |
| 本机绝对路径 | 当前系统文件选择器或文件系统返回值 | 按宿主路径规则解析，保留大小写及合法文件名 |
| 异系统绝对路径 | Linux 接收 `C:\repo\a.md`、Windows UNC 路径 | 返回明确的格式不支持错误，禁止将其静默拼入 cwd；不推测盘符挂载位置 |
| Windows 特殊路径 | `C:relative`、`\rooted`、扩展长度前缀 | 显式识别；本轮可移植输入契约拒绝隐式驱动器上下文及设备路径，正常 Windows 绝对路径沿宿主入口处理 |
| 文件 URL | `file:///...` | 由 URL 与 `fileURLToPath()` 解析；是否允许 query/fragment 由已有调用契约决定，不对 URL 文本全局替换反斜杠 |
| 网络 URL | HTTP(S) 注册表、外部文档链接 | 保留 URL 语义及编码 |
| 模块说明符 | 包名、别名、相对 import | 先分类，文件路径分支再执行对应规则；包名、协议、query/fragment 分别处理 |

POSIX 文件名可以合法包含反斜杠。分隔符兼容只施加于声明接受可移植路径的输入边界；磁盘适配器及目录遍历结果保持本机语义。Markdown 链接还涉及转义与 URL 编码，须通过链接解析后再判断目标，不能对整篇文本做替换。

### 2. 逐入口契约

输入模式由调用方及其数据来源确定。可移植相对路径解析与本机路径解析使用独立入口；本机路径入口保留合法的相对文件名。业务入口需要同时接受可移植相对路径和本机绝对路径时，先按显式规则分流，再调用对应解析函数。URL 与模块说明符由各自领域解析器处理。

| 入口 | 输入模式 | 相对路径基准 | 绝对路径与 URL | 边界策略 |
| --- | --- | --- | --- | --- |
| 归档方案参数 | 可移植相对路径；本机绝对路径单独分流 | 仓库根目录 | 接受本机完整绝对路径；拒绝 URL | 解析结果必须位于 `docs/plans/`；真实路径规则见归档安全批次 |
| `--cwd`、`--workspace-root` | 可移植相对路径；本机绝对路径单独分流 | 命令调用时的进程目录 | 接受本机完整绝对路径；拒绝 URL | 按命令现有项目与工作区检查；允许显式选择仓库外项目 |
| `--path`、`--output-file`、`--sbom-output` | 可移植相对路径；本机绝对路径单独分流 | 各参数现行契约指定的目录 | 接受本机完整绝对路径；拒绝 URL | 安装目标沿用写入边界；报告输出沿用其输出权限范围 |
| 配置内文件路径、别名目标及 tsconfig 引用 | 仅文件路径分支接受可移植输入 | 所属配置格式规定的基准 | 完整本机绝对路径按字段契约处理；协议由领域解析器处理 | 保留各字段原有作用域及别名匹配规则 |
| 本地 registry、显式文档目标及工程脚本参数 | 文件路径分支接受可移植输入 | 各调用入口现行基准 | 网络源、文件 URL 仅由已有支持入口接收 | 保留注册表、文档或脚本的作用域检查 |
| 磁盘遍历结果、VFS 操作与内部本机路径 API | 本机路径 | 相对输入按适配器约定的 cwd | 本机绝对路径直接使用；URL 在上层转换 | 保留宿主文件名语义，安全校验由业务调用方承担 |

后续治理开始时，将表中涉及多个命令或配置字段的条目展开为逐入口清单，记录源码位置、具体基准目录、绝对路径及 URL 接受规则、越界策略和对应测试。实施前逐项以现有文档、调用链和复现用例确认；已有参数定位行为通过回归测试固定，基准目录变更须单列为行为变更。

可移植入口在替换分隔符之前识别盘符、UNC、根相对路径和设备前缀。Windows 上 `/tmp/a` 与单个反斜杠开头的路径依赖当前驱动器，业务可移植入口明确拒绝；要求调用方提供完整盘符路径。POSIX 上 `/tmp/a` 是本机绝对路径。`C:relative` 在可移植入口始终拒绝。UNC 的正反斜杠形式一并覆盖；对可信磁盘返回值使用本机入口，保留其宿主合法形式。分类规则不推断字符串来自哪个操作系统。

### 3. 解析顺序与基准目录

可移植输入执行：类别识别 → 分隔符归一化 → 按基准目录解析 → 目录边界校验 → 必要的真实路径校验 → 文件操作。

- 归档方案相对路径以仓库根目录为基准。
- `--cwd`、`--workspace-root` 以命令调用时的进程目录为基准；`--path`、诊断报告与 SBOM 输出以逐入口清单核实的现行基准解析。
- 配置内别名、样式路径、tsconfig 路径按各自配置文件的现行基准解析。
- 工程脚本参数保留其现有 CLI 基准；传给改变 cwd 的子进程之前转换为绝对路径。
- 含 `..` 的输入在归一化后执行对应入口的越界校验。现有写入安全检查保持有效；归档新增真实路径检查按独立安全批次实现。路径格式化不能代替安全校验。
- 空字符串在必填参数入口报错，可选参数的默认值由调用方提供。

## 三、实现结构

### 1. 共享实现与包边界

以现有 POSIX 路径能力为基础，复用并提取职责明确的 Node 路径工具：可移植相对路径转换、基于指定目录的文件路径解析、供元数据输出使用的斜杠格式化。类型与参数显式声明；转换函数不负责文件读写或安全授权。

| 现有实现 | 可复用能力 | 接入方式 |
| --- | --- | --- |
| [脚本路径工具](../../../../scripts/shared/path.mjs) `toPosixPath()` | 无条件将反斜杠转换为正斜杠，已有 guardrails 测试 | 归档入口先直接复用，再调用宿主 resolve；跨包需要时将纯转换实现下沉并保留脚本侧导出 |
| [共享 VFS](../../../../packages/shared/src/fs/memory-fs.ts) | 父目录处理、符号链接路径重建与 Windows 盘符处理 | 保留适配器职责，按本机路径契约维护内部键；可移植转换放在业务入口 |
| [共享模块解析器](../../../../packages/shared/src/module-resolver.ts) | 模块分类、别名解析、目录边界与大小写检查 | 保留模块领域职责，接入共享路径基础函数 |

现有 `toPosixPath()` 只承担分隔符转换；共享 VFS 的规范化是内部方法，仍依赖宿主 resolve；二者均需结合输入分类才能构成完整入口解析。`node:path.posix` 是可复用的标准库运算能力，适合已经采用 POSIX 表示的逻辑路径；其本身不会将反斜杠识别为目录分隔符，也不负责 Windows 盘符与 UNC 语义。

归档修复先在脚本侧复用现有 `toPosixPath()`，完成入口分类及局部验证，独立交付。后续根据已复现入口的共同契约提取共享能力，优先放入 `packages/shared` 的 Node 工具模块，通过受控子路径供 CLI 与工程工具消费。提取前验证根目录 `.mjs` 脚本的实际运行方式及 CLI 打包能力，再确定扩展名和导出接线；这项验证属于后续治理的前置条件。根脚本必须能够继续通过既有 Node 命令执行；不得依赖共享包预先生成的 dist 或新增构建循环。共享实现落地后，`scripts/shared/path.mjs` 作为脚本侧适配入口复用共享逻辑。

共享接口分别承担可移植相对路径解析、本机路径解析与元数据格式化，基准目录显式传入。元数据格式化只转换宿主目录分隔符，POSIX 合法文件名中的反斜杠保持原值；URL 编码由输出领域处理。VFS 的大小写折叠、模块别名匹配和 URL 协议策略保留在各自模块。

路径工具不进入 UI 组件运行时导出或源码注册表。若新增共享子路径，检查包依赖、类型声明与 CLI 构建闭包，并按生成机制维护属于生成器控制的产物。

### 2. 归档与文档工具

- 在 `preflightPlan()` 解析之前处理可移植参数，保持 `docs/plans/` 边界与目标重名保护。
- 归档输出继续使用规范的仓库相对路径；Frontmatter 关联文档和 Markdown 链接按各自解析规则重算。
- 文档引擎的输入路径与输出格式化分开处理；显式 targetFiles 与文件 URL 走对应入口。
- 验证内存文档适配器中读、写、存在性检查和目录枚举使用一致的键。

归档安全加固作为独立批次交付。当前 `preflightPlan()` 已有词法目录边界、存在性及目标重名检查；这些检查不足以证明源路径及目标父目录的真实位置。新增策略如下：

- 以仓库根目录的真实路径为边界基准；源文件的词法位置和真实位置均须处于方案目录范围内，拒绝源文件本身为符号链接，以及中间链接目录将读取导向范围外的情况。
- 对归档目标校验词法目录范围；目标尚不存在时，检查最近的已存在祖先目录及其真实路径，拒绝链接或 Windows junction 将目标导向仓库外。归档根目录已存在时，其真实位置也须在仓库内。
- 在创建目标目录前完成祖先检查；目录创建后、迁移前重新核验真实目标父目录及重名状态。允许范围内的目录链接，保留路径原有大小写。
- 以临时目录夹具验证源目录外链、目标父目录外链、目标多级目录尚不存在及范围内目录链接；拒绝时不得迁移文件或改写链接与索引。dry-run 执行检查且保持文件树不变。
- 真实路径预检覆盖静态文件树的链接越界；并发替换目录产生的竞态不作为本方案已解决的保证。

### 3. CLI 与配置

- 在命令进入审计日志、项目检测与服务调用之前解析 cwd，避免同一命令中原始路径和解析后路径混用。
- `ProjectContext` 保持 API 调用边界校验，统一配置路径处理，保留别名匹配规则。
- JSON、JUnit、SARIF 与 SBOM 输出共用文件路径解析契约。
- 本地 registry 路径与网络源分流处理；组件名称仍按组件标识校验。
- 检查 `--filter`：已有分隔符处理继续保留，补验以调用目录为基准的父级相对路径分支。

### 4. 模块解析器与 VFS

- 模块解析器对相对说明符、文件绝对路径、别名和包名分别分类；已识别的路径格式必须具有一致的后续解析行为。
- 两套 VFS 均接收本机路径，可移植路径由业务入口转换后传入。所有操作使用同一规范键生成逻辑；POSIX 上反斜杠保留为文件名字符，Windows 上按宿主规则解析盘符、分隔符和点段。
- 内存 VFS 的大小写敏感策略由测试夹具显式指定，保留原始文件名用于枚举与真实路径返回。文档 VFS 的全路径小写行为改为受该策略控制；需要验证错误大小写修复的用例显式选择不敏感模式。大小写行为以实际文件系统夹具验证，不能仅凭操作系统名称假定。
- 分别验证大小写敏感与不敏感模式下的读写、覆盖、存在性和目录枚举，以及 POSIX 上 `a\b.md` 与 `a/b.md` 的独立身份。跨平台纯字符串解析测试使用显式 `path.posix` / `path.win32`，真实磁盘对照使用当前 runner 的文件系统。
- 涉及驱动器、UNC、大小写及符号链接的测试使用显式环境语义，避免内存实现将非法磁盘路径自动“修好”而掩盖生产问题。

### 5. 工程脚本

逐项验证 `consumer-artifacts`、`bench-diff`、`cost-runner`、`generate-api-docs` 和发布协调器的文件参数。对能够复现且属于可移植输入契约的分支接入工具。

发布暂存目录在任何清理、创建和子进程打包之前解析为同一绝对目录，并核验作用域。验证使用适配器或临时测试夹具，不运行真实发布或清理用户目录。

## 四、实施批次与交付清单

| 批次 | 交付物 | 完成条件 |
| --- | --- | --- |
| A：归档修复 | 归档输入契约、失败复现、脚本侧入口修复及 Windows/Linux 回归任务 | 原失败用例、词法越界、重名和链接重算通过；可独立合入 |
| B：入口契约与共享能力 | 逐入口清单、最小复现、共同契约及共享模块加载验证 | 基准目录与支持形式均有证据；提取共享实现时，独立 `.mjs` 与 CLI 两类消费者验证通过 |
| C：CLI 与模块解析 | 经复现确认的 cwd、配置、报告输出及模块解析分支 | 参数定位、写入位置、安全校验与类型检查通过 |
| D：VFS 与工程脚本 | 本机路径及显式大小写策略、制品与发布参数处理 | 点段、合法文件名、枚举和磁盘对照一致；脚本输出路径可验证 |
| E：归档安全加固 | 真实路径范围、目标祖先目录及符号链接检查 | 外链越界被拒绝、目标尚不存在可安全处理、范围内目录链接行为及 dry-run 验证通过 |
| F：总体验收与归档 | 扩展后的 CI 路径矩阵、长期使用约定及完成状态 | 各交付独立验收完成，按文档治理流程归档 |

交付分为归档故障修复（A）与后续路径治理（B—F）。A 完成即可独立验收与合入，B 的共享模块验证及 E 的新增安全能力分别验收。C、D 按 B 确认的共同契约推进；每个候选入口先复现并确认契约，再决定修复或保留现有行为。各批次可独立提交，提交说明采用 Conventional Commits。修复对外 CLI 行为时，依照发布规范判断并补充 Changeset。方案在批准实施后改为 `active`，所有验收完成后才归档。

## 五、测试与验收

### 1. 必测矩阵

| 场景 | 断言 |
| --- | --- |
| 可移植入口的正斜杠、反斜杠、混合路径与前导 `.` | 指向同一目标；输出规范的仓库相对路径 |
| 含 `..` 的合法路径与越界路径 | 合法路径正确折叠；越界在文件操作前被拒绝 |
| 中文、空格、大小写差异 | 保留文件名，按宿主与现有大小写契约检查 |
| Windows 绝对路径、UNC 与异系统输入 | 接受或拒绝符合输入分类约定，无隐式 cwd 拼接 |
| Windows 根相对路径、盘符相对路径及设备前缀 | 可移植入口按明确策略拒绝；本机入口按宿主契约处理，覆盖 `/tmp/a` 与正反斜杠 UNC |
| POSIX 本机文件名与 VFS 大小写策略 | `a\b.md` 与 `a/b.md` 可分别读写；大小写敏感和不敏感模式分别符合夹具声明 |
| 网络 URL、文件 URL 与编码字符 | 按协议解析，编码分隔符与锚点不会被错误改写 |
| 归档完整流程 | 目标路径、原文件迁移、Frontmatter、正反向链接和索引一致；dry-run 保持文件树不变 |
| 归档安全批次 | 源目录外链与目标父目录外链被拒绝；目标尚不存在及范围内目录链接符合策略；拒绝时文件和索引不变 |
| CLI 报告与配置 | 在预期目录生成文件，能重新读取配置，不生成含反斜杠的意外文件名 |
| VFS 与磁盘适配器 | 同一输入策略下读写、存在性、目录枚举与符号链接结果一致 |
| 模块解析 | 相对路径、别名、包名和越界诊断正确；既有 POSIX 导入结果保持兼容 |

纯字符串测试可以显式使用 `path.posix` 与 `path.win32` 覆盖解析差异，但文件系统行为仍需真实 Ubuntu 与 Windows runner 验证。测试应断言文件位置和内容，不能只断言替换字符串的结果。

### 2. 分层检查

归档与文档相关第一批检查：

```bash
pnpm --filter brutx-shared-vue test tests/archive-engine.test.ts tests/doc-link-engine.test.ts tests/guardrails.test.ts
```

后续按触碰范围运行 `tests/module-resolver.test.ts`、`tests/fs/memory-fs.test.ts`，以及 CLI 的项目上下文、命令、报告器、SBOM、workspace 与安全相关局部测试。对修改文件运行所属包的 ESLint；新增类型接口或共享导出时运行对应包 `typecheck`，调整依赖或导出时运行 `pnpm check:contracts`。每次文档交付运行 `pnpm check:docs`。

CI 在归档修复批次新增或复用 Ubuntu/Windows 的轻量回归任务，后续按批次扩展共享包及实际修改的 CLI 路径测试；保留现有构建、测试及 SSR 门禁。符号链接及 junction 测试记录 runner 权限与支持情况，跳过用例不能记为已验证；对应能力须在具备条件的 runner 上补齐。远程验收需确认对应提交的任务结果，不能以 Windows 本地通过代替 Linux 验证。

## 六、风险与完成判据

重点风险是输入语义扩大、VFS 掩盖宿主差异、共享工具引入加载依赖，以及规范化后绕过已有安全检查。通过输入分类、磁盘对照、两类消费者加载验证和越界测试分别控制。

完成时须满足：

- 本次归档 CI 故障在 Windows 与 Linux 均通过验证。
- 排查表中的每个入口都有复现结果、契约结论及必要修复；保留的宿主语义有测试或调用证据支持。
- 文件操作发生在约定位置，现有越界及重名保护有效；新增归档真实路径与符号链接策略独立验收通过。
- CLI 分发可用，根目录文档脚本可直接执行，UI 运行时闭包保持既有职责。
- 相关局部测试、类型、契约、文档门禁及远程 CI 通过。
- 更新长期路径约定后，执行 `pnpm doc:archive docs/plans/core/跨平台路径输入与解析一致性修复方案.md` 完成方案归档。
