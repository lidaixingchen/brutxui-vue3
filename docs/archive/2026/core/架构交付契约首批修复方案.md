# 架构交付契约首批修复方案

> 修复 CLI 公开分发、SSR 状态隔离及构建任务图三项交付契约，并建立对应回归门禁。

## 一、目标与范围

本方案落实[架构审查报告](../../../reports/audits/项目架构与工程实践审查报告.md)第一批工作。采用现有五包结构，以当前源码和 `0.11.2` 分发配置为基线。

| 工作流 | 完成后的契约 | 涉及领域 |
| --- | --- | --- |
| CLI 公开分发 | tarball 可独立安装；运行时和公开类型只引用包内文件或已交付的公开依赖 | CLI、Shared 依赖声明、分发检查 |
| SSR 实例隔离 | 同一应用的默认 Toast/Theme 共享状态，不同请求相互隔离；服务端执行不会保留全局 App 或创建浏览器资源 | fallback manager、Toast、Theme、Message、Plugin、SSR 测试 |
| 构建任务图 | 生成任务有唯一执行入口；消费者显式依赖生成结果；真实输入变化能够使缓存失效 | 根脚本、包脚本、生成器、Turbo、CI、watch 与 pack 入口 |

首批增加与这三项问题直接对应的消费者和回归测试。完整 Vite/Nuxt 消费矩阵、Registry 固定版本寻址、Release 资产发布流程属于审查报告第二批；API 产品分层和特效成本度量属于第三批。

本文件当前为待评审方案。实施时先转为 `active`，全部验收完成后再按项目规则归档。

## 三、S1：CLI 公开分发闭合

### 3.1 依赖与声明文件设计

1. `brutx-shared-vue` 保持内部工作区包定位。在 CLI 中将它声明为构建期依赖，并同步 lockfile。
2. CLI 的两个 JS 入口都把 Shared 的根入口和子路径实现打入产物。匹配规则覆盖 `brutx-shared-vue` 及其 `/fs`、`/ast` 等子入口，边界限定为该包名。
3. 先审计 `src/api.ts` 的可达声明闭包，再为 API 入口配置 `dts.resolve` 数组，解析范围限定为 Shared 包名及其子路径。第三方公开依赖保持 external，实际解析结果由 tarball 类型消费检查验证。
4. 公开 API 仍由 `src/api.ts` 显式导出。共享协议数据与纯接口保持单一来源，由声明构建器内联；CLI 专属的注入能力在 CLI 内定义结构化接口，并通过内部适配连接实现。所有公开签名保持明确的返回类型、泛型和 readonly 约束。
5. 保留 CLI 实际运行时使用的公开依赖，例如 TypeScript、Vue SFC 编译器。消费者检查负责验证其声明与实际解析一致。

边界判据覆盖三层：

| 层次 | 必须满足 |
| --- | --- |
| tarball manifest | `dependencies`、`optionalDependencies`、`peerDependencies` 及 bundled dependency 声明不要求安装内部 Shared；版本来自包清单 |
| JS | 可执行 JS 的模块引用不解析到 Shared 包或工作区源文件 |
| DTS | 声明中的 import/export、`import()` 类型及引用指令不解析到 Shared；所有引用能在独立消费者中解析 |

开发依赖字段可以记录构建工具，验收关注实际安装依赖和公开模块引用。sourcemap 中的源码来源路径不作为运行时依赖判断依据。

公开类型审计至少覆盖以下路径：

| 公开边界 | 设计要求 |
| --- | --- |
| `RegistryClientOptions.fsAdapter` 与 `RegistryClient.fs` | 文件系统能力由结构化接口表达。现有 Shared `FileSystemAdapter` 及其文件信息、删除选项均为纯接口，继续以此为单一来源；消费者可独立实现，不要求构造内部类 |
| `ResolvedComponentPlan.items`、`fetchItem()` 及服务函数的 Registry 数据 | 保持跨包 Registry 协议一致；声明闭包只包含所需数据类型和联合类型 |
| `cacheStorage`、`tracker` 及诊断/变更引擎公开参数 | 检查是否暴露带私有成员的具体实现类型；CLI 专属可注入能力使用 CLI 自有的最小结构化接口，保留实现于内部 |
| 全部公开类的属性、构造器、方法和导出函数 | 检查间接签名，不能仅检查 `api.ts` 中直接导出的类型名；内部 AST 节点和编译器实现类型不进入公共契约 |

审计产物记录声明入口、可达类型及允许的外部模块。测试使用自定义适配器验证结构兼容和行为，避免仅复制字段形成另一套共享协议。构建失败或声明出现异常膨胀时，应定位具体引入边并收敛签名；不得以放宽类型或关闭消费者声明检查通过验收。

### 3.2 独立消费者检查

新增 `packages/cli/scripts/smoke-package.mjs`，接入 `pnpm --filter brutx-vue test:package`。

检查流程：

1. 读取当前 CLI package manifest，确定名称、版本、bin 和 exports。
2. 以上游刚构建的 dist 为输入执行本地 pack。打包检查内部使用 `pnpm --config.ignore-scripts=true pack`，避免 prepack 再次进入构建或检查流程。
3. 创建位于工作区及其父级 `node_modules` 解析范围之外的临时消费者。消费者使用独立 package.json 和 lockfile，通过真实 pnpm 安装 tarball 与必要的类型检查工具。
4. 消费者进程在该目录运行，清除可能指向工作区的 `NODE_PATH`，不使用工作区软链接、类型 paths 或替身包管理器。
5. 从已安装包执行 `brutx-vue --help`，动态导入根 API，并使用公开配置构造 RegistryClient。基础 smoke 不执行组件安装等用户目录写入动作。
6. 在 `strict: true`、`skipLibCheck: false` 下分别验证 `NodeNext` 与 `Bundler` 消费模式。通过 `RegistryClientOptions['fsAdapter']`、`RegistryClient['fs']`、`ResolvedComponentPlan['items']` 等公开签名覆盖可达类型闭包，加入自定义结构化适配器及有意义的错误输入断言，防止声明退化为宽泛类型。
7. 检查安装树不存在内部 Shared 依赖，验证命令行和 API 实际解析均来自当前 tarball。

网络安装失败必须作为检查失败报告，并保留该次诊断输出。普通逻辑单测继续使用现有测试替身，真实消费者检查放在公开包变更检查和发布门禁中。

## 四、S2：SSR 实例隔离

### 4.1 状态解析契约

SSR 集成推荐在每次请求创建 App 后安装 `BrutxUIPlugin`。插件为该 App 创建并通过 `app.provide()` 注入 Toast/Theme 实例；客户端也按 App 创建实例。应用工厂及插件配置不得跨请求复用可变服务实例。

`useToast()` 和 `useTheme()` 的状态来源按以下顺序解析：

| 调用上下文 | 状态来源 | 共享与生命周期 |
| --- | --- | --- |
| 组件子树有局部 provider | 最近的 provider 实例 | 按 provider 所属作用域管理，覆盖应用根注入 |
| 处于有效注入上下文，且 App 根已提供实例（包括插件安装后的同步 `runWithContext()`） | App 根注入的实例 | 同 App 共享，由 App 管理 |
| setup 内调用，缺少 provider | 以当前 `AppContext` 为 owner 的默认实例 | 同 App 共享，不同 App 隔离 |
| 服务端且既不能注入也没有可识别的 App owner | 抛出带稳定错误码的上下文错误 | 错误说明 API 名称、同步取得实例及显式传递实例的修正方法 |
| 浏览器且没有可识别的 App owner | 浏览器便利入口实例 | 保留组件外调用能力，由显式销毁与页面生命周期清理 |

同一 App 的兄弟组件必须获得相同默认实例。局部 `provideToast()`、`provideTheme()` 优先，允许组件子树覆盖应用默认值。Registry 源码消费可以通过局部 provider 完成集成；在有效组件上下文内，按 owner 隔离的默认实例同样满足请求隔离契约。

异步使用遵循以下契约：

- 推荐在同步 setup 中取得实例，并将返回 API 显式传给异步逻辑；返回 API 的后续调用不需要当前组件指针。
- Vue 编译的 `<script setup>` 顶层 `await` 会恢复组件上下文，恢复后调用须正确共享当前 App 的实例。普通 `async setup()`、Promise 回调和任意异步函数不具有该保证。[Vue 顶层 await 文档](https://vuejs.org/api/sfc-script-setup.html#top-level-await)
- `app.runWithContext(() => useToast())` 可以同步取得应用注入的实例，再交给异步任务。`runWithContext(async () => ...)` 的 `await` 后不能依赖调用前的注入上下文。[Vue 应用上下文文档](https://vuejs.org/api/application.html#app-runwithcontext)
- 服务端确实需要独立状态时，调用方显式调用 `createToast()` 或 `createTheme()` 并持有结果；`useToast()`、`useTheme()` 在上下文缺失时不隐式制造独立状态。

插件安装和上下文传递是两个职责：插件提供应用实例，调用方在 Vue 支持的上下文内取得实例。错误码使用具名常量，测试断言错误码及操作指引。

### 4.2 fallback manager 内部模型

在现有 `createFallbackManager` 中实现 owner 感知，保持该模块作为内部基础设施：

- 用 `WeakMap<AppContext, Entry<T>>` 保存按应用共享的实例。模块级变量可以持有弱索引，不能通过另一份强集合间接长期保留服务端 owner。
- entry 管理实例、客户端引用计数和失效状态。客户端卸载回调绑定实际取得的 entry，销毁后旧回调不会误清理后来创建的实例。
- 服务端 acquire 只建立请求内数据关系，不增加客户端引用计数，不注册 `onUnmounted`、`beforeunload` 或浏览器初始化回调。
- 客户端实例的响应式作用域由 entry 管理，避免隐式挂在首个使用组件上；最后一个使用者离开时调用实例清理并停止该作用域。
- 服务端 entry 不创建需要依赖卸载回调回收的监听器、定时器或 detached effect scope。请求和 App 引用释放后，弱索引不会阻止回收。
- `destroyFallback()` 对当前客户端活跃 entry 与便利入口执行幂等清理，并替换内部弱索引。服务端正常请求处理不依赖全局销毁函数。

不把 GC 时机作为正确性前提：跨请求隔离由 owner 映射保证；弱引用仅负责避免长期保留已完成请求。

插件实例通过 App 的注入容器持有，不加入模块级服务端集合。插件安装复用内部 factory 和注入 key，不能直接调用依赖组件 setup 的 `provideToast()`、`provideTheme()`。客户端使用 `app.onUnmount()` 清理插件实例；局部 provider 和 fallback 的引用计数不得提前清理 App 持有的实例。Theme 的初始化时机遵循下一节。

### 4.3 Theme 的状态与环境副作用

为 `createTheme()`、`provideTheme()` 和插件主题选项建立统一的 `ThemeOptions`：

- `initialState` 为可序列化的 `ThemeSnapshot`，包含 `theme`、`colorMode`、`resolvedColorMode`。使用已有主题和颜色模式联合类型校验；固定模式的 resolved 值须与模式一致。
- `initialization` 明确取 `mounted` 或 `manual`。组件 provider 与应用默认实例默认在客户端 mounted 阶段初始化；SSR 集成指定 `manual`，由宿主在确认水合完成后调用 `initTheme()`。factory 本身仅创建状态和方法，组件外使用者显式初始化。
- 插件创建的实例在有效消费组件中安排一次 mounted 初始化，且只在 `mounted` 模式生效；此初始化安排不会转移 App 对实例的所有权。`manual` 模式覆盖普通 provider、插件和所有后续消费者的自动初始化行为。

状态更新与环境副作用按阶段分离：

| 阶段 | 状态和副作用契约 |
| --- | --- |
| SSR 渲染 | 从当前请求的快照或固定默认值初始化；状态方法可以修改本实例；不读取 localStorage、媒体查询或 DOM，不注册客户端资源 |
| 客户端初次渲染与水合 | 在渲染前恢复与服务端相同的快照；初始化前的状态修改只作用于实例，不通过存储或系统偏好覆盖首帧，也不提前写 DOM |
| 客户端初始化 | `initTheme()` 幂等开启 DOM、存储与媒体监听。优先使用初始化前显式设置的字段，其次使用由快照恢复的字段；缺省字段才采用有效存储值和既有系统默认策略 |
| 初始化后的交互 | `setTheme()`、`applyColorMode()` 同步本实例状态、DOM 和存储；`system` 模式跟踪系统变化，固定模式保持显式选择 |

宿主从请求可读的 cookie、用户设置或固定默认值取得主题快照，使用框架的安全序列化通道传递给客户端。客户端在 `createSSRApp()` 挂载前恢复同一快照，不能在首帧用不同的 localStorage 值替换它。显式快照优先于存储值；`system` 模式在初始化后才用客户端媒体查询刷新解析结果。

SSR 集成文档提供插件与局部 provider 两种示例，说明 `manual` 初始化的调用位置。存在 Suspense 或延迟水合时，宿主应在所有读取该共享主题的待水合边界完成后初始化；无法统一同步的分支由框架按客户端渲染处理，不以首个消费组件的 mounted 充当整个应用水合完成信号。

主题防闪烁脚本由宿主的 head 管理与 CSP 策略负责。首批不提供通用内联脚本生成器；示例要求前置脚本、服务端输出和客户端首帧采用同一主题决策。首批必须验证状态与水合正确性，首屏闪烁度量和完整 Nuxt 集成矩阵仍按后续批次推进。

`theme`、`colorMode` 保持公开配置状态的可写契约，内部检测状态只读。根主题样式继续作用于 `document.documentElement`，视觉作用域为整个文档。仅改变 Vue 管理范围外的根主题类不等同于必然水合错误；验收重点是使用主题状态的实际渲染树与客户端首帧一致。[Vue 水合说明](https://vuejs.org/guide/scaling-up/ssr.html#hydration-mismatch)

### 4.4 Message、Plugin 与弹层服务端守卫

当前 `useMessage().show()` 已在服务端返回空操作，`mountOverlay()` 也在没有 document body 时返回空宿主。首批围绕这两条契约补齐外围生命周期：

- `useMessage()` 在服务端直接返回空操作 API，不增加模块级 `refCount`，不注册卸载、定时器或延迟 GC。
- `BrutxUIPlugin.install()` 向当前 App 注入 locale、Toast/Theme 并注册指令；服务端不把 App 写入模块级 `globalApp`，`getGlobalAppContext()` 返回 `null`。主题选项仅传递配置与初始快照，不能使插件默认实例跨 App 复用。
- `mountOverlay()` 的服务端守卫保持位于 DOM 创建和 App 上下文回退之前；返回 Promise 按当前 API 契约完成，不新增悬挂 Promise。
- 客户端 Message 与命令式弹层的宿主模型保持既定职责。本批验收双 App 的 Toast/Theme 状态隔离，不将其解释成整个命令式宿主系统已支持双 App 隔离。

### 4.5 回归测试矩阵

新增 `packages/ui/src/ssr/request-isolation.test.ts`，使用真实 `createSSRApp()` 和 `renderToString()`：

| 场景 | 关键断言 |
| --- | --- |
| 连续请求 | A 写入 toast 或主题，B 的状态与 HTML 不含 A 的值 |
| 并发请求 | 用可控 Promise 屏障交错两个请求，A、B 均只读取自己的状态；不通过固定 sleep 制造时序 |
| 同请求兄弟组件 | 一个组件写入默认实例，另一个组件读取相同实例 |
| 显式 provider 与插件 | 最近 provider 优先；插件按 App 创建实例，局部覆盖与应用默认实例彼此独立 |
| 服务端无 owner | `useToast()`、`useTheme()` 抛出可诊断错误；显式 factory 仍能创建独立实例 |
| 异步上下文 | 编译后的 SFC 顶层 await 正确恢复；普通异步断层明确报错；异步前捕获的实例持续有效 |
| 应用同步上下文 | `runWithContext()` 同步取得插件实例；异步回调越过 await 后重新调用受上下文规则约束 |
| 服务端资源 | 监测定时器、存储与媒体查询；插件安装、Message 和弹层调用不创建对应资源或保留全局 App |
| 客户端双 App | Toast/Theme 状态独立；卸载 A 不清理仍由 B 使用的实例 |
| 销毁后重建 | 全局显式清理幂等；旧卸载回调不会影响新实例 |

顺序请求用例在 A 与 B 之间禁止调用 `destroyBrutxUI()` 或重置模块，以免测试替实现完成隔离。异常渲染后的下一次请求同样需要验证。

主题水合新增真实 SSR → 浏览器测试：Node 端用 `renderToString()` 生成 HTML 与快照，通过测试夹具交给现有 Chromium 测试入口；浏览器恢复相同快照并水合，不用手写 HTML 代替服务端输出。让 localStorage 与服务端主题不同，覆盖固定模式和 system 模式，断言首帧文本/属性一致、没有水合告警、初始化后按规定更新且监听器只注册一次。额外加入延迟边界用例，验证 `manual` 模式不会被较早 mounted 的消费者提前激活。

`test:browser` 在启动 Vitest 前以独立 Node 执行阶段准备本次水合夹具，避免浏览器环境检测污染服务端渲染。生成 HTML、快照和测试加载信息放在 UI 测试缓存目录；准备失败时停止浏览器测试，测试结束后逐一清理。本地和 CI 使用同一入口，不依赖此前运行过 SSR 测试留下的产物。

修改范围：[fallback manager](../../../../packages/ui/src/lib/fallback-manager.ts)、[useToast](../../../../packages/ui/src/composables/useToast.ts)、[useTheme](../../../../packages/ui/src/composables/useTheme.ts)、[useMessage](../../../../packages/ui/src/composables/useMessage.ts)、[Plugin](../../../../packages/ui/src/plugin.ts)、[环境适配](../../../../packages/ui/src/lib/env.ts)及其直接关联测试与 SSR 集成文档。`render-imperative.ts`、`destroyFallbacks.ts` 的修改限于上述上下文和清理契约。

## 五、S3：生成与构建编排

### 5.1 任务命名与公开命令

将公开命令入口与 Turbo 实际执行任务区分开。公开入口负责选择任务，实际任务执行器不再反向启动公开入口。

| 任务名称 | 所有者 | 职责 |
| --- | --- | --- |
| `generate` | UI | 按顺序生成令牌、扫描清单、组件 index、package exports |
| `generate` | CLI | 生成 CLI 样式及 utils 模板的令牌内容 |
| `build:artifact` | UI、CLI、Registry、Docs | 只构建本包交付物；不在任务体内运行生成器 |
| `typecheck:source` | 各适用包 | 执行当前包的类型检查和既有静态类型契约 |
| `lint:source` | 各适用包 | 执行当前包 lint，不写生成文件 |
| `test`、`test:ssr` | 各适用包 | 运行现有测试；由任务图准备所需构建结果 |
| `test:browser` | UI | 先准备本次 SSR 水合夹具，再运行浏览器测试 |
| `test:package` | CLI | 检查已完成构建的真实 tarball 消费 |

公开命令保持 `pnpm build`、`pnpm typecheck`、`pnpm lint`、`pnpm --filter <pkg> build/typecheck/lint`。根命令分派至上述实际任务；包级公开入口从工作区根调用 Turbo 并指定包过滤器。例如 UI 的 `build` 入口分派 `build:artifact`，实际任务只调用 Vite、构建后导出验证和 preflight 编译。

`pnpm --filter <pkg> test <路径>` 保留聚焦测试与参数传递能力。需要生成或 dist 的场景先由对应构建入口准备，CI 与根测试编排通过任务依赖统一准备。

### 5.2 必须声明的依赖边

| 消费任务 | 必须先完成 |
| --- | --- |
| UI `build:artifact`、`typecheck:source`、`lint:source` | UI `generate` |
| CLI `build:artifact`、`typecheck:source`、`lint:source` | CLI `generate` |
| Registry `build:artifact` | `brutx-ui-vue#generate` |
| Registry `validate` | Registry `build:artifact` |
| Docs `build:artifact`、`typecheck:source` | UI `build:artifact` |
| 包级 `test`、UI `test:ssr` | 本包适用的 `build:artifact` |
| UI `test:browser` | UI `build:artifact` |
| CLI `test:package` | CLI `build:artifact` |

Shared 继续按源码工作区包使用，读取 Shared 的任务直接把其源码与 package 配置纳入输入。Registry 的源代码编译仅依赖 UI 生成契约，不需要等待 UI 的 JS/CSS 打包。

CI 的集中执行使用实际任务名称，例如 `turbo run build:artifact typecheck:source lint:source`。现有 UI 类型契约 `check-twmerge-colors`、构建后 exports 验证与 preflight 编译必须保留在正确阶段。

### 5.3 生成文件唯一写入者

UI 的 `generate` 执行顺序固定为：令牌生成 → AST 清单扫描 → 组件 index 生成 → package exports 生成。CLI 的 `generate` 独立生成本包令牌目标。

| 生成入口 | 负责文件 |
| --- | --- |
| UI `generate` | `registry-manifest.json`、`exports-manifest.json`、`src/components/*/index.ts`、`package.json` 的 exports、`src/styles.css` 的生成区、`src/preflight.css` 字体栈、`src/lib/utils.ts` 生成列表 |
| CLI `generate` | `src/styles/brutalist.css` 生成区、`src/lib/constants.ts` 中 `UTILS_TEMPLATE` 生成区 |

实施要求：

- 既有 `prebuild:*` 手动入口通过所属包的生成入口执行，生成器的计算职责仍留在所属包内。
- 新增包级生成编排脚本，复用现有生成函数。混合手写与生成的文件仅更新已声明生成区。
- 同一次 Turbo 调用通过依赖图对 `generate` 去重，生成脚本不再被各消费任务隐式调用。CI 将相关任务合并为同一次 Turbo 执行，各 job 使用隔离工作区。
- 每包生成入口以排他创建的占用标记保护跨命令重入，标记记录诊断信息和唯一令牌。标记已存在时立即非零退出，报告包名与标记位置；不轮询、不自动抢占，不按 PID 存活检查推断可安全删除。持有者在 finally 中仅释放令牌仍匹配的标记。
- 文件内容变化时才替换文件；使用目标目录内的临时文件及原子替换写入，失败后返回非零状态，不继续运行消费任务。
- 占用标记放在包缓存目录，临时文件使用每次调用的唯一名称并放在目标目录，结束时逐一清理。强制终止留下标记时，在确认生成进程已退出后显式清理对应标记并重跑；Windows 替换失败保留诊断，不通过删除目标源文件绕过错误。
- 文件集合以成功完成的 `generate` 为消费边界，不宣称多个文件具备单次文件系统事务。中途失败后重新执行必须能够收敛到确定产物。

生成器与构建检查模式分离。复用 `generate-exports.ts` 已有的 `--check`、`--verify`；为其他生成器补充只读一致性检查或集中比较入口。`lint:source` 和 `typecheck:source` 自身不修改生成产物，其公开入口可以通过前置生成任务完成准备。

同一 checkout 的支持边界为一次构建编排或一个 watch 写入会话。需要同时运行不同构建命令时，合并任务到同一 Turbo 调用，或使用独立 worktree。每包占用标记只负责生成阶段的重复进入检测，不承诺隔离整个源码读取过程或多个进程对同一 dist 的写入；watch 期间的额外检查使用准备完毕的只读任务。单次任务图的去重不能替代不同 Turbo 进程之间的协调。

### 5.4 缓存策略

1. UI/CLI 的 `generate` 首批设 `cache: false`。生成任务写入源树和 package 元数据，不交由缓存恢复工作区文件。
2. Registry 的实际 `build:artifact` 继续 `cache: false`，签名环境变量继续显式传递。
3. 缓存输入以 `$TURBO_DEFAULT$` 为基线，按包追加跨包源码和相关生成文件，确保 `tsup.config.ts`、Vite/Vitest/TS/ESLint 配置与构建脚本进入实际输入。
4. UI 构建明确纳入 gitignore 中的生成组件 index；不能仅依赖默认 Git 跟踪文件集合。读取混合生成文件的任务必须把完整文件作为输入。
5. UI、CLI 的 `build:artifact.outputs` 只包含各自 `dist/**`；Docs 包含 `.vitepress/dist/**`。生成文件不混在构建缓存输出中。
6. 测试缓存纳入实际执行的 `src`、`tests`、`scripts`、测试配置及其依赖任务；消费者类型任务纳入 `test-d`。分发检查涉及真实安装，首批不缓存其成功结果。
7. 具有 Node 版本或操作系统矩阵的任务将运行环境标识纳入哈希。标识由统一命令引导层依据 `process.version`、`process.platform`、`process.arch` 派生，CI 与本地使用同一方式注入。

生成任务依赖完整源输入，保证新增组件或令牌变化传播到下游，即使本次命令启动时源树中的生成结果尚未更新。冷构建、生成后的再次构建和缓存命中都必须参加等价性验证。

### 5.5 pack、watch、提交钩子与 CI

| 入口 | 目标行为 |
| --- | --- |
| UI/CLI `prepack` | 调用该包公开构建入口，完成生成与 artifact 构建；包测试内的 pack 显式关闭生命周期，避免递归 |
| UI/CLI `dev` | 初次先生成；源码变化后串行执行生成及增量构建，保证新组件和令牌变化被捕获 |
| Registry `build:watch` | 初次及重建前等待 UI 生成；同一时间只执行一轮，变化到来时合并排队 |
| `.husky/pre-commit` | 调用统一生成入口；基于既有暂存范围处理生成文件，避免将无关未暂存内容加入提交 |
| `ci.yml` | 采用新任务图；加入 CLI package contract、SSR 隔离及构建图回归检查 |
| `publish.yml` | 同步任务名称，增加首批 package/SSR/构建契约门禁；资产发布顺序属于第二批 |
| `deploy-docs.yml`、`bench.yml` | 更新相应任务调用，使其通过同一构建入口准备产物 |
| 根 `release`、`build:docs`、`generate:tokens` | 分派到统一实际任务，不再在不同入口拼装各自的生成顺序 |

watch 对生成引起的相同内容事件做去重，避免自激循环；手写与生成内容混合的文件不能按整个路径永久忽略。提交钩子遇到手写输入同时存在暂存与未暂存变更时，应给出明确诊断并停止自动暂存，避免让生成文件代表另一份源码快照。

### 5.6 修改范围

根 `package.json`、`turbo.json`、各包 package 脚本；UI/CLI 生成入口及生成器；Registry runner/watch；`.husky/pre-commit`；四份现有工作流；`docs/guides/COMMANDS.md` 与相关开发流程文档。

占用标记和条件写入仅在 UI/CLI 确实共享实现时放入 Shared 的内部 `/fs` 子模块，职责限定为排他创建、令牌校验释放与文件替换。包级脚本承担顺序编排，复用既有文件系统设施。新增测试分别归入对应包。

### 6.2 CI 分层

- 日常开发运行触碰模块的定向单测、包级类型检查和对应契约。
- PR 的质量任务运行构建图和公开包检查；SSR job 执行请求隔离与资源守卫，浏览器 job 执行主题水合夹具。首批涉及 runtime、生成器、构建配置、依赖声明的变更都触发对应检查。
- 发布门禁要求 CLI tarball 独立消费、SSR 回归和构建契约通过，使用将被发布的同一份构建结果。
- 检查失败报告具体包、任务、输入文件或消费者编译错误。失败不能通过更新一份接受缺陷的基线来放行。

## 七、验收矩阵

以下均为实施阶段必须执行的验收，本文编写完成不代表这些验收已经通过。

| 编号 | 验收动作 | 通过标准 |
| --- | --- | --- |
| C1 | 构建 CLI 后 pack，解析 tarball manifest | 安装依赖不要求 Shared；包版本与当前清单一致 |
| C2 | 扫描 tarball 的可执行模块与声明引用 | Shared 根路径、子路径及工作区路径均不成为外部模块依赖 |
| C3 | 干净目录真实安装 tarball，执行命令行和程序 API smoke | 安装、解析、执行成功；消费的包就是本次 tarball |
| C4 | 独立消费者的 NodeNext/Bundler 严格类型检查 | `skipLibCheck: false` 下通过，错误输入被检出 |
| C5 | 遍历公开声明闭包并用自定义适配器消费 | 公共签名只依赖允许的纯数据、接口与公开外部类型；内部编译器类型不泄露 |
| S1 | 连续两次 SSR | B 不包含 A 的 toast/主题状态 |
| S2 | 可控异步交错 SSR | A、B 分别只读到自身数据，无全局 reset 辅助 |
| S3 | 同应用兄弟组件与嵌套 provider | 默认实例共享，provider 优先级正确 |
| S4 | 服务端资源监测与异常渲染后续请求 | 不创建浏览器资源、全局 App 引用或 Message 引用计数；后续请求隔离 |
| S5 | 客户端双 App 与销毁后重建 | Toast/Theme 状态独立；卸载不跨实例清理 |
| S6 | 普通异步断层、SFC 顶层 await、runWithContext | 上下文缺失时明确报错，Vue 恢复的上下文和预先取得的实例正常共享 |
| S7 | SSR HTML 在 Chromium 中恢复快照并水合 | 存储偏好冲突不改变首帧；无水合告警；初始化与 system 更新符合阶段契约 |
| S8 | 插件所有权、局部 provider、延迟水合边界 | 局部卸载不清理 App 实例；manual 初始化在宿主确认前不自动执行 |
| B1 | 修改 CLI tsup 配置后比较实际 dry-run | CLI artifact 哈希改变 |
| B2 | 修改 Shared 令牌、UI 源码及生成脚本 | 所需下游任务哈希改变；Registry 在 UI 生成后执行 |
| B3 | 单次并行执行 build/typecheck/lint | 每包生成任务只执行一次，检查阶段不写源文件 |
| B4 | 同一包两个生成进程重入、模拟替换失败及终止残留 | 第二个进程立即报错且不改输出；失败阻止下游；显式恢复后产物确定 |
| B5 | 隔离副本中新增组件或依赖，再运行 Registry 构建 | 自动准备清单并编译正确闭包，无手动预热步骤 |
| B6 | 冷构建、缓存命中、强制构建对比 | UI/CLI dist、类型、CSS 的相对文件集合和内容哈希一致 |
| B7 | 校验 Registry 重建内容 | 组件与依赖闭包一致；签名与完整性校验通过 |
| B8 | pack、包级过滤构建和 watch 新增组件 | 均按约定准备生成物；watch 无生成事件循环 |
| B9 | Node/系统矩阵的缓存检查 | 不同运行环境的相关任务缓存键可区分 |

B6 在相同目录、相同源码与相同运行环境中比较，排除路径不同造成的 sourcemap 差异。B7 对生成时间、耗时等运行元数据逐字段声明比较策略；组件源码、版本、依赖、完整性字段不能被归入可忽略项。签名按验签结果检查，不以忽略签名来通过等价检查。

新增组件的验收在隔离副本中调用项目脚手架，临时源码和配置变化不施加到开发工作区。缓存恢复检查仅操作该副本中明确记录的输出文件，并逐一清理。
