# 文档体系与文档网站协同改造方案

> 统一工程文档的事实与规则，精简 AGENTS.md，补齐现行架构说明，并同步文档网站的安装、迁移和贡献指引。

## 一、目标与实施边界

本方案面向仓库维护者、贡献者和文档使用者，建立从现行实现到内部说明、再到用户指引的维护关系。

交付目标：

1. 常青文档中的命令、路径、生成来源和生命周期定义与实际工具保持一致。
2. 每项工程约定具有明确的权威文档；`AGENTS.md` 提供通用约束和任务阅读入口。
3. 新贡献者能够通过现行架构文档理解包职责、分发契约与构建过程。
4. 中英文文档网站准确说明公开 API、安装方式、升级路径和贡献流程。
5. 自动检查覆盖可确定的命令、状态、索引、页面完整性与示例类型问题，并在网站部署前阻断失败产物。

本轮实施范围包括 `AGENTS.md`、`docs/`、相关包 README、`apps/docs/`、文档检查脚本与定向测试，以及以下协同入口：

- `.github/PULL_REQUEST_TEMPLATE.md`、`.github/copilot-instructions.md`：同步本轮涉及的规则、检查选择、权威来源和链接。
- `skills/brutxui/SKILL.md` 及受影响的 `references/`：同步安装选择、公开 API、使用示例和链接，遵循 [AI 技能维护指南](../../../../skills/README.md) 的外部使用者定位。
- `.github/workflows/ci.yml`、`.github/workflows/deploy-docs.yml` 及必要的命令配置：接入文档与示例验证，保证网站部署使用通过检查的同一提交和产物。

组件、CLI、生成和包发布的业务行为作为核对依据；发现实现缺陷时单独登记修复项，避免通过文档整理改变运行时契约。检查与工作流调整限于本轮文档交付所需的验证链路。

当前交付是方案文档。方案进入实施时转为 `active`，全部验收完成后按归档流程处理；撰写完成不代表改造已经落地。

### 3.2 文档中心的阅读顺序

首页依次提供：理解项目、开发组件、修改分发与构建、发布版本、维护文档、查看活跃方案、查阅报告与归档。

归档入口按年度和领域展示数量与链接，完整主题列表在对应归档索引中查看。活跃方案列表显示标题、状态和简述。既有 `AUTO_ACTIVE_PLANS`、`AUTO_ARCHIVE_PLANS` 标记继续作为生成区域边界。

调整索引展示时同步修改 [索引投影实现](../../../../scripts/docs/lib/archive-engine.mjs)。抽出可独立调用的刷新与只读检查入口，使新建方案、状态调整和归档都能更新索引。刷新索引只更新文档；归档操作继续按既有契约处理迁移与暂存。

### 3.4 编写与同步原则

- 按读者任务组织正文：入门页面帮助完成首次使用，操作指南指导具体任务，API 参考陈述接口，架构说明解释职责与机制。沿用现有生命周期目录，在导航和页面职责中应用 [Diátaxis 文档分类](https://diataxis.fr/map/)。
- 可机械核实的值、接口和示例优先共享输入或派生；面向不同读者的解释分别编写，并明确引用的权威来源。
- 每批变更同时交付权威正文、受影响入口、中英文使用说明和对应检查。原位置精简前，承接正文必须完整可读；新增目录时同批更新治理与索引。
- API、安装和规则变更时，按本方案同步矩阵核对网站、包 README、PR 模板、Copilot 指引和使用者技能。PR 清单记录受影响位置及验证结果，人工审核承担自然语言语义和版本归属判断。

| 内容 | 调整方式 |
| --- | --- |
| 生成文件详细清单与 Registry 缓存原理 | 集中到生成与构建机制；AGENTS 保留保护要求和入口 |

### 4.3 约定统一提案

本节是拟采用的规则，随方案评审确认后再写入 AGENTS 和对应指南。修改 AGENTS 时遵循其维护约定，不把未经确认的偏好写成既定事实。

- **类合并**：以当前根 AGENTS 的严格要求统一，动态类名在 `computed()` 中计算，模板绑定计算结果；同步 CVA、组件指南和中英文贡献指南。将其表述为本仓库编码约定；解释性能时依据响应式依赖和缓存行为，[Vue 官方说明](https://vuejs.org/guide/essentials/computed.html#computed-caching-vs-methods) 同时支持计算属性与模板方法调用。
- **原语复用**：优先复用 Reka UI 和已有组件；特殊 ARIA 语义且没有适用组件的场景，在组件指南集中说明边界，避免使用无法覆盖基础组件实现的绝对表述。
- **注释**：解释当前复杂业务逻辑与边界条件；变更原因、审查取舍与跳过结论写入报告或交付说明。
- **只读状态**：区分内部可变状态、对外只读状态和公开可配置状态；说明 `DeepReadonly` 是类型工具，`readonly()` 是运行时 API。
- **检查选择**：日常按触碰领域运行针对性检查；发布流程执行完整门禁。统一命令的执行目录与副作用说明。
- **API 演进**：允许按当前需求调整 0.x API；涉及消费者变化时同时交付迁移说明，避免将破坏式变更写成每次修改的目标。

## 八、文档自动检查设计

复用 [文档检查聚合入口](../../../../scripts/docs/check-docs-all.mjs) 和现有调度器，按以下边界补强检查。检查过程只读取内容，修复入口显式执行写入。

### 8.1 命令与脚本引用

- 命令检查按第九节分批覆盖：第一批纳入发布与命令文档、本批修改的 PR 指引；第二批扩展至 AGENTS、工程指南、新架构文档、中英文贡献指南和 Copilot 指引。每个文件中属于支持语法的命令完成校准后，同批启用检查；使用者技能、用户项目安装示例与历史方案按各自语境处理。
- 核对仓库任务命令是否存在于根配置或明确指定的包配置，区分根目录、包目录、`--filter`、`pnpm exec` 和 `pnpm dlx`。
- 首版支持声明执行目录的单条 Shell 命令、命令表格及明确标注为仓库命令的行内片段；从 Markdown 中抽取这些内容后，仅解析所支持的命令形式。复合 Shell、动态目录切换、变量替换、占位命令和错误示例显式跳过，并报告位置、原因与未覆盖范围。
- 检查具体 Node/tsx 脚本路径存在性。命令检查不执行发布、安装、归档或其他带副作用的命令。
- 复用已有 Markdown 解析中适用的能力，补充代码围栏与表格内容提取，输出文件、位置、执行目录和原因。集中维护执行语境与例外声明，并对支持范围和跳过行为建立回归；新增语法由实际漏检场景驱动。

### 8.2 生命周期与索引

- 将状态集合与状态解析收敛为文档工具共享定义，供状态扫描、归档和索引使用。
- 新方案使用 `draft / active`；`done` 表示待归档；归档结果使用 `archived`。
- 对既有 `implemented` 值逐篇确认含义后规范化，先完成数据处理再收紧校验；状态名称不能单独证明任务已经完成。
- 治理指南的字段示例和状态表从共享定义派生或建立一致性检查；错误提示使用项目实际字段名。
- 索引提供刷新与检查两种模式；覆盖新建未跟踪方案、状态变化、归档和重复运行，保持手写导航区域稳定。

### 8.3 网站页面与示例

- 对已配置导航的指南检查目标页面存在、具有有效正文，并核对中英文对应页面，拦截仅有标题的发布页面。
- 组件章节与覆盖检查继续使用现有门禁；核实并修正文档对 `check:i18n:strict`、页面镜像检查和模板检查职责的描述。
- 将本轮修改的导入、公开类型与关键用法示例登记到固定验证集合，按第六节直接引用受测源码。验证集合持续进入 CI 和网站部署前置检查，避免仅在本轮人工执行。
- 校验中英文页面的代码片段目标、命名区域与受测源码的对应关系。站点构建负责渲染，类型检查负责接口兼容，真实消费者场景负责安装与产物解析；三类结果分别记录。
- 链接与命令检查显式覆盖新增的协同入口；外部网站地址与仓库相对链接按各自语境处理，核对精简后仍有效的章节入口。
- 自然语言规则冲突、版本归属和迁移说明充分性由人工审核；自动检查只承诺能够确定验证的范围。

### 8.4 网站部署前置检查

- [CI](../../../../.github/workflows/ci.yml) 与 [网站部署工作流](../../../../.github/workflows/deploy-docs.yml) 使用同一套文档和示例验证入口。部署工作流在当前检出的提交上完成 `pnpm build:docs`，执行 `pnpm check:docs`、`pnpm --filter docs typecheck` 及固定验证集合中的消费者场景，全部通过后才上传并部署本次构建产物。
- `push` 和 `workflow_dispatch` 均经过上述检查。检查步骤使用阻断失败的执行方式，上传和部署依赖检查成功；重新运行仍检查当前部署提交。
- 构建、检查和上传之间保持同一源码提交与候选产物。现有缓存可以复用构建结果，上传仍须经过本次部署的验证入口；涉及 npm 或 CLI 的示例验证使用与该提交对应的候选包或注册表。
- 为工作流配置建立定向契约测试，检查两个触发入口、验证步骤、执行顺序和上传条件。通过隔离的失败样例验证门禁返回非零退出码，再校验该失败会使上传与部署步骤不可达；验证过程使用模拟上传/部署，不写入正式站点。
- 记录提交标识、检查命令、结果和产物标识，作为部署前置检查的验收证据。

### 8.5 必要的回归场景

| 检查领域 | 成功场景 | 失败场景 |
| --- | --- | --- |
| 命令 | 有效根脚本、包脚本、外部工具示例按语境识别；复杂命令明确报告跳过 | 不存在的根命令、过滤包不匹配、脚本路径不存在、未报告的漏检语境 |
| 状态 | 新建草案、实施中方案、合法归档 | 未知状态、目录与状态不匹配、文档模板枚举漂移 |
| 索引 | 新方案可见、重复生成稳定、手写区保持 | 遗漏方案、残留旧路径、归档数量不符 |
| 网站 | 导航目标可达、中英文均有内容、展示与受测示例共用源码 | 空指南、缺失镜像、失效的片段引用、已移除导出的示例 |
| 协同入口 | PR 模板、Copilot 指引和使用者技能引用当前规则与示例 | 失效的文件或章节引用、技能示例与受测源码不一致 |
| 部署 | 同一提交与候选产物通过全部前置检查后允许上传 | 内容门禁或示例验证失败仍可上传、任一触发入口跳过检查 |
