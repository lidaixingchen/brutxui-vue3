# 架构交付契约第二批修复方案

> 建立两种分发方式的真实消费者门禁、Registry 快照与版本重放契约，以及资产完整、可恢复的统一发布流程。

## 一、目标、证据与前置条件

本方案落实[架构审查报告](../../../reports/audits/项目架构与工程实践审查报告.md)第二批工作，承接[第一批方案](架构交付契约首批修复方案.md)。以第一批落地后的工作区和 `f1ee89ca` 提交为参考，实施前记录实际提交及工具版本。

| 工作主题 | 完成后的契约 |
| --- | --- |
| 消费者测试 | 安装实际 UI/CLI tarball 后，npm 组件与 CLI 复制源码均能在 Vite、Nuxt 消费者中完成类型检查、生产构建及关键浏览器行为 |
| 版本化 Registry | 一次操作固定一个 Registry 快照；组件及依赖沿用该快照；已安装来源与基线可核验、可重放 |
| 统一发布 | 同一提交只构建并封存一组待交付产物；Release 公开前资产完整；npm 发布与重试消费同一组字节，并校验已存在版本 |

当前代码依据：

- [UI package smoke](../../../../packages/ui/scripts/smoke-package.mjs) 通过软链接解析工作区包；[CLI 矩阵](../../../../packages/cli/tests/integration/matrix-runner.test.ts) 依赖现有测试辅助设施，尚未承担真实依赖安装和应用生产构建。
- [消费者类型配置](../../../../packages/ui/test-d/consumer/tsconfig.json) 使用 `skipLibCheck: true`；[CI](../../../../.github/workflows/ci.yml) 尚未形成覆盖两种分发方式的真实消费者发布门禁。
- [RegistryClient](../../../../packages/cli/src/lib/registry-client.ts) 对默认 Release 源忽略显式版本；逐项取件、源回退及依赖展开需要改为操作级快照。
- [RegistryCompiler](../../../../packages/registry/src/compiler/registry-compiler.ts) 的 `registryVersion` 当前为固定 `0.1.0`，构建 manifest 的 `gitCommit` 为 `null`；[现有 manifest 摘要](../../../../packages/shared/src/registry.ts) 未包含提交身份。
- [发布工作流](../../../../.github/workflows/publish.yml) 在上传资产前公开 Release，重试会覆盖资产，并通过错误文本跳过已存在的 npm 版本。[本地发布入口](../../../../package.json) 与 tag 工作流各自承担发布动作。

启动实施时必须确认第一批的三项前置契约：CLI tarball 安装与声明通过；SSR 隔离与主题水合通过；构建及生成任务依赖明确。第一批文档归档不替代这些结果。尚未满足的项作为对应阶段的阻塞条件处理，本批不重复建立其底层实现。

本批保留五包结构与现有组件体系。公开 API 产品分层、基础组件特效成本和全仓规则精简属于第三批。运行本方案中的发布演练以本地测试服务和只读远程核验为边界；正式 tag 推送与对外发布按发布任务单独执行。

## 二、实施顺序

| 阶段 | 交付 | 前置条件 | 完成判据 |
| --- | --- | --- | --- |
| T0：冻结回归与交付模型 | 消费者模板、快照 A/B、发布故障场景、版本映射与 provenance 验证夹具 | 第一批前置契约可复验 | 每个风险对应可重复断言；工具版本固定，记录 CI 耗时基线和真实服务验证状态 |
| T1：真实消费者基线 | UI tarball、CLI 源码安装、Vite/Nuxt 与浏览器门禁 | T0；CLI 分发及 SSR 契约通过 | 当前候选产物在核心矩阵中可安装、构建和运行 |
| T2：Registry 快照与重放 | 版本元数据、签名摘要、操作级快照、本地基线 | T0；生成任务图通过 | 指定版本、依赖闭包、缓存及更新均保持快照一致 |
| T3：发布产物封存与恢复 | 交付清单、draft 上传、逐项核验、npm 幂等发布 | T1、T2；发布适配器定稿前完成 provenance 兼容性验证 | 同一产物通过门禁后交付；每个失败阶段均可安全重试，真实服务验收证据完整 |
| T4：联合验收与迁移说明 | CI 分层、完整故障演练、开发及使用文档 | T1—T3 | 第七节验收完成，正式发布入口和文档一致 |

默认顺序为 T0 → T1 → T2 → T3 → T4。T1 使用明确的本地 Registry 产物启动消费者验证；T2 将同一批场景接入快照协议；T3 复用消费者入口验证封存产物。实施阶段可以并行开发独立模块，协议与交付清单需要先定稿。

## 三、T1：真实消费者测试

### 3.1 测试产物与目录隔离

1. 从一次完成的构建取得 UI、CLI tarball 与 Registry 目录，生成候选产物描述文件，记录提交、包版本、相对文件名与摘要。描述文件格式复用第五节的交付清单；本地及 PR 产物明确标识为测试用途。
2. 使用第一批已建立的 CLI pack 能力；UI `test:package` 改为安装真实 tarball。已有 exports 枚举和入口检查继续保留，并将解析起点改为消费者目录。
3. 临时消费者位于仓库及其父级依赖解析范围之外。清除指向工作区的 `NODE_PATH`，不配置工作区 alias、junction 或 `workspace:` 依赖。
4. 使用真实 pnpm 安装。消费者能访问公开依赖仓库，但 UI/CLI 只能来自指定候选 tarball；记录安装后的解析路径、包版本和 tarball 摘要。
5. 框架模板、直接依赖版本和基础 lockfile 入库。候选 tarball 与 CLI 安装产生的依赖变动只更新临时消费者的 lockfile；最终锁定后再执行 frozen install，保存该锁作为失败重放输入。
6. 测试启动的服务使用系统分配端口，通过就绪探测等待启动，以具名超时配置控制失败。进程退出、浏览器关闭和临时文件逐一清理均由测试持有者负责；Windows 子进程默认隐藏窗口。

进程管理器从启动时记录本次运行拥有的进程及其身份，覆盖正常结束、启动失败、超时和取消。先关闭浏览器与服务资源，在具名宽限期后终止仍存活的进程树并等待退出；不以 `child.kill()` 返回成功作为清理完成。Windows 对仍由本次运行持有的根进程可使用 `taskkill /PID <pid> /T /F`；父进程先退出的场景通过启动时建立的进程归属记录或 Job Object 管理残留子进程，终止前核验身份，避免 PID 重用误伤。Linux 使用本次运行独占的进程组。禁止按 `node.exe` 等通用进程名清理。[Node 子进程语义](https://nodejs.org/api/child_process.html#subprocesskillsignal)、[Windows taskkill](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/taskkill)

确认进程和文件句柄释放后，校验临时路径位于本次测试目录内，再逐一清理文件及空目录，不跨越符号链接或 junction。仅对可重试的 `EBUSY`、`EPERM` 等锁定错误进行有界指数退避；超时、间隔、次数由配置维护。保留原测试错误并附清理诊断；清理失败本身也使任务失败，输出残留路径。增加“父进程启动持锁子进程后退出”和“服务启动超时”的 Windows 回归，验证无残留进程、端口和文件锁。

依赖工具版本由一份消费者矩阵配置维护，不能在 CI 临时使用 `@latest` 初始化应用。Nuxt 核心场景沿用当前集成模板对应的 Nuxt 3 系列，并锁定实际可用版本；额外框架主版本通过明确扩展矩阵纳入，不隐含宣称支持。

### 3.2 核心消费矩阵

| 编号 | 消费方式与宿主 | 必须覆盖 |
| --- | --- | --- |
| U1 | UI tarball → Vite + Vue + Tailwind v4 | 根入口与代表性子路径、SFC 类型、样式入口、生产构建、基础交互 |
| U2 | UI tarball → Nuxt SSR | 服务端实际 HTML、插件/provider、主题快照、客户端水合和弹层交互 |
| C1 | CLI tarball → Vite 源码项目 | `init`、`add`、配置与样式注入、依赖真实安装、生产构建 |
| C2 | CLI tarball → Nuxt 源码项目 | Nuxt 配置注入、组件发现、真实 SSR 与水合、生产服务启动 |
| C3 | CLI tarball → pnpm workspace 子应用 | 从根及子包执行时的目标定位、依赖落位、兄弟包完整性、子应用构建 |

每种分发方式至少覆盖基础 Button、具备依赖闭包的 DataTable，以及 Dialog/Select 的弹层或键盘场景。组件清单由测试配置维护，新增样例依据风险选择。

UI 另分两档依赖安装：根入口综合消费安装声明要求的 peer 集合；子路径基础消费仅安装所选组件实际需要的 peer，验证不会隐式要求无关重型依赖。缺失某组件必需 peer 时，应修正相应声明或隔离边界，不能向所有模板无差别安装整仓 devDependencies。

CLI 复制源码的应用通过本地生成目录导入组件，不额外安装 UI 二进制包兜底。源码、语言包、utils、变体和 Tailwind 样式必须来自 CLI 的完整安装结果。

### 3.3 类型、样式与更新行为

- 在真实消费者中执行 `vue-tsc` 或宿主类型检查，开启 strict 与 `skipLibCheck: false`。迁移现有 consumer 断言，覆盖 props、emits、slot 泛型、composable 及根/子路径导出；错误类型输入必须被检出。
- CSS 验收包括样式入口可解析、生产 CSS 生成，以及浏览器中代表组件的计算样式。npm 与源码消费都验证主题变量、边框、阴影和交互状态，不以 CSS 文件存在作为完成标准。
- `init` 重复执行、同版本 `add` 和 `doctor` 的行为可重复；对幂等动作比较前后文件和依赖配置。
- 更新测试使用两个确定快照：安装 A → 修改本地组件 → 预览并更新 B。无冲突修改保留；冲突产生明确预览并按现有交互契约处理，不能静默覆盖。
- `remove` 场景先移除消费者对目标组件的使用，再执行删除并重建；存在其他组件依赖时验证依赖保护，避免把模板自身残留 import 误判为库缺陷。
- 同一 Registry 快照在相同 CLI、配置和依赖 lockfile 下应能重建相同投影源码。Registry 固定版本不意味着第三方 semver 范围自动锁定，完整应用重放必须同时保存消费者 lockfile。

### 3.4 浏览器与现有门禁接入

补充以下真实 Chromium 用例，并复用现有 Vitest Browser/Playwright 配置：

| 领域 | 关键断言 |
| --- | --- |
| Dialog 嵌套弹层 | 初始焦点、Tab/Shift+Tab、Escape 关闭顺序、关闭后焦点返回、卸载后的滚动状态 |
| Select/Combobox | 键盘展开与选择、禁用项跳过、活动项与 ARIA 状态、Teleport 下焦点行为 |
| VirtualScroll | 实际视口与滚动定位、数据更新后可见区域、键盘目标可达；以可见行和窗口化约束断言，不绑定内部 DOM 结构 |
| Nuxt SSR | 服务端已包含预期内容、客户端 hydration 无告警、事件可用、第一批主题初始化契约在宿主中成立 |

`test:types`、`check:isolation` 和 `test:coverage` 接入第六节的固定 CI 任务：相关代码 PR 运行类型、隔离与受影响回归，main 与正式候选运行完整覆盖率。覆盖率使用现有配置阈值，在 T0 记录实际基线；若未达到则修复对应测试缺口，不降低阈值或扩大排除范围放行。覆盖率不替代消费者与交互验收。

现有替身集成测试继续承担快速逻辑检查。`BRUTX_RUN_FULL_INTEGRATION_MATRIX` 只控制其已有矩阵；真实消费入口显式运行且输出用例清单，不能因环境变量缺失而全部 skip。

## 四、T2：Registry 快照与版本重放

### 4.1 版本身份与构建输入

| 字段 | 含义与来源 |
| --- | --- |
| `schemaVersion` | Registry 协议版本，由 Shared 中的具名常量定义 |
| `registryVersion` | 本次源码组件版本，来自 UI package.json；与私有 Registry 包的工具版本分开 |
| `releaseTag` | 正式分发 tag，按 `v<UI version>` 派生，构建时校验远程 tag 实际指向 |
| `gitCommit` | tag 解引用后的完整提交 SHA；正式分发必须存在 |
| `integrity` | 对规定字段和组件摘要集合计算的 manifest 摘要，作为快照内容身份 |
| `signature`、`keyId` | 对 manifest 摘要的签名及受信密钥标识，沿用现有 Ed25519 设施 |

`runBuild()` 将版本身份显式传入编译器，index、manifest 和 SBOM 从同一构建上下文派生。删除固定产品版本赋值，编译器工具版本从对应包清单读取。开发构建允许明确的本地身份，不伪造正式 tag；正式构建缺少或不匹配身份时失败。

协议增加字段和摘要输入时提升 schema 版本，发布端与 CLI 校验端复用同一规范化实现。摘要纳入 `releaseTag`、`gitCommit`、版本及所有影响安装的组件元数据。规范化规则固定编码、键排序与数组语义；时间和耗时留在诊断信息，不参与快照身份。

每个组件资产同时记录现有文件内容 integrity 与整个组件 JSON 的字节摘要。后者覆盖 dependencies、registryDependencies、cssVars 等安装决策，CLI 必须先核验完整资产，再解析及展开依赖。正式 manifest 需完整 schema 校验与摘要复算，不能因字段缺失而跳过复算。

产物按确定顺序序列化一次，计算摘要的 Buffer 与写盘的 Buffer 相同。组件资产先就绪，再计算 manifest 与签名，最后生成依赖 manifestIntegrity 的 SBOM。manifest 不反向包含 SBOM 摘要，避免循环；第五节交付清单统一核验包括 manifest、index、SBOM 在内的最终文件。

### 4.2 源解析与版本选择

默认源建立明确的 GitHub 仓库描述，集中复用现有源配置；根据 repo 与 tag 构造地址，不从临时 CDN 重定向 URL 猜测源身份。

| 用户请求或源类型 | 解析规则 |
| --- | --- |
| 默认源 `button@<精确版本>` | 规范化为精确 tag，直接取得该 tag 的 manifest 和资产；校验 manifest 版本/tag 相符 |
| 默认源 `button` 或 `button@latest` | 操作开始时通过 latest manifest 发现并验证 tag，再从固定 tag 下载同一 manifest，确认摘要一致后固定会话 |
| 同次操作一个显式版本，其余省略版本 | 全部根组件沿用该显式版本 |
| 同一源出现不同显式版本或不受支持范围 | 在变更计划前失败，报告冲突或不支持的版本选择器 |
| GitHub raw 源 | 可重放请求使用固定完整 commit 地址，并验证快照；可变 ref 不能仅通过字符串替换被宣称为固定版本 |
| 自定义 HTTP/本地源 | 使用有效 manifest 与内容摘要固定会话；支持精确版本须有明确映射，缺少能力时明确失败 |

latest 只用于发现，不参与组件及依赖的逐项下载。预发布版本必须显式指定，稳定 latest 不自动选择预发布。发现阶段遇到 latest 切换可按具名上限重新发现；固定快照后不再切换版本。

官方远程源要求受信签名验证通过。自定义源使用现有信任配置；允许的未签名本地源仍必须通过 schema 和完整性校验，并记录其信任级别。显式版本、严格验签与离线错误均不能降级到 latest 或其他不匹配源。

### 4.3 操作级会话

在 RegistryClient 内增加 `RegistrySnapshot` 与操作级读取会话，使用只读类型表达：逻辑源身份、固定下载地址、版本/tag、提交、schema、manifest 摘要、组件摘要集合和信任结果。

1. `resolve()` 先解析根组件的版本约束并固定快照，再按该快照展开完整依赖图。
2. 根组件、传递依赖、locale 与其他安装资源都使用同一会话。依赖内显式版本必须与当前快照相容，否则给出依赖路径与版本冲突。
3. 会话在一次 CLI 命令或一次程序 API 操作中复用；`fetchItem()` 等单件入口自行建立短会话，批量操作使用同一会话，不依赖模块级“最后命中源”。
4. 多源回退只允许切换到同一快照的镜像，要求身份和摘要一致。没有完整闭包时失败；不能在两个不同发布版本中拼接成功结果。
5. `list`、`diff`、`add`、`update`、变更引擎与诊断按实际需求传递快照。删除仅依赖本地清单时不增加远程请求。
6. 完整闭包验证成功后才形成文件与依赖变更计划。复用现有文件事务；失败不得留下部分源码和与之不符的安装清单。

### 4.4 缓存与本地记录

缓存键包含逻辑源、manifest 摘要及组件资产摘要。固定快照的缓存与 latest 发现缓存分开；后者使用短期策略且不作为已安装版本的身份。single-flight 去重必须包含快照身份，失败 Promise 不污染后续重试。

离线模式只使用已记录且完整、校验通过的快照与资产。缺少一个依赖即明确失败；已安装记录可用于离线重放，不能把一次旧 latest 缓存标成当前最新。缓存命中仍验证内容与当前信任策略，凭据不进入缓存键的可读日志或项目清单。

扩展现有安装 manifest schema，至少保存：

| 记录层 | 必要内容 |
| --- | --- |
| 快照表 | 逻辑源与固定地址、版本/tag、完整提交、schema、manifest 摘要、签名标识及信任级别 |
| 组件记录 | snapshot 引用、组件资产摘要、现有文件内容 integrity、安装文件、依赖与安装时间 |
| 投影基线 | 当前 CLI 版本、投影格式版本、影响源码的配置摘要，以及安装时投影到用户目录的原始基线字节引用 |

源记录使用去凭据的可移植描述；敏感请求头继续由配置提供。沿用 `.brutx/manifest.json`，投影基线存放于 `.brutx/baselines/` 内容寻址目录，路径在记录中保持相对形式。基线、组件文件与清单按现有事务能力一致落盘。

三方合并使用“安装时基线 → 用户当前文件 → 目标快照投影”。优先读取并校验持久化基线；缺失时仅在能够验证旧快照和相同投影规则的条件下恢复，不能用当前 latest 伪造旧基线。旧清单迁移保持用户源码不变，无法确认来源的条目标识为待重建，阻止依赖该基线的自动覆盖，并给出只读差异与迁移说明。

项目协作采用以下存储契约：

| 内容 | Git 与恢复约定 |
| --- | --- |
| `.brutx/manifest.json` 与所引用的 `.brutx/baselines/` 文件 | 作为更新依据，随组件源码、CLI 配置及消费者 lockfile 一起提交；基线是源码副本，按内容去重，不假定体积可忽略 |
| `.brutx/.gitattributes` | 随基线提交；在该文件中为 `baselines/**` 设置 `-text`，保持哈希对应的原始字节，避免 Git 换行转换改变基线 |
| 下载缓存、日志、临时目录与事务运行态 | 使用独立的可重建目录，按实际路径提供精确 ignore 规则；不纳入源码基线 |
| 凭据与敏感请求头 | 留在现有安全配置渠道，不写入上述入库文件 |

初始化文档给出 `.gitignore` 建议：保留 `.brutx/manifest.json`、`.brutx/baselines/` 与 `.brutx/.gitattributes`，只忽略明确的运行态路径。CLI 输出应提交的文件与新增基线大小，不自动执行 Git 暂存；发现项目已有整目录 ignore 时，`doctor` 提示团队重放受影响并给出具体规则位置，不直接覆盖用户规则。Git 的 `-text` 语义见 [gitattributes](https://git-scm.com/docs/gitattributes)。

现有下载缓存默认位于用户主目录的 `.brutx-vue/cache`，项目不需要为它添加 ignore。若通过 `BRUTX_CACHE_DIR` 将缓存配置到项目的 `.brutx/cache/`，对应的项目 `.gitignore` 规则为下例；`.brutx/` 本身保持可跟踪。其他运行态路径按实际配置列出，不用整目录通配兜底。

```gitignore
/.brutx/cache/
```

基线文件写入后不可原地修改；每次更新引用新的内容摘要。跨成员克隆、分支切换后，先验证清单引用与基线摘要，再允许合并；不在普通安装/更新中自动清理可能被其他分支引用的基线。消费者源码自身的 LF/CRLF 差异由合并输入的统一换行规则处理，不改变持久化基线的字节身份。

用户选择忽略基线时，`doctor` 和更新预览明确区分“基线可校验”“可从旧快照恢复”“恢复条件不足”。只有取得完整旧快照、相同投影版本及配置，并复算出记录中的基线摘要，才保存恢复结果；恢复所需的投影配置需随去凭据记录保存，不能只有配置摘要。缺少旧资产、对应投影能力或网络时保持只读差异并阻止自动合并。恢复基线只写基线与清单，不改用户组件；用户可在恢复后重新预览更新。

不要求历史 Release 全部补齐新协议。新的精确快照能力从声明的支持版本开始，旧 schema 在需要该能力时明确报错。Changeset 与使用文档说明 CLI 最低版本、清单迁移及精确版本语法。

### 4.5 确定性回归场景

测试 HTTP 服务使用本地生成的两个签名快照 A/B 和测试专用密钥，控制响应顺序；不访问真实 latest 制造时间竞争：

- 在根组件返回后把 latest 从 A 切到 B，传递依赖仍全部来自 A。
- 同一命令请求冲突版本、缺失依赖或循环依赖时，在写文件前失败。
- 镜像返回同版本但不同摘要时拒绝；相同快照镜像允许继续。
- 篡改 tag、commit、依赖元数据或组件 JSON 时能够被检出。
- 在线安装 A、清理测试内存状态后按本地记录离线重放 A；缺失缓存时明确失败。
- A → 本地修改 → B 更新验证合并和冲突策略；基线不存在时不会自动覆盖本地修改。
- 成员 A 安装并提交后，成员 B 在没有 A 下载缓存的新克隆中读取基线、修改源码并更新 B；目标快照由测试服务提供，合并不依赖旧快照下载。
- Linux 写入并提交基线后，Windows 在启用换行转换的克隆中仍通过字节摘要校验；分支切换保持清单与基线引用一致。
- 分别覆盖忽略基线后的成功恢复、旧快照不可用、投影配置缺失和基线损坏；恢复不改变当前源码，条件不足时不自动合并。

## 五、T3：统一发布与失败恢复

### 5.1 入口、版本与责任

正式发布由 `publish.yml` 执行同一套发布协调脚本，本地保留准备、检查和打 tag：

| 命令或入口 | 最终职责 |
| --- | --- |
| `pnpm release:prepare` | 消费 changeset、准备版本和 Changelog，并执行现有准备流程 |
| `pnpm release:check` | 构建、契约与核心消费者检查；生成本地检查结果，不写远程发布状态 |
| `pnpm release` | 调用 `release:check`，输出正式 tag 流程指引 |
| `pnpm release:tag` | 校验版本、检查结果与提交一致后创建 annotated tag；已存在 tag 仅在同一提交时视为完成 |
| tag push / 同一 workflow 重跑 | 校验固定 tag，准备或恢复交付产物，执行发布状态机 |

本批采用统一发行批次，tag 使用 `v<UI version>`，Registry 源码版本沿用 UI 版本。每次正式交付需要新的 UI 版本；CLI 单独变化时同步声明 UI patch，表示该批次的分发工具链交付。Changeset 与 UI Changelog 明确写出关联的 CLI 修复及 UI 组件行为保持一致，不能编造组件修复。两个公开包仍独立记录各自版本，交付清单逐包映射，不根据 tag 猜测 CLI 版本。

这项产品发布约定会增加 UI 用户收到的版本通知，准备阶段应显式列出本批次的包变更与发布原因，消费者测试仍验证整批交付。T0 固化“UI 单独变化、CLI 单独变化、两者变化、包内容未变化”四种准备场景，核对 Changeset、包版本、tag 和清单映射。

准备阶段比较包版本与实际待交付内容。相同 npm 版本的字节发生变化时要求新的 changeset；未变化的包可复用已核验的既有发布。正式 tag 不移动，修复代码使用新版本；同一 tag 的工作流重跑只恢复原交付。

GitHub 命令使用 `gh`，参数结构化传递；Release Notes 通过文件提供。根 release、工作流和文档不得保留另一条独立的本地 npm 发布通道。

### 5.2 一次构建与交付清单

新增 `release-manifest.json`，由发布协调脚本生成，包含：

- 交付清单 schema、tag、完整提交、Registry 版本与 manifest 摘要。
- UI/CLI 各自版本、tarball 名称、SHA-256 与 npm SRI 摘要、目标发布 channel。
- 所有 Registry JSON、SBOM 和 tarball 的相对资产名、长度及字节摘要。
- 用于构建的 Node、pnpm、lockfile 摘要，以及适用的测试矩阵版本。
- 清单自身的规范化摘要、签名和 keyId；自身不进入资产摘要集合。

Registry 的 manifest 负责源码快照，release manifest 负责整次交付的字节集合。生成顺序为组件资产 → Registry manifest 与签名 → SBOM → tarball → release manifest 与签名，避免摘要之间的循环引用。

构建完成后使用 `pnpm --config.ignore-scripts=true pack` 封存 tarball。候选包与 Registry 都从封存目录参加消费者门禁；发布时使用相同 tarball，不重新从包目录触发 prepack。pnpm 支持按 tarball 发布，具体参数以仓库锁定版本的命令验证为准。[pnpm 发布文档](https://pnpm.io/cli/publish)

T0 准备最小 provenance 验证夹具，以根 `packageManager` 锁定的 pnpm（当前为 `11.21.0`）验证 tarball 读取、生命周期行为和实际发送字节；T3 发布适配器定稿前取得相同工具链、工作流及认证方式的真实环境证据。发布工作目录保留已核验 tag 的源码 checkout，封存目录可位于工作区内；即使调整目录，仍只发布原 tarball 并在发送前后核验摘要。Git 检查参数、tag checkout 行为与 provenance 生成分别验证，禁止通过重新打包或关闭 provenance 绕过失败。

真实验证运行在受支持的 GitHub 托管 runner，核对 `id-token: write`、包的 public repository 元数据、仓库/提交身份及发布认证。对已经明确授权的测试包或预发布版本，完整执行“构建封存 → 上传/下载产物 → 消费者检查 → 原 tarball 发布”，记录远程 tarball 摘要、attestation subject 摘要、源码提交与工作流身份；恢复运行同时记录首次构建与本次发布的关联。上述行为以正式服务证据验收，本地仓库或 `--dry-run` 只证明参数与字节路径。[npm provenance 前置条件](https://docs.npmjs.com/generating-provenance-statements/)

该验证属于单独授权的对外发布任务，可复用满足上述条件的既有证据。本方案编写及本地实施不自动创建测试发行；真实证明缺失时可继续消费者、快照及本地协调实现，正式发布切换保持待验收。工具版本、权限、认证或发布路径变化后，重新验证受影响条件。

封存目录是本次交付的唯一产物来源。上传 Actions artifact 并记录其身份和清单摘要，随后把同一组产物附到 draft Release。重跑优先下载既有封存产物并验签、验摘要；确需重建时必须逐字节匹配已封存集合。新的时间戳、随机 SBOM 标识或压缩元数据不能改变同一候选产物的含义，相关值应确定化或保存在首次封存结果中。

签名密钥仅提供给签名步骤；消费者依赖安装和测试只使用公钥。npm 凭据只提供给发布步骤，PR 与本地测试使用测试密钥或明确未签名候选模式，不依赖正式发布凭据。

### 5.3 发布状态机

| 状态 | 动作 | 进入下一状态的条件 |
| --- | --- | --- |
| 已准备 | 核验 tag、提交、包版本、changeset 与生成物；构建并封存 | 身份一致，完整资产与清单存在 |
| 已验证 | 对封存产物运行核心消费者、快照和现有发布门禁 | 必需检查通过且结果绑定清单摘要 |
| 草稿资产就绪 | 复用或创建指定 tag 的 draft；上传资产及清单 | 远程资产名称集合、长度、摘要和签名均通过 |
| Release 已公开 | 将 draft 发布，明确发送 `make_latest: "false"` | 固定 tag 的匿名下载可用且资产核验通过，稳定 latest 未提前推进 |
| npm 版本就绪 | 按依赖顺序发布原 tarball 到候选 dist-tag，并核验已存在版本 | 每个包的版本及远程 tarball 摘要匹配 |
| 渠道已推进 | 推进稳定 Registry latest，再推进适用 npm dist-tag | 两条消费路径均指向完整交付；不回退已存在的更高版本 |
| 已完成 | 从公开端点核对映射并运行轻量消费检查 | 发布汇总记录版本、tag、提交、资产摘要和验证结果 |

创建 draft 时使用已存在远程 tag，并检查解引用后的提交，不允许 CLI 自动从默认分支补建 tag。草稿不是需要自动删除的残留；相同 tag 下仅复用身份匹配的草稿，出现多个或身份不符时停止并报告。

Release 发布与渠道推进统一由 `gh api --method PATCH --input <请求文件>` 调用 REST API。请求文件使用 JSON 序列化：公开草稿发送 `draft: false`（布尔值）与 `make_latest: "false"`（字符串）；全部 npm 版本核验完成后，符合推进条件的稳定发行才发送 `make_latest: "true"`。不依赖默认值或 `"legacy"` 自动选择；预发布保持 `prerelease: true` 且不推进稳定 latest。固定 gh 与 API 版本，并以请求断言检查字段类型。每步写入后读取 Release 及 `/releases/latest` 的实际指向；已有稳定发行须保持原指针，首次发行允许 latest 暂不存在。[GitHub Release API](https://docs.github.com/en/rest/releases/releases)

上传前按交付清单列举文件，避免 `*.json` 把调试输出纳入发布。上传后分页取得全部资产：核对精确名称集合、状态、长度与摘要，关键文件下载后本地重算并验签；不能只检查文件个数或 signature 字段存在。GitHub 自动生成的源码下载链接不属于本项目上传的资产集合。

正式 Release 公开后禁止覆盖或删除资产。开启 GitHub immutable releases 作为服务端保护，并在正式发布预检中核实；当前仓库开关状态需实施时读取，不能由文档推定。GitHub 支持先创建 draft、附齐资产再公开，并允许随后调整 latest 标记。[GitHub 不可变 Release](https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases)

### 5.4 幂等性、渠道与失败恢复

| 发现的远程状态 | 处理规则 |
| --- | --- |
| 同 tag 的 draft，部分资产缺失 | 核验已有资产与清单；只补缺失资产，同名不同摘要立即失败 |
| draft 内上传出现中断或损坏条目 | 保留诊断，明确清理对应未完成资产后重试；仅操作该 draft 的单个资产 |
| 同 tag 的公开 Release | 校验已公开资产及提交；完全匹配后从 npm 阶段继续，不重写 Release 内容 |
| npm 版本不存在 | 发布清单内 tarball，保留 provenance 并验证远程结果 |
| npm 版本已存在 | 查询远程 manifest 与 dist.integrity，必要时下载 tarball 重算；匹配才跳过，不依据错误文本判定成功 |
| 仅一个 npm 包已发布 | 保持已成功版本，重试另一个；全部就绪前不推进正式渠道 |
| 渠道推进中断 | 重新读取两端实际指针并补齐；更高版本已生效时不降级 |
| tag、提交或资产摘要不一致 | 停止当前交付，输出具体差异；修复代码以新版本发布 |

候选 dist-tag 名称从发行身份派生，并集中配置。稳定版本完成后推进 `latest`；预发布只推进预发布 channel，Registry 也保持 prerelease 且不成为稳定 latest。重跑旧发行不得重新抢占较新发行的渠道。

GitHub 与 npm 之间没有跨服务原子事务；本方案保证先备齐资产、再补齐 npm 版本、最后推进渠道。渠道推进仍存在短暂中间状态，失败后按远程事实收敛，不通过移动 tag、撤销已发布版本或覆盖资产模拟回滚。新协议首次发行须明确 CLI 最低支持版本及升级顺序，避免将旧客户端对新 schema 的行为当作兼容保证。

发布并发沿用全局串行组且不取消进行中的发布；脚本还需要在关键写入前重新核验远程状态。重试只对网络和服务临时故障采用有界退避，权限错误、摘要冲突与协议错误立即失败。

### 5.5 本地故障演练

发布协调逻辑与远程访问适配器分开，使用临时文件系统、GitHub API 测试服务及本地 npm 测试仓库演练。真实 pnpm tarball 发布、查询和安装参与本地测试；不向正式 GitHub Release 或 npm 发送测试版本。

必须注入：上传到一半失败、响应丢失但远程已成功、npm 第二个包失败、同名不同摘要、tag 指向错误、公开 Release 重跑、渠道推进中断、旧版本重跑。故障后比较远程状态及请求记录，确认没有改写已公开资产。

正式环境预检负责验证实际 gh/pnpm 版本、认证权限、immutable 配置及 §5.2 的 provenance 证据。测试服务必须区分字符串 `make_latest` 与布尔字段，覆盖首次发行和已有 latest 两种情况；本地替身不被描述为已证明真实服务权限可用。

生成清单通过所属生成器更新；保持包自治。协议逻辑归 Shared/Registry/CLI，根脚本只编排跨包交付，不再建立另一套 Registry 编译器或通用工作流平台。

### 6.2 门禁分层

| 触发 | 必需检查 |
| --- | --- |
| 定向开发 | 相关单测、受影响包类型检查、对应契约 |
| 普通相关代码 PR | Linux U1/C1 最小消费者组合；类型、隔离、受影响单测及浏览器回归 |
| 涉及宿主或交付边界的 PR | 在普通 PR 门禁上按下表增加 U2/C2/C3、进程清理或发布回归 |
| main 集成与正式发布候选 | Linux 全部核心矩阵、Windows 消费与清理矩阵；完整覆盖率、快照重放、第一批 SSR/水合、发布状态机回归 |
| 同一发行的恢复运行 | 核验封存产物与测试证明后恢复；证明缺失或失效时针对原产物重跑门禁 |

PR 扩展选择写在受测的矩阵配置中，并在任务开始时输出触发原因：

| 变更领域 | PR 增量门禁 |
| --- | --- |
| Nuxt 模板、插件/provider、SSR 状态、主题初始化及宿主集成 | Linux U2/C2 与相关 SSR/水合用例 |
| CLI 项目定位、包管理器执行、依赖安装及 workspace 配置 | Linux C3；涉及 Windows 路径或进程生命周期时增加 Windows 定向回归 |
| Registry schema、快照解析、投影、基线与更新 | 快照/重放回归；跨宿主投影变化增加 C2，基线字节与换行变化增加跨平台克隆回归 |
| 发布脚本、封存格式及发布工作流 | 完整本地发布故障演练与产物字节检查；真实权限验证沿用第五节边界 |
| 根依赖/lockfile、Shared、构建配置、exports、消费者执行器或矩阵选择器 | Linux 全部核心矩阵，防止公共变更绕过间接受影响路径 |

纯文档 PR 可由明确的路径规则标识消费者检查不适用；代码变更无法分类时采用完整 Linux 矩阵。选择器测试覆盖公共路径、文件删除/重命名和未知路径；受保护的汇总任务核对预期用例与实际结果，不把误判为空矩阵视为通过。Windows 全量组合在 main/正式候选执行，相关 PR 保留定向 Windows 回归。

操作系统、Node 和工具链组合在矩阵文件集中维护，至少覆盖 Linux 与 Windows。包的最低 Node 支持与框架工具链支持分别验证；如消费者工具链要求更高版本，必须记录交集，不能借调整测试版本掩盖公开 engines 不成立。

真实安装和远程状态核验不缓存成功结果。pnpm store 按 OS、架构、工具版本和依赖 lockfile 缓存，正常安装优先复用本地下载；仅在 store 已按当前 lockfile 完整预热的场景使用离线安装，冷缓存允许真实下载并验证失败路径。缓存候选构建产物时，键包含 tarball/Registry 摘要、模板、lockfile、脚本与运行环境。消费者任务依赖第一批实际构建任务，使用稳定公共命令接入，不再次引入重复生成入口。

T0 分别测量冷缓存和热缓存下的安装、构建、浏览器启动、执行与清理耗时，T4 用重复运行记录 p50/p95、网络失败和不稳定用例比例。普通 PR 热缓存关键路径以 5 分钟为初始工程目标，样本数量、并发度及超时预算均落入矩阵配置；目标与实测结果分别报告。超预算时按测量瓶颈优化模板复用、并发和下载缓存，不静默减少必需用例。仅对暂时网络错误有限重试，断言失败及重试后通过的用例单独报告。

新增测试命令明确为 `test:consumers`、`test:release`、`release:check`。依赖第一批已落实的 `test:package`、`test:ssr`、`test:browser` 等入口。CI 输出实际运行用例数和结果；受保护门禁未运行、全部跳过或消费者安装失败都不能作为成功。

快照类型及服务返回值发生变化时，复用第一批 CLI tarball 类型检查验证公开声明，确保新增协议类型没有再次泄露私有工作区依赖。

## 七、验收矩阵与聚焦命令

本文列出实施验收，不代表方案编写时已经执行或通过。

| 编号 | 验收动作 | 通过标准 |
| --- | --- | --- |
| E1 | 从同一候选产物安装 U1/U2/C1/C2/C3 | 安装、严格类型、生产构建成功，解析路径全部属于消费者 |
| E2 | 子路径与综合入口的依赖分档 | 基础消费不依赖无关 peer，综合消费声明完整 |
| E3 | 生产应用 CSS 与 SSR 水合 | 样式生效、SSR 内容正确、水合无告警且交互可用 |
| E4 | 浏览器焦点、键盘、虚拟滚动 | 行为与公开契约一致，无焦点或滚动资源残留 |
| E5 | CI 类型、隔离、coverage 及用例清单 | 实际执行，既有阈值通过，没有全 skip 放行 |
| E6 | Windows 正常结束、父进程先退出、超时和取消 | 本次拥有的进程树退出，端口/文件锁释放；残留清理有界且不影响其他进程 |
| E7 | PR 风险选择、冷/热缓存与耗时记录 | 各风险触发预期矩阵；store 缺失仍真实安装，输出实测耗时及不稳定用例 |
| V1 | 构建指定 tag 的 Registry | 版本来自 UI，tag/commit/index/manifest/SBOM 一致 |
| V2 | 重复安装精确版本，期间切换 latest | 仍取得同一 manifest 和完整依赖闭包 |
| V3 | 冲突版本、缺依赖、不同快照镜像 | 写入前明确失败，不拼接版本 |
| V4 | 篡改版本身份、依赖元数据或组件字节 | schema、摘要或签名校验检出 |
| V5 | 清空内存后按记录离线重放 | 缓存完整时结果一致，缺失时明确失败 |
| V6 | 安装 A、本地修改、更新 B | 三方合并保留本地修改；冲突和缺基线不自动覆盖 |
| V7 | 旧清单迁移与不支持 schema | 保留用户文件，来源状态明确并给出迁移指引 |
| V8 | 新克隆、跨平台及分支切换后更新 | 入库基线摘要一致，清单引用有效，不依赖另一成员的下载缓存 |
| V9 | 基线忽略、缺失或损坏后的恢复 | 可验证的旧投影恢复成功且不改用户源码；条件不足时阻止自动合并 |
| R1 | 上传中断 | Release 保持 draft，已有默认渠道可用，重跑补齐缺失资产 |
| R2 | 公开前完整性核验 | 精确资产集合及字节摘要通过，正式签名验证通过 |
| R3 | 同 tag 重跑与同版本 npm 已存在 | 完全匹配则恢复，不同字节停止；不依靠错误文本跳过 |
| R4 | npm 部分成功、渠道推进失败 | 从远程状态恢复，只补未完成阶段，不重发或覆盖既有版本 |
| R5 | 旧发行重跑与预发布 | 不回退 stable 指针，预发布不进入稳定 latest |
| R6 | 产物在构建、测试、上传及 npm 之间传递 | 使用同一组封存字节，SRI/摘要与交付清单一致 |
| R7 | 本地正式入口与流程文档 | 本地准备/检查、云端统一发布；tag 固定且命令一致 |
| R8 | 锁定工具链原 tarball 携带 provenance 发布 | 真实服务证据关联源码/工作流、attestation 与封存摘要；缺少证明时不能启用正式发布 |
| R9 | draft 公开、npm 就绪后推进 latest | 请求字段及类型正确；公开时未抢占 latest，推进后读回目标；首次及预发布行为明确 |
| R10 | UI/CLI 单独变更及共同变更 | 版本、Changeset、Changelog 与统一发行 tag 映射一致，逐包内容可核验 |

## 八、交付与归档

按职责形成可审查提交：消费者门禁、Registry 协议、CLI 重放、发布协调、CI 与文档。跨包 schema 变更及 CLI 行为变化在相应 Changeset 中声明，用户文档提供确定版本安装、项目清单迁移、基线随 Git 协作、缺失基线恢复和发布失败恢复的可操作示例。

验收结果记录实际提交、工具链、候选产物摘要及矩阵结果。正式外部服务权限或仓库配置尚未验证时明确记录限制，不能把本地演练描述成已完成正式发布。

方案编写阶段保持 `draft`；实施开始后转为 `active`。代码、测试及必要配置全部完成并通过验收后执行：

```powershell
pnpm doc:archive docs/plans/core/架构交付契约第二批修复方案.md
pnpm check:docs
```
