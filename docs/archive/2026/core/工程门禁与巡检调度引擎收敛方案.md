# 工程门禁与巡检调度引擎收敛方案

---

## 一、 背景与第一性原理

### 1. 现状痛点分析

在 BrutxUI Vue 3 的工程自动化体系中，门禁脚本已全面接入了结构化诊断协议（Agent Result Envelope）与 Unix 沉默原则。但在底层的执行与调度层面，存在显著的**调度胶水代码重复（Duplicated Runner Glue）**与**调度编排能力分散**问题：

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│                          当前工程门禁调度链路现状                           │
├─────────────────────────────────────────────────────────────────────────────┤
│ 1. scripts/check-contracts-all.mjs (357 行，契约门禁聚合入口)               │
│    ├─ getRunner(): 检测 LOCAL_TSX 与 npx tsx 平台环境（重复实现）           │
│    ├─ spawn 子进程、StringDecoder 缓冲流拼接、超时熔断处理（重复实现）       │
│    ├─ Agent Result Envelope 协议反序列化、状态机汇总与表格渲染（重复实现） │
│    └─ Promise.all 无限并发拉起进程（无并发池限流，无孤儿进程信号清理）      │
│                                                                             │
│ 2. scripts/docs/check-docs-all.mjs (382 行，文档门禁聚合入口)               │
│    ├─ 逐字复制 check-contracts-all 的 getRunner、spawn 与解析逻辑           │
│    ├─ 逐字复制终端表格渲染、建议自愈动作（suggested_actions）组装逻辑       │
│    └─ 自愈（--fix）逻辑硬编码耦合在聚合脚本入口中，未形成标准能力           │
│                                                                             │
│ 3. 门禁单项脚本的独立性与调度层边界模糊                                     │
│    └─ 各聚合脚本各自处理字段命名（id vs name）、超时时长与错误编码配置      │
└─────────────────────────────────────────────────────────────────────────────┘
```

1. **调度执行器逻辑重复达 80%（Duplicated Runner Glue）**：
   - `scripts/check-contracts-all.mjs`（357 行）与 `scripts/docs/check-docs-all.mjs`（382 行）的核心调度逻辑高度雷同。
   - 两者各自维护了 200 余行底层的子进程调度、流编码拼接、协议解析、失败分类、退出码决策与表格渲染代码。一旦诊断信封协议（Envelope Protocol）演进或新增输出格式（如 CI 摘要或专用注解），必须跨文件同步复制修改，极易发生协议分叉。
2. **缺乏受控并发调度与进程树生命周期管理（Process Lifecycle & Concurrency）**：
   - 现有脚本均采用无限制的 `Promise.all` 并发派生所有任务。当门禁项持续扩展时，在 Windows 环境下极易诱发瞬时 CPU 负载尖峰与 I/O 争抢。
   - 缺少对 `SIGINT`（Ctrl+C）与 `SIGTERM` 信号的统一捕获转发，主进程意外中止时容易残留后台孤儿子进程。
3. **自愈能力（Auto-Fix）缺少统一契约抽象**：
   - 当前 `--fix` 自愈动作硬编码于 `check-docs-all.mjs` 的入口函数中，未作为规则定义的一等公民纳入生命周期统一管理，使得新增支持自愈的门禁项时成本高昂。

### 2. 移除性测试（Deletion Test）

- **假设删除聚合脚本中的子进程管理、流解析与信封聚合代码**：
  复杂度并未增加，`check-contracts-all.mjs` 与 `check-docs-all.mjs` 缩减为各约 30-40 行的声明式配置清单（声明门禁 ID、描述、执行目标、自愈配置与诊断建议），所有调度、限流、熔断与协议格式化细节彻底交由深模块接管。
- **假设坚持进程沙箱隔离作为核心边界**：
  单项规则保持完全自包含的 CLI 脚本形态，既支持聚合调度又保留独立的命令行逃生通道，杜绝全局状态污染、日志交织与单线程抢占超时失效问题。

## 二、 目标与非目标

### 1. 目标
- **抽象收敛门禁调度引擎深模块（GuardRunnerEngine）**：
  创建 `scripts/lib/guard-runner.mjs`，统一管辖运行时环境自适应（TSX/Node）、进程沙箱派发、受控并发池调度、超时熔断、孤儿进程级联清理、Agent Result Envelope 状态机聚合、Unix 沉默输出与自愈动作分发。
- **聚合入口轻量化与声明式改造**：
  将 `scripts/check-contracts-all.mjs` 与 `scripts/docs/check-docs-all.mjs` 改造为纯元数据声明的极轻量入口，消除 400 余行重复底层胶水代码。
- **规范化自愈生命周期（First-Class Auto-Fix Lifecycle）**：
  在规则配置中将自愈定义提升为标准能力，支持 `--fix` 参数触发前置自动修复并无缝更新诊断信封的 `effect` 字段。
- **健全受控并发与信号容错机制**：
  内置轻量并发池限制与进程退出信号（`SIGINT`/`SIGTERM`）监听转发，确保异常退出时彻底回收所有子进程。

### 2. 非目标
- 不变更现存各项门禁规则本身的扫描范围、判定算法与基线快照。
- 不影响各单项检查脚本（如 `node scripts/scan-phantom-deps.mjs`）在命令行直接独立运行的逃生通道。

### 2. 受控沙箱调度器设计（Sandboxed Process Pool）

1. **强物理隔离边界（Process-level Sandboxing）**：
   - 保持被调度脚本的自包含 CLI 特性，所有检查均通过隔离的 Node/TSX 子进程执行；
   - 彻底规避全局变量污染、`process.exit()` 意外猝死、单进程事件循环中的日志流混杂与动态 import 单例缓存问题。
2. **受控并发池（Concurrency Limiter）**：
   - 引擎内置轻量任务队列，控制最大同时存活子进程数不超过 `concurrency` 配置；
   - 避免无限制并发派生导致的瞬间系统高负载与 I/O 争抢。
3. **抢占式超时熔断与进程回收（Preemptive Watchdog & Signal Forwarding）**：
   - 子进程关联定时器熔断，超时立即发送强制终止信号；
   - 主调度器监听 `SIGINT` 与 `SIGTERM`，在用户按下 `Ctrl+C` 时统一级联杀死所有存活子进程，避免孤儿进程悬挂。

### 3. 一流自愈生命周期（First-Class Auto-Fix Lifecycle）

当 CLI 携带 `--fix` 参数运行时，调度引擎自动执行标准自愈周期：
1. **前置扫描**：识别声明了 `fix` 属性的门禁项；
2. **串行/有序修复**：依次调用各修复命令，收集修复流输出；
3. **复核验证**：修复完成后自动执行正常校验流程，确认修复结果；
4. **信封跟踪**：将修复状态与日志完整记录在 Result Envelope 的 `effect` 节点中（`type: 'updated' | 'none'`）。

### 4. 诊断信封协议与结果汇总状态机

- 严格依循 `Agent Result Envelope` 协议：
  - `status: 'success'`：全部门禁校验通过且退出码为 0；
  - `status: 'partial_success'`：部分门禁失败但处于可降级范围；
  - `status: 'error'`：存在阻塞性门禁失败或调度执行异常。
- 遵循 **Unix 沉默原则**：
  - 默认校验通过时仅输出单行静默确认（如 `✓ contracts check passed`）；
  - 校验失败时打破沉默，结构化格式化失败项、诊断行号及对应建议自愈指令（`suggested_actions`）。
