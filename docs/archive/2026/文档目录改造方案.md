## 一、背景与现状

`docs/` 现有 **31 个被 git 跟踪的文件**（本方案未跟踪，算上即 32 个物理文件），混合了三种生命周期完全不同的文档，全部平铺在根目录：

| 类别 | 文件数 | 例子 | 生命周期 |
| --- | --- | --- | --- |
| 规范 / 操作手册 | 8 | COMMIT_CONVENTION、COMPONENT_GUIDE、CVA、RELEASE | 常青，持续维护 |
| 方案计划 | 12（含 4 个旧版待归档） | ARCHITECTURE_OPTIMIZATION_PLAN×3、AUXILIARY_PACKAGES_IMPROVEMENT_PLAN×2、REGISTRY_ARTIFACTS_PUBLISH_TIME_PLAN | 提出 → 落地 → 过期 |
| 审计 / 扫描报告 | 9 | TECH_DEBT_REPORT、ui-bug-scan-*×2、perf-audit、hoist-* | 时间点快照，持续累积 |

另有 2 个纯扫描输出 txt（`audit/` 下）与 3 个历史产物子目录（`audit/`、`review/`、`superpowers/`）。

**现有问题**：

1. **三类文档平铺混杂**：根目录 17 个文件，「现在的架构方向」「发布怎么操作」「历史审计」互相穿插，检索成本高。
2. **方案状态不显式**：只有少数文档自标「已完成/已定稿」，多数要通读才知道进度；已完成的旧方案（ARCHITECTURE_OPTIMIZATION_PLAN V1/V2、AUXILIARY_PACKAGES_IMPROVEMENT_PLAN V1）与现行方案并列，`_V1/_V2/_V3` 后缀无法直接回答「谁当前有效」。
3. **报告无限累积无归档机制**：ui-bug-scan / root-scan 按日期命名，每次扫描新增一个，将来必然失控。
4. **命名不统一**：`*_PLAN` / `*-design` / `方案` / `计划` 混用，文件名大量英文大写（ARCHITECTURE_OPTIMIZATION_PLAN_V3、ui-bug-scan-2026-07-18…），视觉负担重；[README-en.md](../../README-en.md) 实为根 README 的英文版，有意放置于 docs/（引用 `[中文](../../../README.md)` 与 `apps/docs/public/favicon.svg` 均仅根目录成立）。
5. **链接不可移植**：9 个文件存在 `file:///e:/project/...` 绝对路径共 **214 处**（root-scan、ui-bug-scan、auxiliary-packages-scan、ARCHITECTURE_OPTIMIZATION_PLAN、INFRASTRUCTURE_CLOSURE_PLAN）。**来源**：这些均为历史 AI/工具生成的审计产物，生成时即以 `file:///` 形式嵌入仓库路径（Windows/IDE 环境复制或生成链接的默认形态），非手工约定。绝对路径不因文件移动失效，但换机器即死链，且违反可移植约定。
6. **外部硬编码引用**：`AGENTS.md` 有 **7 行**直接引用 `docs/` 路径需同步（L31、L112-117，迁移后加 `guides/` 前缀）；L20、L103 为目录结构描述，新结构下语义不变，不须改。
7. **无索引**：docs/ 没有索引文档，新文档落位无约定可循。
8. **README-en.md 现状含 2 处死链**：L10 `[中文](../../../README.md)`、L223 `[MIT License](../../../LICENSE)` 因文档身处 docs/ 而相对链接失效（分别解析到不存在的 `docs/README.md`、`docs/LICENSE`）。保留原位即必须修复。

> 已确认 **docs/ 不是 VitePress 文档源**（站点在 `apps/docs/`），整理不破坏文档站；所有文件均在 git 跟踪中，可 `git mv` 保留历史。

## 二、目标

1. **分类清晰**：三类生命周期分层，任何文档「一眼知其位」。
2. **状态显式**：方案文档统一 frontmatter 标注生命周期状态，旧版方案入归档区，现行方案一眼可辨。
3. **链接可迁移**：全部链接相对化、脚本化修复与验证，改造后 0 死链、**0 处 `file:///` 绝对链接**。
4. **规范固化**：命名 / frontmatter / 落位 / 归档规则写进索引与 AGENTS.md，防止三个月后回潮。
5. **充分可扩展**：骨架固定、类内自由生长，为未来文档量增长、站点化、索引自动化预留接口（见 §6）。

## 四、方案文档规范（含 frontmatter）

所有 **plans/ 与 archive/** 下的方案文档统一文档头，位于标题下、正文前：

```markdown
> 方案类型：重构 / 流程改造 / 功能设计 / 优化 …
> 状态：**draft** | active | done | archived
> 日期：YYYY-MM-DD
> 关联文档：[xxx](../guides/xxx.md)、[yyy](../reports/yyy.md)   ← 可选
> 修订记录：YYYY-MM-DD 本次改动摘要            ← 有修改才写
```

**状态机**（这是可扩展性的核心接口）：

```text
draft ──评审通过──▶ active ──落地完成──▶ done ──作者决定归档──▶ archived
                    │                        │
                    └──被新版本取代───────────┘   （如 V3 落地后 V1/V2 → archived）
```

- 状态含义：
  - `draft`：未定稿，正在评审
  - `active`：已定稿，正在实施，或实施完成且**仍是读者应遵从的权威指引**（读者照它干活）
  - `done`：已全部落地，保留在 plans/ 供追溯，**不再作为操作指引**，作者决定归档时机
  - `archived`：已被取代或完结归档，位于 `archive/YYYY/`，不再维护
  - **一句话判据**：读者还要照着做 = active；读完不用做 = done
- **同一主题只保留一份 active/done**：新版本接管后，旧版本立即移入 archive（不需要等新版本也落地）。plans/ 内同主题文件带 `-v{n}` 后缀区分世代，archive/ 内保留原名。

**命名规范**（约束未来新文档）：

- **方案 / 报告 / 归档文档一律用中文文件名**：`<中文主题>方案.md` / `<中文主题>报告.md`；方案类型为**功能设计**时用 `<中文主题>设计.md`（如 `changelog自动化设计.md`）。英文专有名词保留原文（如 `composables状态只读化方案.md`、`registry产物发布时构建方案.md`）。多世代方案带 **`-v{n}`**：当前版在 `plans/`，旧版移入 `archive/` 时文件名保留版本号（如 `架构优化方案-v3.md` → 旧版 `架构优化方案-v1.md` / `-v2.md`）。
- **报告类分两种**：
  - **快照型**（周期性扫描 / 审计快照）：日期前置 `<YYYY-MM-DD>-<中文主题>报告.md`，目录内按日期自然排序，可滚动累积（如 `2026-07-11-ui界面bug扫描报告.md`）
  - **结论型**（一次性审计结论）：不带日期 `<中文主题>报告.md`（如 `技术债审查报告.md`、`性能审计报告.md`）
- **guides/ 例外**：规范与操作手册保持英文 kebab-case 命名**与英文标题**，不改名、不要求中文标题（「标题一律中文」的约束对 guides/ 豁免）。
- **约定名**：目录索引固定 `index.md`；`README-en.md` 为项目英文简介（保留原位），两者定位不同。
- **标题一律中文**（guides/ 除外）。
- **链接一律相对路径**，禁止 `file:///` 绝对链接（历史遗留由本次迁移清零，后续新文档禁止再引入）。

## 五、链接修复策略（脚本化）

迁移必然破坏文档间相对链接，且需清除 `file:///` 绝对链接。**实测**（`docs/` + AGENTS.md）涉及链接分三类：

| 链接类型 | 数量（实测） | 是否因移动失效 |
| --- | --- | --- |
| docs 间 `.md` 相对互链 | 74 处 / 18 文件 | 是 |
| 指向 `packages/`、`apps/` 的相对源码链接 | 约 403 处 / 17 文件（含 `file:///` 折算相对后并入此类） | 是（`../` 深度变化） |
| `file:///` 绝对链接 | 214 处 / 9 文件 | 否（绝对路径不因移动失效），但为可移植性必须转相对 |
| `https://` 外链 | 若干 | 否，不动 |

> 说明：真正因移动**失效**的是「相对链接」；`file:///` 只是**不可移植**，转相对是额外要求。两者都需脚本处理，但成因不同。

**新增 `scripts/docs/check-doc-links.mjs`**（可复用工具，非一次性脚本；`scripts/docs/` 目前不存在，纯新增），三种模式：

```bash
node scripts/docs/check-doc-links.mjs check     # 遍历全仓库 md 链接，报告死链 + file:/// 残留（CI 可用）
node scripts/docs/check-doc-links.mjs fix --dry # 按迁移映射表预览改写（不落盘）
node scripts/docs/check-doc-links.mjs fix       # 执行改写
```

**处理规则**：

| 链接类型 | 处理 |
| --- | --- |
| `](相对路径.md)` 含 `#锚点` | 按「旧路径 → 新路径」映射表重写，保留锚点 |
| `](file:///...绝对路径)` | 转为相对路径（含其 `#锚点`），**并按新文档位置重算 `../` 深度** |
| `](../../packages/...源码路径)` | 重算相对深度（`../` 层级随文档新位置变化） |
| `https://` 外链 | 不动 |

- **映射表内置于脚本**（31 条：29 迁移 + 2 删除 + README-en 特殊处理），作为 `fix` 与 `check` 的共同数据源，避免执行时手写遗漏。
- **README-en.md 的 2 处死链**（`README.md`、`LICENSE`）一并修复为 `../` 前缀，纳入映射表。
- `check` 模式同时校验 **0 处 `file:///` 残留**。

**验证标准**：`check` 模式对 `docs/` + `AGENTS.md` 输出 **0 死链、0 处 `file:///`**。迁移前先跑一次基线——注意 **README-en.md 现有 2 处死链，基线并非 0**；迁移修复后为零即成功。

> 口径说明（执行实测后补充）：「0 死链」指**文档间 `.md` 互链**与已删文件引用；指向 `packages/`、`apps/` 源码的相对链接若目标已随重构删除（历史快照引用了当时存在的文件），`check` 降级为「源码引用失效」**告警**，不计入失败——历史快照的时效性属性，非缺陷，不修（修复即破坏快照内容）。

**同步更新** `AGENTS.md` 的 7 行 `docs/` 引用（L31、L112-117）加 `guides/` 前缀，并将 §4 的命名/状态约定写入 AGENTS.md 或 docs/index.md。

## 六、可扩展性设计

结构设计为「**固定骨架 + 自由生长**」，为以下演进预留接口：

1. **骨架四类固定，类内子目录按需新增**：`plans/` 可再分 `plans/components/`、`plans/infra/`；`reports/` 可再分 `reports/scan/`、`reports/perf/`。新增主题目录不改变骨架，也不影响索引结构。
2. **归档按年分区**：`archive/YYYY/` 每年一个目录，归档永不拥挤，且能一眼看出历史时间线。
3. **报告无限累积不失控**：快照型报告按 `YYYY-MM-DD-<中文主题>报告.md` 命名自动落位 `reports/`，结论型报告不带日期；索引只列**最新一份** + 历史列表（一行一条），旧报告永不删除、永不进入 plans/。
4. **状态机可扩展**：如需可增 `paused`、`deprecated` 等状态，frontmatter 是机器可读 YAML 行，无解析成本。
5. **索引自动化接口**：当前 30 篇以内手工维护 `docs/index.md`；frontmatter 已机器可读，未来可写脚本从 `type/status/date` 自动生成状态表——手工版与脚本版共用同一数据源，迁移平滑。
6. **站点化兼容**：全部链接使用相对路径 + `.md` 扩展名，与 VitePress 路由约定一致；若未来要把方案文档并入 `apps/docs/` 文档站，plans/reports 结构可直接映射为路由，无需改链接语法（中文文件名在站点化时需处理 URL 编码，届时一并评估）。
7. **工具沉淀**：`check-doc-links.mjs` 可进入 CI 或 husky 钩子，从工具层面防死链与 `file:///` 回潮（本期不做，接口已留）。
