# 工作流门禁冗余与性能审计报告

审计日期：2026-10-10。范围覆盖 CI、Bench、文档部署、发布工作流，以及生成、样式、文档、测试和消费者门禁。

主要耗时来自宽泛的构建任务图、重复测试和缓存配置失效。旧逻辑防回潮检查中确有可以退役的迁移等价测试、重复投影校验和实现形态断言，但它们对 CI 墙钟的影响小于构建和 coverage。优化顺序应是修正缓存边界、收窄任务图、合并重复测试，再清理历史门禁。

本报告记录审计结论和实施建议；工作流及门禁实现尚未调整。

### Turbo 本地缓存没有保存

[CI 配置](../../../.github/workflows/ci.yml)缓存 `node_modules/.cache/turbo`，仓库没有自定义 `cacheDir`，Turbo 2.10.5 的默认目录是 `.turbo/cache`。最新 main 的所有执行 job 都出现路径不存在、无法保存缓存的警告。Quality 的缓存读取与收尾步骤合计占约 16 秒。[Turbo 2.10.5 缓存说明](https://github.com/vercel/turborepo/blob/v2.10.5/apps/docs/content/docs/crafting-your-repository/caching.mdx)

同次运行的 Turbo Remote Cache 已启用，但 Quality 主任务只命中 1/16，Registry validate 命中 0/3，Node 22 命中 2/12，Node 24 命中 0/12。pnpm 和 Playwright 缓存已命中。因此不能把问题归结为所有缓存都未开启。

建议先修正实际运行版本的缓存输入，再把本地缓存路径改为 `.turbo/cache`。比较修正后本地缓存恢复、保存成本与 Remote Cache 收益；若本地缓存没有净收益，移除该层 Actions cache。各 job 的 key 前缀目前互相隔离，单改路径不会让并行 job 在同次运行里即时共享缓存。

### 多个 job 构建了不消费的包

根 `pnpm build` 是无过滤的 `build:artifact`，覆盖 UI、CLI、Registry 和 docs。Quality、两种 Node 测试、Browser、Integration、Consumers 共六个执行 job 带入构建图。Quality 后续运行 Registry validate 时，还因其依赖的 Registry builder 关闭缓存而再次调用构建入口。[根命令](../../../package.json)、[Turbo 任务图](../../../turbo.json)、[Registry 包命令](../../../packages/registry/package.json)

这既增加计算量，也让当前关键路径中的 Quality 承担较大的构建成本。优先收窄各 job 的实际产物需求，比删除耗时很小的类名断言更有效。

## 任务图与缓存优化策略

### 给每个任务明确产物需求

| 任务 | 必要输入或产物 | 收窄方向 |
| --- | --- | --- |
| UI 普通单测与 coverage | UI、shared 源码，必要生成文件 | 源码测试依赖生成；去除 UI `build:artifact` 前置要求 |
| UI SSR | UI、shared 源码，Node 环境与 SSR 配置 | 独立源码测试任务，保留请求间隔离和浏览器资源抑制测试 |
| Browser | UI 及其样式、浏览器测试输入 | 当前若保留构建，限定 UI；去除 CLI、Registry 和 docs 构建 |
| CLI integration | CLI dist 与本地 Registry 数据 | 限定 CLI、Registry，保留 UI 生成器作为 Registry 的必要前置 |
| U1、C1、C3 消费者 | UI、CLI tarball 与 consumer fixture | 构建和打包 UI、CLI；移除 docs 与无关 Registry 构建 |
| 文档构建与类型检查 | 文档、API manifest、UI dist 类型与运行产物 | 独立领域任务；保持真实 UI 类型产物依赖 |
| Registry validate | 本次已生成的 Registry 数据、元数据与源码 | 合并构建及校验的调度，避免第二次调用关闭缓存的 builder |

UI [Vitest alias](../../../packages/ui/vitest.config.ts)指向源码，SSR 也直接导入源码；coverage 目前只生成后测试、未先构建，证明源码测试与产物构建可以分工。CLI integration 则通过 [测试 helpers](../../../packages/cli/tests/integration/helpers.ts)读取 CLI dist 与 Registry，不能照搬 UI 的依赖调整。文档类型入口读取 UI 的 `dist/index.d.ts`，其 UI 构建依赖有实际依据。[UI 包导出](../../../packages/ui/package.json)

UI 默认入口还包含 10 个脚本测试文件；coverage 报告范围不包含 scripts。可将这些测试交给独立 tooling 任务，coverage 专注运行时源码。拆分时先保留 coverage 对当前全部 UI 测试的执行，再迁移脚本测试所有者并核对 ID，避免同时“去重”和“排除”造成遗漏。[UI Vitest 配置](../../../packages/ui/vitest.config.ts)

### 缓存输入必须包含真实运行时

Node 22/24 的 Actions cache key 不等于 Turbo Remote Cache 的任务 key。当前根 `engines` 只声明最低版本，矩阵没有将实际 Node 版本加入 Turbo 环境输入。Turbo 2.10.5 的全局哈希实现读取 `engines` 元数据，因此存在两种实际运行时复用测试结果的风险；最新 main 的 Node 24 没有命中缓存，本次没有观察到错误复用。[Turbo 全局哈希源码](https://github.com/vercel/turborepo/blob/v2.10.5/crates/turborepo-task-hash/src/global_hash.rs)

将实际 `node --version` 注入任务环境并声明为相关测试、构建的缓存输入，或者让运行时兼容性测试实际执行而不读取成功结果缓存。随后再扩大缓存复用。保持 `VERCEL` 等确实影响构建配置的环境输入。[Turbo 环境输入说明](https://github.com/vercel/turborepo/blob/v2.10.5/apps/docs/content/docs/crafting-your-repository/using-environment-variables.mdx)

UI、CLI generate、docs manifest 和 Registry builder 当前关闭缓存且没有 Turbo 文件输出声明。父级构建仍可缓存 dist，但这些生成副作用不会从缓存恢复。要缓存生成结果，先明确所有输出所有者及其输入；不应只把 `cache: false` 改成开启缓存。[任务配置](../../../turbo.json)、[Turbo 输出恢复规则](https://github.com/vercel/turborepo/blob/v2.10.5/apps/docs/content/docs/crafting-your-repository/caching.mdx)

### 并行任务与共享产物

继续让互相独立的检查并行。将所有 job 改成等待一个共享构建 job，虽然减少构建次数，却可能把原来并行的等待变成串行。优先使用正确的构建范围和可复用缓存；当需要保证各消费者验证同一候选 tarball 时，再评估共享打包任务及上传、下载的总成本。[GitHub job 依赖](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-jobs)

[消费者入口](../../../packages/cli/scripts/test-consumers.mjs)已支持共享 `--artifacts`，CI 的 U1、C1、C3 是打包一次后顺序执行，不存在每个矩阵重新打包的问题。各 fixture 独立冻结安装是不同消费环境的验证。可以按 U1 与 CLI 消费者的真实职责选择运行范围，保留完整发布候选验收。

## 按变更领域调度门禁

保留 required CI workflow 每次触发，并由轻量变更分类决定具体 job 或步骤。GitHub 的工作流级 `paths` 跳过会让必需检查停在 Pending；job 条件跳过的语义不同。[GitHub 必需检查跳过规则](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks#handling-skipped-but-required-checks)

| 改动领域 | 对应检查 |
| --- | --- |
| 纯内部文档、指南 | docs、命令与链接检查；涉及发布规范时补相关发布测试 |
| 站点页面、主题、API 页面 | docs 检查、i18n、manifest、站点类型检查和构建；UI 类型依赖保留 |
| UI 源码、样式、API contract | UI 源码测试、coverage、SSR、相关 browser、生成与依赖契约、产物和类型消费者 |
| CLI 源码、模板 | CLI 单测与集成、相关 C1/C3、CLI 生成与包契约 |
| Registry 编译器、元数据 | 编译器测试、生成与 validate、CLI 集成及相关消费闭包 |
| shared 源码、令牌 | 沿 UI、CLI、Registry、docs 的实际依赖闭包触发 |
| 根依赖、锁文件、workspace、Turbo 配置 | 触发所影响的依赖安装、构建和测试领域；无法分解的全局输入覆盖全部领域 |
| 发布脚本、协调器、发布工作流 | release tests 与相应工具测试；正式发布保留受信构建边界 |
| 门禁脚本、测试配置、生成器 | 执行被修改门禁自身的行为测试及其消费者 |

变更分类本身只需确定领域和依赖关系，不引入旧逻辑黑名单或内容摘要。先按已证实的依赖保守设定，再用实际读取关系收窄。

当前 `CI Gate` 只拒绝 failure、cancelled，并将 skipped 视为可接受。新增条件调度时，分类输出与 Gate 应一起调整：被选中的检查必须成功，未被选中的领域允许跳过；不能让被选中却意外 skipped 的检查放行。[CI Gate](../../../.github/workflows/ci.yml)

主干规则集要求唯一状态 `CI Gate (all checks passed)`。Bench 的报告不是该必需状态。路径策略应维护这个稳定出口，而不是新增一组必需工作流名称。

## Bench 与资源成本门禁

[Bench](../../../.github/workflows/bench.yml)的 `vitest bench --reporter=json` 在 2026-10-09 的 main 运行中报错，生成的 `bench-main.json` 只有 289 字节。工作流允许该命令失败继续，[bench-diff](../../../scripts/bench-diff.mjs)又将解析错误作为成功结束，因而 workflow 成功不能表示取得有效基准。应修复机器可读结果出口，并让数据缺失在报告状态中明确可见。[Bench 运行](https://github.com/lidaixingchen/brutxui-vue3/actions/runs/37927167221)

Bench 当前比较的是 timing 报告，变化比例用于分类，并未阻塞合并。[源码基准](../../../packages/ui/perf/render.bench.ts)直接导入 DataTable、TreeView 源码，因此可删除 main、PR 和基线缓存回退分支中的 UI 产物构建。抽查的 main、PR 构建分别占 16 秒、28 秒；这是不同运行的观察值，不能相加承诺单次提速。实际 PR 已命中基线缓存并跳过 base 回退。

[Button 成本步骤](../../../.github/workflows/ci.yml)默认执行 [cost runner](../../../packages/ui/perf/cost-runner.ts)的 7 个构建场景；五个浏览器 profile 均测 Button。Input、DataTable、GlitchText 场景可以移出 Button 专项，将构建场景缩为 empty 和三个 Button 场景，构建次数从 7 次减到 4 次。少 43% 的场景数不等于少 43% 的总耗时；该步骤墙钟收益尚未测量。[成本 profile](../../../packages/ui/perf/cost-profile.ts)

cost runner 记录字节数据，却没有字节预算判定；实际门禁是样式及资源断言。字节预算由 [size-limit 配置](../../../packages/ui/package.json)执行。因此工作流名称应准确表达“资源门禁与字节报告”。保持 size、资源、类型、打包消费者各自有效的契约，专项成本只在 Button、动效依赖、样式令牌、导出和成本配置等输入发生变化时运行。

Playwright 缓存只有浏览器二进制，Linux 系统依赖仍需安装。当前命中后执行 `install-deps` 有实际作用。官方也指出缓存恢复不一定比浏览器下载更快，应测量后决定是否保留缓存；不应单为减少步骤而删除系统依赖安装。[Playwright CI 缓存说明](https://playwright.dev/docs/ci#caching-browsers)

## 文档部署与发布

[Deploy Docs](../../../.github/workflows/deploy-docs.yml)只监听 main push 与手动运行，没有监听 CI、Bench 的 `workflow_run`，因此没有同 SHA 被这两个来源重复触发的问题。最新 main 的 CI、Bench、Deploy Docs 各有一个 push run，但它们各自安装并构建相关包。[文档部署运行](https://github.com/lidaixingchen/brutxui-vue3/actions/runs/37927167251)

文档部署再次执行 docs 检查，可在部署绑定同一 SHA 的 CI 成功结果和文档产物后合并；当前部署独立启动，不能直接删除它的独立检查。跨 run 复用产物需要使用明确的所属 run 与提交，保持 Pages 上传、部署的现有产物关系。

常规 PR 的 [test:release](../../../scripts/release/tests/run-release-tests.mjs)主要是 coordinator 回归与 pnpm tarball dry-run fixture。最新 main 仅耗时约 2 秒，可以按发布输入变化触发，但优先级较低。状态续跑与真实包、渠道检查仍保护有效发布行为，不属于旧命名回潮守卫。

[publish.yml](../../../.github/workflows/publish.yml)独立监听 tag，未将 tag SHA 绑定到 main 上已通过 CI Gate 的同一 SHA；main 规则集也不约束 tag。若希望复用 CI 结果以删减发布重复验证，先建立这一绑定。受信 Registry 签名构建与常规源码构建的权限、环境不同，维持独立边界。现有发布架构说明对全量门禁及原子分发的表述强于实际工作流，应随发布门禁调整对齐。[发布架构](../../guides/RELEASE_ARCHITECTURE.md)

## 分阶段实施与验收

| 批次 | 主要文件与职责 | 验收重点 |
| --- | --- | --- |
| 缓存与运行时 | ci.yml、turbo.json、构建任务契约测试 | 缓存路径实际存在并成功保存；Node 22/24 运行时维度进入任务输入，兼容性测试实际验证相应版本 |
| 构建与测试去重 | 各包命令、Turbo 源码测试任务、CI job 过滤 | dry-run 不再带入无关 docs/Registry；各真实产物消费者仍取得所需文件；覆盖测试 ID 的并集保持完整 |
| 生成与规则收敛 | contracts、生成器契约、equivalence、旧检查器、样式基线 | 原始提交漂移在生成写入前失败；正式检查覆盖登记与投影；移除历史对照与旧容忍额度；同步指南和命令 |
| 领域调度与报告 | CI Gate、docs/release/perf 输入分类、Bench 数据出口 | 代表性变更选择正确领域；选中检查失败或取消阻止放行；Bench 输出有效数据；正式发布保持提交与产物绑定 |

实现时按职责提交，逐一删除退役文件，并同步包命令、测试、指南与门禁登记。新增维护能力以当前输入、输出和行为为依据。

性能验收分别记录 workflow 总墙钟、排队、关键 job、主要步骤和全部 job 的累计用量。保持相同运行时与测试覆盖，区分冷缓存、热缓存及不同改动领域；用同条件重复样本评估收益。检查减少后的测试 ID 应等于原覆盖集合减去已确认退役的历史断言，再加新增正式契约测试；测试总数相近不能证明覆盖等价。

本轮已通过文档门禁基线：6 项检查、退出码 0。链接扫描报告的 78 条失效源码引用属于已有历史快照提示，不是死链错误。运行时实现没有修改，因此尚无优化后的 CI 时间；上述步骤和场景数量属于可验证的削减对象，提速幅度需要后续 CI 验收。
