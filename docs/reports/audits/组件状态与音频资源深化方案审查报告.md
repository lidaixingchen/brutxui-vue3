## 一、实施前需要补齐的契约

### 1. Kanban 权威数据回流时同步校正交互位置

**优先级：高；性质：方案契约缺口。** 对应方案第 77、81—85、104—106 行。

方案规定父级接受、拒绝或规范化更新后，工作快照回到外部输入，但只明确了实体删除时清理交互状态。当前 [useKanban](../../../packages/ui/src/composables/useKanban.ts) 第 202—228 行在键盘跨列移动后同步改写 `grabbedCard.columnId`；后续方向命令使用该列寻找卡片。

可触发场景：抓取 A 列卡片并移动到 B 列，父级拒绝此次更新。外部数据仍把卡片放在 A 列，而交互状态可能仍指向 B 列；卡片没有被删除，因此只做存在性清理不足以恢复下一次方向操作。父级把落点规范化到 C 列也有相同问题。

建议补充以下约定：

- 外部输入成为权威数据时，按卡片 ID 重新定位抓取状态；拖拽状态按当前有效列校正或取消。实体不存在时清理。
- `moved` 明确表示控制器计算出的移动结果。移动通知在请求发出时触发，父级是否采纳由回流数据体现；焦点与完成播报依据回流后的实际位置。
- 列出整体替换、响应式数组原地删除及重新挂载的支持范围。当前[看板文档](../../../apps/docs/components/kanban-board.md)第 86—92 行使用 `cards.push`，原地更新属于实际调用方式。
- 增加“拒绝后继续方向移动”和“规范化后继续方向移动”的组件测试，直接断言焦点、抓取态和下一次结果。

Vue 的单向数据流支持由父级持有数据并通过事件请求更新，但 Vue 批次结束本身不构成业务确认协议。[Vue Props](https://vuejs.org/guide/components/props.html#one-way-data-flow)

本轮建议采用方案已有的“外部输入到达即成为权威数据”策略，异步请求排序由父级负责。只有业务明确要求看板识别过期确认时，才需要增加版本号或确认协议。

### 2. 动态音效开关需要贯通门面与组件调用方

**优先级：高；性质：现有接线与目标契约不匹配。** 对应方案第 162、184、186 行。

[useBrutalHaptics](../../../packages/ui/src/composables/useBrutalHaptics.ts) 第 4—6 行声明 `sound?: boolean`，第 24 行通过 `computed(() => options.sound === true)` 读取。实际调用方 [NumberInput](../../../packages/ui/src/components/number-input/NumberInput.vue) 第 45 行和 [Switch](../../../packages/ui/src/components/switch/Switch.vue) 第 58 行均传入 `{ sound: props.sound }`。该对象保存的是初始化时的布尔值，内部 computed 无法跟踪后续 prop 变化。

因此，父级从开启切换为关闭后，门面继续允许播放，共享运行时也收不到关闭信号；从关闭切换为开启后则继续静音。仅改造 `useAudioEngine` 无法实现方案承诺的释放行为。

建议将门面的输入改为 `MaybeRefOrGetter<boolean | undefined>`，内部用 `toValue` 求值，两个组件传 getter 或 prop ref，并把这两个组件及对应测试显式加入 A 工作包。Vue 官方同样建议向 composable 传入 getter 以保留响应式依赖。[Vue 响应式参数传递](https://vuejs.org/guide/components/props.html#passing-destructured-props-into-functions)

验收应覆盖初始静音、动态启用、resume 等待中关闭、播放中关闭、重新启用，并验证其他实例继续工作。

### 3. 音频等待请求需要时效与容量策略

**优先级：中；性质：由既有实现延续到共享运行时的设计风险。** 对应方案第 160、163、177—178 行。

方案合并 resume 操作后逐一调度有效请求，当前 [useAudioEngine](../../../packages/ui/src/composables/useAudioEngine.ts) 第 156—184 行也为各次播放请求安排恢复后的调度。lease 存活、开关开启和上下文代次一致，仅能说明请求仍有所有者，不能说明声音仍符合当前交互。

Web Audio 规范允许恢复请求因尚未获准启动而保持 pending。[Web Audio resume](https://webaudio.github.io/web-audio-api/#dom-audiocontext-resume) 据此可推导：在长时间等待期间连续点击或输入，恢复后可能集中播放历史反馈；共享一次 resume 并不会自动合并这些声音请求。

建议对短促交互声音保留有限的最新请求，并在实际调度前检查时效；成功与失败反馈按实例保留最新语义状态。具体时效值应集中定义并由交互体验验证。等待 close 的播放请求应用相同策略。该策略是本项目的交互设计建议，规范只证明等待可能发生。

增加可控长时间 pending、连续请求、恢复后播放数量和关闭后请求清理测试，避免测试只覆盖立即 resolve/reject。

### 4. 音频 adapter 应明确播放所有权及设备状态转换

**优先级：中；性质：内部 interface 与验收细化项。** 对应方案第 151、160—165、174、186 行。

单个 lease 释放时要停止自己的声音，adapter 就需要提供可执行的归属关系，例如每次调度返回幂等取消句柄，或由 adapter 按 lease 持有节点。当前 [useAudioEngine](../../../packages/ui/src/composables/useAudioEngine.ts) 第 77—107 行主要依赖声源局部引用和 `onended` 清理；共享设备后，应显式验证 A 的节点释放与 B 的播放相互独立。

状态处理还应包括 `interrupted`。MDN 描述了电话或会议设备独占、合盖以及 iOS Safari 页面切换引发中断的情况；恢复策略需按目标浏览器验证。[MDN BaseAudioContext.state](https://developer.mozilla.org/en-US/docs/Web/API/BaseAudioContext/state) Chromium 实测是合理的首批门槛，跨浏览器恢复结论需要对应环境的证据。

`close()` 的失败处理应以设备实际状态为依据。规范规定，关闭进入控制流程后上下文不能继续恢复；文档未 fully active 时也可能在关闭前拒绝调用。方案已经要求检查设备是否仍存活，这一条件应保留并细化为可观察状态，测试替身应覆盖真实状态转换。[Web Audio close](https://webaudio.github.io/web-audio-api/#dom-audiocontext-close)

### 5. DataTable 需要明确行身份与开关行为的支持范围

**优先级：中；性质：既有行为与方案契约待明确。** 对应方案第 116、124、127、137 行。

[DataTable](../../../packages/ui/src/components/data-table/DataTable.vue) 第 306—319 行只监听 `data` 引用并比较 key 集合；[useDataTableSelection](../../../packages/ui/src/composables/useDataTableSelection.ts) 第 32—49、95—97 行使用当前 `rowKey` 解释已有选择集。若 `rowKey` 从 `id` 改为 `uuid`，旧选择标识可能仍被计入选中数量，却无法对应实际行。展开状态由组件持有，也需要遵循同一行身份约定。

建议在实施前选择明确规则：本轮以唯一、稳定的 rowKey 为前提，身份规则变化通过重新挂载重置；或者正式支持动态 rowKey，并同步重置选择及组件展开状态。函数形式的 rowKey 可能使用外部响应式依赖，因此动态支持不能只比较函数引用。[表格使用文档](../../../apps/docs/components/data-table.md)第 501、575 行已经要求唯一 key，可直接沿用这一前提。

另外，当前功能开关行为并不完全相同：排序关闭后已有排序状态仍参与处理；过滤关闭时暂时绕过过滤；选择和页码保留各自状态。流水线提取前应形成“关闭、重启、外部 pageSize 更新、用户命令、内部同步”的行为矩阵，保留或调整均有明确断言。证据见 [排序](../../../packages/ui/src/composables/useDataTableSort.ts)、[过滤](../../../packages/ui/src/composables/useDataTableFilter.ts)、[分页](../../../packages/ui/src/composables/useDataTablePagination.ts)和[选择](../../../packages/ui/src/composables/useDataTableSelection.ts)。

“key 集合变化就清空所有选择并回到第一页”是当前产品策略。它适合整批换数据的表格；持续追加数据的场景可能更适合保留仍存在的选择。此次内部编排可沿用当前策略，若要改变体验，应明确列为行为变更。

## 二、各工作包的实践判断

| 工作包 | 判断 | 价值与建议 |
| --- | --- | --- |
| K：移动控制器 | 建议优先推进，先补齐回流契约 | Board 与 headless 确实有两套移动与交互实现。统一移除后的插入索引、结果和互斥状态能集中维护规则；DOM 几何与焦点留在组件中合理。 |
| T：数据编排 | 建议采用内部 composable | 过滤、排序、分页、选择的组合具有真实协作规则。将 computed 链、过滤 patch 和跨状态 watcher 一起迁入才能形成实质收益；组件继续处理展开和虚拟测量。 |
| A：共享音频 | 共享与缓存合理，资源退出策略需测量 | 同一模块实例共享设备、SSR 懒创建、真实与测试 adapter 分层均有明确用途。lease 用来表达节点和待播放请求所有权，具有实际价值。 |
| P：选择值判定 | 可作为小型独立整理 | 当前两个 composable 对基础值的结果一致。提取纯函数能保证后续语义一致；收益主要是维护集中，改动规模应保持小。 |

Web Audio 规范描述大多数使用场景每个 document 使用一个 AudioContext，因此共享上下文有一手依据；规范并未要求所有 UI 库必须使用完全相同的租约实现。[AudioContext](https://webaudio.github.io/web-audio-api/#AudioContext)

复用 AudioBuffer、每次创建 AudioBufferSourceNode 符合设备模型：声源只能启动一次，缓冲可供多次播放使用。[MDN AudioBufferSourceNode](https://developer.mozilla.org/en-US/docs/Web/API/AudioBufferSourceNode)

最后一个 lease 释放后立即 close 可以尽快释放设备，也是可接受的默认策略；频繁路由切换或短暂卸载时会重复创建上下文及缓冲。建议资源基线同时记录多实例并存与连续挂载卸载的构造次数、首声恢复表现和空闲占用，再决定是否需要延迟回收。当前方案可以先采用立即关闭，无需提前增加空闲定时器或全局应用管理器。

P 的语义已核对 [useClearable](../../../packages/ui/src/composables/useClearable.ts) 第 29—35 行与 [useSelectableTrigger](../../../packages/ui/src/composables/useSelectableTrigger.ts) 第 47—58 行。`0`、`false`、对象、空白字符串都是有效值，显式 `false` 和自定义判断的优先级应保持；无需新增公共配置层。
