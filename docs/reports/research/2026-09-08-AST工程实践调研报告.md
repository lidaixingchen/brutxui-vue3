# AST 工程实践调研报告

> 调研日期：2026-09-08。依据当前仓库源码与官方文档；本次为架构调研，未修改业务代码，未执行性能基准或全面缺陷验证。

## 结论

对于 BrutxUI 的依赖提取、模块路径重写和源码 API 提取，使用成熟解析器生成 AST 是合适的工程实践。项目已经采用此路线，当前优先事项是统一解析契约并补齐边界处理。

为整个仓库额外自研一套常驻、持久化的完整 AST 系统，暂时缺少收益证据。建议按文件按需解析；确有跨文件语义需求时使用 TypeScript Program / TypeChecker；代码导航与影响分析继续使用现有 CodeGraph。以上为结合项目现状的工程判断，不是官方对所有项目的统一要求。

## AST 能解决什么

AST 表达源码的语法结构。例如导入语句、类型声明和调用表达式可以按节点类别区分，避免把注释或普通字符串当成代码。TypeScript 官方提供 SourceFile、遍历节点以及生成代码的 Compiler API，无需自行实现 TypeScript 语法解析器。[来源：TypeScript Compiler API](https://github.com/microsoft/TypeScript/wiki/Using-the-Compiler-API)

单文件 AST 并不自动包含跨文件符号解析与完整类型信息。需要判断某个标识符实际绑定哪个声明、查询推导类型时，应使用 Program / TypeChecker。Vue 也明确说明，基于 AST 的 props 类型转换对需要真正类型分析的复杂类型存在限制。[来源：TypeScript Compiler API](https://github.com/microsoft/TypeScript/wiki/Using-the-Compiler-API)、[Vue 类型声明限制](https://vuejs.org/api/sfc-script-setup#type-only-props-emit-declarations)

Vue SFC 包含脚本、模板和样式等不同块，官方 compiler-sfc 提供 descriptor 解析以及脚本、模板、样式处理能力。项目应复用这些入口，按任务处理对应语言，而不是用一种脚本解析模式理解整个文件。[来源：Vue compiler-sfc](https://github.com/vuejs/core/blob/main/packages/compiler-sfc/README.md)、[SFC 语法规范](https://vuejs.org/api/sfc-spec.html)

## 值得优先验证的边界

以下是静态阅读发现的检查点，尚未运行针对性复现，不等同于全面审计结论。

1. **解析诊断传递。** SfcAstEngine.parse 获取 errors 后没有返回诊断或中止。建议区分只读扫描与源码写入：扫描可返回部分结果和诊断；写入应在无法可靠解析时中止，避免将不完整结果当作成功。
2. **语言模式选择。** 脚本解析固定使用 ScriptKind.TSX，虽然 descriptor 已记录 lang。建议根据真实扩展名与块语言选择 JS、JSX、TS、TSX，并覆盖 TS 类型断言与 JSX 等有歧义语法。
3. **运行时导入分类。** 两处实现对默认导入和内联 type 绑定的条件不同。例如 `import Foo, { type Bar } from 'pkg'` 需要保留默认值绑定的语法事实，不能只看花括号中的元素。依赖分析还应说明采用保守源码依赖还是编译产物依赖口径。
4. **动态依赖的完整性。** 当前遍历提取字符串字面量及无插值模板字面量导入；`import(variable)` 无法由该逻辑确定路径。应将此类依赖标记为未解析，或明确支持边界，避免将结果宣传为完整运行时依赖图。
5. **文档提取的语义需求。** AST 可以改善嵌套结构、属性顺序和多行声明识别；导入类型、继承和复杂类型求值需要额外语义能力，不能承诺仅引入 parser 即得到完整 API 文档。

上述源码证据分别见[共享 AST 引擎](../../../../../packages/shared/src/ast/sfc-ast-engine.ts)、[共享模块提取器](../../../../../packages/shared/src/extract-module-specifiers.ts)与[API 文档生成器](../../../../../packages/ui/scripts/generate-api-docs.ts)。

## 按场景选择能力

| 需求 | 推荐方式 | 引入边界 |
| --- | --- | --- |
| 查字符串、注释、日志 | rg / 文本搜索 | 无需解析语法 |
| 目录扫描、JSON manifest、令牌数据生成 | 文件系统与结构化数据处理 | 无需为了统一而转成 AST |
| import/export 提取、路径重写 | 现有 SFC + TypeScript AST | 共用模块定位与分类规则 |
| Vue props、emits、slots 文档 | SFC/模板解析；按需增加类型语义能力 | 先确认支持的 API 语法范围 |
| 跨文件类型、符号绑定 | TypeScript Program / TypeChecker，结合 Vue 工具链 | 有真实类型查询需求再使用 |
| AI 代码检索、导航、改动影响分析 | 现有 CodeGraph | 图谱结论仍需编译器与测试验证 |
| 高频重复扫描 | 先复用单次任务解析结果，再基准评估缓存 | 无性能数据前不建设全仓常驻 AST |

此表为基于前述一手资料与项目证据的选型建议。AST 是语法表示，依赖图是模块关系，代码索引是检索设施，三者的职责应分别定义。

## 建议执行顺序与验收

首先为共享模块提取建立一致的测试契约，覆盖默认导入混合 type 绑定、双 script 块、TS/TSX、重导出、静态与动态导入、语法错误和源码偏移；然后将调用入口收敛到同一实现。源码重写还应验证未触及区域保持原样、重复执行保持幂等。

随后按实际使用情况迁移 API 文档与主入口导出检查中的结构性正则。保留适用于固定标记、文件名和普通文本的字符串处理。

最后测量真实项目的冷启动耗时、重复解析次数、峰值内存和增量变更耗时，再决定缓存。缓存若落地，应将内容、文件语言、解析选项及解析器版本纳入有效性判断，并明确容量与失效机制。

以上属于后续工作建议。本次没有重构实现，也没有证据宣称 AST 一定提升运行速度或完整 AST 持久化一定提升 AI 检索质量。
