# Node 22 统一后的 CI 优化机会

调研日期：2026-11-04。源码基线：`805efb71a9eb95aa2c3db061b81a7eae4ff3c702`。本报告记录下一批候选与测量依据；远端收益需要后续对照运行确认。

## 一、结论

下一批应优先优化 **UI 测试公共初始化、覆盖率汇总环境准备和 Browser 作业的缓存搬运**。前两项位于当前 Gate 的关键路径；Browser 是紧随其后的限制因素。共享 Chromium 进程和双语 API 原始提取也有明确的重复工作，但收益较小。

依据最新 [Node 22 成功运行](https://github.com/lidaixingchen/brutxui-vue3/actions/runs/41759015647)，CI 创建至 Gate 完成为 **150 秒**，累计作业时长 **683 秒**。相邻[成功基线](https://github.com/lidaixingchen/brutxui-vue3/actions/runs/41757499283)用于辨识持续开销与运行波动；两个样本不足以推断长期分位数或单项优化的因果收益。

| 优先级 | 候选 | 已确认的成本 | 收益与适用条件 |
| --- | --- | --- | --- |
| 第一批 | 将 `axe-core` 加载移到可访问性 helper | 186 个 UI 测试文件共用的 setup 静态导入；helper 当前仅供一个测试文件使用 | 降低重复初始化；实际节省需 Node 22 全量对照 |
| 第一批评估 | 精简覆盖率汇总环境 | 汇总作业 29 秒，实际 merge 约 3 秒，准备约 18 秒 | 本轮 Gate 可回收空间最多约 16 秒，必须计入新的准备或传输成本 |
| 第一批实验 | Browser 按缓存来源调整 Actions Turbo 缓存 | 恢复及保存共 16 秒，UI 构建步骤 4 秒 | 同仓库远端缓存有效时优先验证；冷缓存与外部分支单独验证 |
| 第二批 | 五个资源 profile 共用 Chromium 进程 | 资源步骤连续两轮为 33 / 34 秒，启动浏览器五次 | 保持上下文隔离；后四组全部处理约 9.7 秒，仅能作为宽松上限 |
| 第二批 | 双语 API 共用原始提取结果 | 209 个成员各提取两次 | 本机第二轮原始提取约 0.68 秒；属于小幅节省 |

上述收益不能相加为 Gate 收益。覆盖率汇总结束于 UTC 02:13:07，Browser 结束于 02:12:51，Gate 随后结束于 02:13:14；单独缩短汇总链路约 16 秒后，Browser 即成为限制因素。

## 二、UI 测试公共初始化

[`vitest.setup.ts`](../../../packages/ui/src/vitest.setup.ts) 顶层导入 `axe-core`，并提供异步 `axe()` helper。该 setup 由 [`vitest.config.ts`](../../../packages/ui/vitest.config.ts) 应用于每个测试文件；[`test-utils/a11y.ts`](../../../packages/ui/src/test-utils/a11y.ts) 的实际调用方当前为 Button 无障碍测试。

候选实现是将 `axe-core` 放到 helper 的首次调用路径加载，保留统一测试环境配置、可访问性规则、元素处理和清理语义。这样可以让其余测试文件不承担该依赖的初始化成本。

本机 Node `v24.20.0` 的临时对照使用 20 个最小测试文件、两个 worker，保留当前 setup 的其他逻辑。记录分阶段统计的四次对照按“按需加载、当前版本、当前版本、按需加载”运行，四次均为 20 个文件与 20 个测试通过：

| 设置 | setup 累计统计 | Vitest 墙钟 |
| --- | --- | --- |
| 当前静态导入，两次 | 1.21 / 1.18 秒 | 2.49 / 2.43 秒 |
| helper 按需导入，两次 | 0.744 / 0.739 秒 | 2.28 / 2.28 秒 |

包含 pnpm 启动的八次进程总耗时有明显波动：当前版本为 7.319 / 5.737 / 5.560 / 5.470 秒，按需加载为 5.348 / 8.680 / 5.351 / 5.325 秒。因此分阶段统计更适合定位 setup 成本。该实验确认重复加载有成本，但它使用 macOS、Node 24 和最小测试，不能按文件数量线性外推为 Linux、Node 22 的真实覆盖率收益。

当前两个 coverage shard 都包含 93 个文件。最新运行的 Vitest 累计统计如下；setup 等统计可能在 worker 间重叠，不能直接相加为墙钟时长：

| 项目 | 分片一 | 分片二 |
| --- | ---: | ---: |
| 实际测试步骤 | 44 秒 | 58 秒 |
| 测试用例数量 | 2,116 | 2,038 |
| tests 累计统计 | 18.83 秒 | 18.61 秒 |
| setup 累计统计 | 14.29 秒 | 21.93 秒 |
| environment 累计统计 | 16.02 秒 | 22.34 秒 |

相邻基线的两个测试步骤为 68 / 66 秒。两片 tests 统计相近，而 setup、import、environment 与 runner 准备明显波动；目前缺少调整分片内容或增加 worker 的稳定依据。

验收应保持 **186 个源测试文件、4,154 个测试、105 个 UI 脚本测试**及覆盖率阈值，并单独复测 Button 无障碍检测与定时器恢复路径。

## 三、覆盖率汇总环境

[`coverage` 作业](../../../.github/workflows/ci.yml)等待全部分片完成后，重新执行 checkout、pnpm / Node 初始化、安装与 UI 生成。最新作业 29 秒中，环境准备约 18 秒，下载两个分片约 0.6 秒，正式 `--merge-reports --coverage` 约 3 秒，上传约 2 秒。

优先评估合并专用配置与最小依赖安装，缩小该作业所需的配置加载和安装范围。若探索复用已准备的环境，必须同时测量环境传输或等待成本；当前每个分片都在隔离 runner，不能直接假定依赖可共享。

汇总仍需承担完整阈值与最终报告契约。分片配置关闭 reporter 和阈值，由汇总统一执行。约 2.23 MB 的分片与约 2.39 MB 的最终产物没有表现出明显传输瓶颈；HTML、JSON 等 reporter 全部包含在约 3 秒的 merge 命令中，调整它们的收益较低。

汇总日志中的 `Duration 99.19s` 为原始测试运行的汇总统计，不是 merge 本身耗时。依据步骤与日志时间戳，merge 实际约 3 秒。

## 四、缓存搬运

[`ci.yml`](../../../.github/workflows/ci.yml)为任务域分别保存 `.turbo/cache`。最新日志的成本如下，restore / save 按 Actions 步骤整秒计：

| 作业 | Turbo Actions 缓存体积 | restore / save | Turbo 命中数 |
| --- | ---: | ---: | --- |
| Browser | 11 MB | 8 / 8 秒 | 1 / 2 |
| CLI Integration | 1 MB | 6 / 5 秒 | 1 / 4 |
| Consumers | 15 MB | 4 / 4 秒 | 2 / 5 |
| Test Node 22 | 2 MB | 5 / 6 秒 | 包测试 4 / 6；SSR 1 / 2 |
| Quality | 11 MB | 4 / 4 秒 | 11 / 14 |
| Documentation site | 126 MB | 2 / 3 秒 | 3 / 5 |

这些作业均显示 `Remote caching enabled`，但同时恢复了本地缓存。`Cached` 计数无法区分命中来自本地还是远端。Browser 的 4 秒构建步骤也是缓存命中条件下的结果，不能据此认为冷构建同样只需 4 秒。

建议先在同仓库 main / PR 做对照：跳过 Actions 的本地 Turbo 恢复与保存，并以 `--cache=remote:rw` 明确限制缓存来源，记录命中数、构建时间、累计作业时长和结果。该参数由 [Turbo 官方 CLI 文档](https://turborepo.dev/docs/reference/run#--cache-options)定义。若远端命中成立，Browser 有回收最多约 16 秒搬运成本的窗口；远端获取本身仍有成本。

随后应覆盖远端凭证缺失、首次构建和依赖变化的场景。Dependabot / 外部分支的缓存条件与 main 不同。pnpm 缓存与 Playwright 浏览器缓存属于其他层；本轮未发现删除它们的依据。Browser 的 Playwright 缓存约 259 MB，恢复耗时 8 秒，当前命中时免去浏览器下载。

## 五、较小的重复工作

### 1. 资源检查共用 Chromium

[`cost-runner.ts`](../../../packages/ui/perf/cost-runner.ts)已经为五个资源 profile 共用一次静态 HTTP 服务，但 `measureBrowserProfile()` 每次启动、关闭 Chromium。可以在运行级复用浏览器，为每个 profile 创建独立上下文，保留冷页面、资源归属和生命周期隔离。

后四组 profile 的全部处理约 9.7 秒，包含启动、加载、测量和关闭，因此实际可节省时间会更少。五组 profile 的 effect、reduced-motion 与 KeepAlive 状态各有独立断言；现有稳定等待用于观察计时器和监听器生命周期。

资源检查消费生产 tarball，Vitest Browser 测试消费源码，分别覆盖不同边界。最新 Vitest Browser 为 37 个文件、156 个测试通过，执行步骤连续两轮约 17 秒。

### 2. 双语 API 原始提取

[`collectComponentApiOutputs()`](../../../packages/ui/scripts/generate-component-api.ts)在 locale 循环内调用 `extractGroup()`，后者对组内每个成员执行 `extractor.extract()`。83 个组件组的 209 个成员因此各提取两次，随后才通过 [`mergeApiContent()`](../../../packages/ui/scripts/api-docs/merge.ts)合并各语言语义。

本机 Node `v24.20.0` 的只读 profile 保持相同分组与调用顺序：第一轮 209 次提取约 3.74 秒，第二轮 209 次约 0.68 秒，组内两轮原始 JSON 完全一致。第二轮有组件 checker 的预热与内部复用，因此不能将总提取时间直接减半；本机数字也不能直接视为 Node 22 CI 收益。

可把原始组件提取移到 locale 循环之外，仅对语言语义合并分别执行。验收应逐文件比较全部 167 个生成输出，并保留源信息、重复成员、完整语义、非法内容和 dispose 诊断。

### 3. 消费者进一步计时

最新 Consumer 作业为 79 秒，矩阵 48 秒，其中 C1 为 46.33 秒；C1 的十次 CLI 添加覆盖约 29 秒。相邻运行的矩阵为 73 秒，差异同时受 runner、缓存与依赖准备影响，不能单独归因于已有并发实现。

[`test-consumers.mjs`](../../../packages/cli/scripts/test-consumers.mjs)已经共用候选包并以最多两个隔离子进程并发。下一步可分别计时 CLI 启动、Registry 读取与实际写入，识别可复用的准备。逐组件添加、已有依赖状态、更新保护、严格类型检查与生产构建均需保留。目前没有足够证据把十次入口合并为批处理作为第一批改动。

## 六、验证顺序

1. 先验证公共 setup 的按需加载；记录各片 setup、import、environment、测试步骤墙钟与 Gate。
2. 单独验证 Browser 的缓存来源，覆盖有远端凭证与冷路径，避免与其他改动混合归因。
3. 对覆盖率汇总作业建立最小依赖方案，确认全量阈值、报告内容和生成输入，再比较净收益。
4. 对 Chromium 复用与双语 API 提取分别做前后对照，比较生产产物资源断言和生成文件。

每项按相同 SHA、Node 版本、runner 与缓存条件重复采样，分别报告 Gate 等待时间和累计作业时长。本报告保留上述基线的取证与候选排序，现行实现见[生成与构建机制](../../architecture/生成与构建机制.md)。
