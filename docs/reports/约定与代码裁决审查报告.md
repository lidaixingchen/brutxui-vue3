**一句话结论：约定的方向正确（令牌化、单一事实源、显式完整声明），代码是主要修复对象；但约定体系在机制表述精确性、例外条款、与共享变体/状态模型的交互三处确有真实缺口，且 CVA.md 作为权威蓝图已过期失配。没有一条指控是"纯约定错而代码对"。**

8 条指控判定分布：

| 判定 | 指控 | 谁对 |
| --- | --- | --- |
| **代码违反好约定**（约定对） | C2 手抄 shadow / C3 硬编码色 / C4 border-2 / C6 separator 类名插值 | 约定占优（C2/C3/C6 三维全胜；C4 因 Transfer 例外记为 mixed） |

## 一、八条指控裁决明细

### C1 焦点体系残留 11 处 outline-none —— 裁决：**both_flawed**（mixed）

**代码确有真缺陷：**
- 3 处真实 a11y 缺口：CommandInput 输入容器无 focus-within 指示（键盘焦点不可见）；cascader trigger 用 shadow+位移做焦点指示（库内方案文档已判属 a11y 缺口）；MenuItem/SubMenu 聚焦非选中项无可见指示。
- 同族漂移：select trigger 已迁 FOCUS_OUTLINE_CLASSES，cascader trigger 未迁；dropdown-menu item 合规而 select/command/cascader item 不遵。
- 死遗物：input-variants.ts:36 的 `focus:ring-0`（ring 系死重置）。

**代码合理、应豁免的偏离：**
- 内层 input 保留 outline-none（input/number-input/TagsInput 容器已有 focus-within 指示，内层抑制 UA 环避免双圈）——合法，且约定原文已限定「同一元素」，本不适用于此。

**约定的问题：**
- 「禁止任何 outline-none」绝对化，未为「容器 focus-within + 内层抑制 UA 环」与「不可聚焦元素（listbox 选项、浮层面板）纯惰性 outline-none」划出例外。
- 机制表述可再精确：`--tw-outline-style` 陷阱是**元素级**（`@property` `inherits:false`），只在「同一元素 outline-none 与 outline-\<n\> 并存」时抑制渲染，不跨元素扩散——约定原文已写「同一元素」，但措辞用「扩散」易误读为跨元素。

**修复方向（四步）**：① 修 3 处真实 a11y 缺口（CommandInput 补 focus-within、cascader trigger 补 FOCUS_OUTLINE_CLASSES 对齐 select、MenuItem/SubMenu 补 focus-visible 指示）；② 删除不可聚焦项（popover 面板、列表项）的惰性 outline-none——不给不可聚焦项补 outline（永不触发是死类）；③ 删 input-variants.ts:36 的 focus:ring-0；④ 约定改为带明确例外的规则（a 容器 focus-within 的内层 input 可保留、b 不可聚焦元素不得携带、c 修正机制为元素级描述），并保留既得方案（内层 input 三处 + tags-input.test.ts:77 断言标注「方案 E 组例外」）。

**置信度**：high

### C2 手抄 shadow 值（VISUAL_SYSTEM 规则 2）—— 裁决：**code_violates_good_convention**（约定三维全胜）

**关键证据（已核）**：13 处硬编码 `shadow-[Npx_Npx_0px_0px_rgba(...)]` 中有 **10 处值恰落在令牌标度上**（2px=shadow-brutal-sm、6px=shadow-brutal-lg、4px=shadow-brutal 基座），真正标度外仅 3 处（3px/1px/半透明红）。代码方「仅 3 处是字面副本、其余为令牌标度外」的主张**不成立**。且 13 处颜色通道全部冻结为 `rgba(0,0,0,1)/rgba(255,255,255,1)/rgba(239,68,68,0.3)`，无任何 `var()` 间接层——theme-pastel/mono 对 `--brutal-shadow-color` 的覆写永远作用不到；6 处缺 dark 变体，暗色下黑阴影在 `#141414` 背景上肉眼消失。

**约定占优理由**：单点事实源，主题/暗色经 CSS 变量级联自动跟随；现状是 13 处冻结字符串 + counter.test.ts:101 把任意值固化进测试，维护需 grep 逐一同步。约定唯一不精确处是把 3px/1px/半透明红也笼统称「令牌手抄」——它们并非副本，但这恰证明需要**扩展令牌刻度**而非硬编码。

**修复方向**：10 处标度内迁 shadow-brutal\*/sm\*/lg\*；标度外 3 处保留偏移但颜色走 `var(--brutal-shadow-color)`；半透明红在 styles.css 增补 `--shadow-brutal-destructive` 令牌（引用 --brutal-destructive 派生）而非硬编码 rgba；同步 counter.test.ts 断言；VISUAL_SYSTEM 规则 2 增补子刻度逃生口（定义 shadow-brutal-xs 或显式允许标度外偏移 + var() 颜色）。

**置信度**：high

### C3 硬编码颜色（VISUAL_SYSTEM 规则 6）—— 裁决：**code_violates_good_convention**（约定三维全胜）

**关键证据（已核）**：Result.vue 同一份 statusConfig 内 error/warning/empty 走 bg-brutal-\* 令牌、success/info 却硬编码 hex，**自相矛盾**；`bg-[#3b82f6]` 恰等于**暗色** --brutal-info 值，默认亮色下与库内 `#4A90D9` 不符；`text-gray-500(#6b7280)` 与库内 55 文件 84 处通用的 `text-brutal-muted-foreground(#4B5563)` 在默认主题下即已漂移。硬编码版本在默认主题下就有可观测不一致，token 版本没有。

**约定占优理由**：`--brutal-*` 运行时经 `var()` 解析，能响应 theme-pastel/mono/warm 预设、ThemePlayground .theme-custom、prefers-contrast:high；硬编码值构建期冻结。theme-warm 下全库边框 `#5C3D2E` 唯 Tour/TreeViewNode 是纯黑。

**合理例外（仅 2 处，暂留待约定补齐）**：TreeViewNode 虚线拖拽指示（border-brutal 的 solid 在产物中恒后于任意 border-style 类，属真实 token 工具缺口）与 5% 叠色（无对应令牌）。

**修复方向**：16 处硬编码回归令牌（success/info→bg-brutal-\*/info、text-gray→text-brutal-muted-foreground、border-brutal-black→border-brutal、硬编码 shadow→shadow-brutal）；约定补齐 text-brutal-muted-foreground/bg-brutal-yellow 工具类清单、虚线边框着色工具、--brutal-status-\* 状态色；同步 result.test.ts:35、counter.test.ts:100-101 断言。

**置信度**：high

### C4 border-3 双定义与细边框（VISUAL_SYSTEM 规则 1）—— 裁决：**code_violates_good_convention**（who_is_right=mixed，整体约定占优）

**关键证据**：约定机制核心（border-3 是令牌映射类：@theme `--border-width-3` → `var(--brutal-border-width,3px)`，随 mono 4px / high-contrast 4px / pastel 2px 变化）经产物级联验证成立，是库内唯一主题延伸点。代码侧 border-2 是固定 2px 工具类，mono/高对比度增强永远到不了消息边框。

**修复方向**：删 styles.css 手写 .border-3（纯冗余，.border-brutal 保留）；MessageContainer border-2→border-3（对齐 toast）；Transfer 保留 1px 次级边框但 rounded→rounded-brutal；VISUAL_SYSTEM 规则 1 补豁免子句「主边框 border-3 border-brutal；次级交互边框允许细 border border-brutal，圆角一律 rounded-brutal」。

**置信度**：high

### C5 过渡声明与实际属性错配 6 处 —— 裁决：**both_flawed**（整体约定占优，两者都要改）

**代码确有真缺陷（已实证）**：

### C6 separator 类名插值拼接 —— 裁决：**code_violates_good_convention**（约定占优）

**关键证据（已全核实）**：`@source ../**/*.ts` 覆盖测试文件；dist 产物实测含 `.h-[var(--sep-thickness,3px)]`；全仓非测试源码 grep `sep-thickness,3px` 零命中，唯一字面量来源是 separator.test.ts:10,42——**倒置依赖坐实**（测试内容是产物 CSS 的唯一字面量来源）。brutal-interaction-variants.ts 自身 `${brutalPress}` 拼接中每个完整类名仍是源码字面量，真实规则是「每个完整类名在可扫描源码中为字面量」，separator 恰缺此字面量。

**约定非过宽**：代码方「值单一事实来源」收益被高估——DEFAULT_THICKNESS 是冻结的 '3px'，不随主题 `--brutal-border-width`（mono 4px）变化，只是具名字面量而非活的主题来源；库内既有合规样板（SelectSeparator、stepper-variants）证明合规可行。

**修复方向**：改用「完整类名字面量常量 + ${} 组合」模式（`const thicknessHClass = 'h-[var(--sep-thickness,3px)]'` 等），既保单一事实来源又可被 @source 扫描；定级由 P0 降为 P2 构建契约健壮性债（产物当前完整、常量变更路径响亮失败）。

**置信度**：high

### C7 command item 按压反馈失效 —— 裁决：**both_flawed**（code_quality 判约定，可扩展性判代码）

**代码的问题**：command 复用共享构建块（brutalHighlightLiftWithBorder + brutalPress）DRY 且单一事实来源，但在主导交互路径（悬停高亮→点击）静默产出死代码——产物字节序 `data-[highlighted]` 恒后于 `active` 且同特异度，按压位移与去影反馈不出现。**干净但不工作的组合劣于重复但正确的模式**（对照 cascader/select 的显式 active:translate-x-0 重置，虽重复但兑现契约）。

**约定的问题**：未覆盖 data-\* 复合变体与字节序；cascader/select 的私有重置不可作 data-\* 冲突的参照（它们只解 hover/focus 冲突）。

**修复方向**：首选在共享变体补 `data-[highlighted]:active:translate-y-[...] data-[highlighted]:active:translate-x-0 data-[highlighted]:active:shadow-none`（特异度 0,3,0 压过 data-\* 的 0,2,0）恢复按压反馈；若设计确认「高亮项按压不反馈」为有意，则移除 brutalPress 并补注释，严禁保留永不生效的导入。约定补 data-\* 字节序机制警告。

**置信度**：high

### C8 toggle ON 态持久位移压过 hover/active —— 裁决：**no_real_violation**（报告过度指控）

**核心裁决**：ON=保持按下是**有意设计**，与库内 brutalPressedState「保持按下」惯用法一致（首个 Vue 提交即含该组合，copy-to-clipboard 同模式），行为在精神上符合 brutalPress「按下即整体接管」。brutalPress 约定只约束瞬态 `active:` 伪类接管，报告将其外推到持久 `data-*` 状态属过度扩展。

**报告定级修正**：从「违反约定、需人工确认」降为「P2 打磨」。

## 三、约定体系系统性弱点（7 条，Workflow 综合归纳）

1. **绝对化禁令普遍缺例外条款**：r04/r03/r12/R7/R1/AP3/R6 多为「禁止/切勿」绝对措辞，审计已把多数标为 over_constraint，裁决进一步实证合法例外（内层 input 保留 outline-none、Transfer 细边框防跳变、半透明红阴影、ghost 变体豁免）。规则无法指导真实边界，贡献者无法区分既有用法是缺陷还是惯例。
2. **关键技术机制表述不精确或缺失**：--tw-outline-style 元素级机制、transition-all 惯例与混合实践不符、@utility vs @layer utilities 变体支持、twMerge 同组静默移除、@source 静态扫描字面量要求——均未写入约定，正是 C1/C5/C6 争议根因，需要一份 Tailwind v4 机制权威说明。
3. **约定未覆盖与共享变体/状态模型的交互**：brutalPress/brutalHoverLift/WithTransition 常量与 data-\* 复合变体（C7 字节序）、持久 data-* 状态与瞬态 active 的管辖分界（C8）、共享模块「完整类名字面量」要求（C6）均无规则指引。
4. **多 guide 规则重复且口径不一**：outline 在 COMPONENT_GUIDE r12 / VISUAL_SYSTEM R7 / CVA.md 三处重复；transition 在 r13 与 R4 重复；按压在 R4 与 AP4 重复（「交互元素」vs「按钮」措辞不一）；**CVA.md 过期蓝图直接与 R6/R7 矛盾**。
5. **令牌/工具类体系不完整，迫使合法需求硬编码**：缺 --shadow-brutal-destructive、--brutal-status-\*、虚线边框着色工具、text-brutal-muted-foreground/bg-brutal-yellow 未入工具类清单——合法需求（C2/C3 标度外、C4 虚线指示）无令牌可循，规则只剩「禁」而无「给」。

## 四、交叉一致性核验冲突说明

Workflow 总编在约定审计与指控裁决之间发现 2 处 soundness 冲突，均集中在 C1 与 C5 的机制描述上：

- **C1 机制之争**：约定审计判 r12 sound 且「--tw-outline-style 机制描述高度准确」；裁决判「约定机制表述不精确（元素级非扩散）」。**本报告独立判断**：约定原文已限定「同一元素」，`--tw-outline-style` 陷阱确为元素级（@property inherits:false）——审计更正确；裁决的「表述不精确」有夸大，但其更核心的主张（绝对禁令需例外条款）成立。二者分歧在措辞精度，不在事实。
- **C5「transition-all 全库惯例」之争**：审计判 r13 sound 并实证 transition-all 确为默认惯例（约 80 处）；裁决判该表述与混合实践不符。二者都对：transition-all 是多数派，但 button/pagination/badge/select/breadcrumb 等关键组件各有不同，且 WithTransition 变体与规则 4 冲突——「全库惯例」的表述精确性不足是实。

## 附录：方法

1. **约定审计**（4 个并行只读 agent）：COMPONENT_GUIDE（17 条）/ VISUAL_SYSTEM+CVA / DOC_TEMPLATE+COMMIT / RELEASE 两组，逐条评估文本精确性、理由成立性、技术依据准确性（必要时读代码/产物核实）、过度约束、内部一致性、净影响。
2. **两方对抗**（8 条指控 × 2）：「约定拥护方」与「代码辩护方」各自独立读代码取证，验证技术机制（--tw-outline-style、@source 扫描、twMerge 合并、产物字节序），诚实列出对方最有力论点。
3. **首席裁判**（8 × opus）：逐点核对两方证据独立裁决，三分维度（代码质量/可扩展性/可维护性）分别判「约定更优/代码更优」，给出可执行修复方向。
4. **总编综合**（opus）：交叉核验约定审计 soundness 与裁决 verdict 一致性（发现 C1/C5 两处机制描述冲突，已在本报告第四节独立判断），归纳系统性弱点 7 条。
