# 项目架构总览

本文档阐明 BrutxUI 代码库的子包职责、依赖关系、关键系统流程与修改导航。

---

## 一、 职责与边界

BrutxUI 采用基于 pnpm 工作区与 Turbo 编排的 Monorepo 架构。各子包职责边界如下：

| 包名 | 物理路径 | 核心定位与职责 | 分发与交付形式 |
| --- | --- | --- | --- |
| `brutx-shared-vue` | [`packages/shared`](../../packages/shared) | 跨包基础设施层：统一虚拟文件系统抽象（VFS）、AST 解析与转换引擎、全局设计令牌（Design Tokens）单一事实来源、组件分类与共享类型 | 内部工作区依赖（`workspace:*`），不独立发布到 npm |
| `brutx-ui-vue` | [`packages/ui`](../../packages/ui) | 核心组件库：提供基于 Vue 3 + Tailwind CSS v4 + Reka UI 的新粗野主义 UI 组件、Composable、i18n 语言包与聚合样式表 | npm 官方包（`brutx-ui-vue`）及源码注册表的数据源 |
| `brutx-registry-vue` | [`packages/registry`](../../packages/registry) | 注册表编译流水线：将 UI 源码经过静态 AST 分析、依赖闭包递归计算、切片转换，编译生成符合 shadcn 规范的单组件 JSON 产物、SBOM 清单与数字签名 | 发布资产（GitHub Release Assets），供 CLI 在线拉取 |
| `brutx-vue` | [`packages/cli`](../../packages/cli) | 命令行脚手架：提供 `init`、`add`、`update`、`diff`、`doctor` 等指令，负责在用户项目中配置环境、注入令牌并下载/合并组件源码 | npm 官方 CLI 工具（`brutx-vue`） |
| `docs` | [`apps/docs`](../../apps/docs) | 官方文档站点：基于 VitePress 构建的中英文双语使用文档、组件交互 Demo、API 规范与迁移指南 | GitHub Pages 静态网站 |

## 二、 依赖拓扑与分发链路

### 1. 依赖拓扑关系

各包之间的构建与引用关系严格遵循单向依赖，禁止出现跨层反向引用或循环依赖：

```text
               ┌──────────────────────┐
               │   brutx-shared-vue   │  (令牌、VFS、AST、元数据)
               └──────────┬───────────┘
                          │
          ┌───────────────┼───────────────┐
          │               │               │
          ▼               ▼               ▼
   ┌─────────────┐ ┌─────────────┐ ┌─────────────┐
   │ brutx-ui-vue│ │  brutx-vue  │ │brutx-registry│
   │ (核心组件库) │ │  (CLI 工具) │ │-vue (编译器)│
   └──────┬──────┘ └─────────────┘ └──────┬──────┘
          │                               │
          │ (产物与样式)                   │ (编译输出注册表 JSON)
          ▼                               ▼
   ┌─────────────┐                 ┌─────────────┐
   │  apps/docs  │                 │GitHub Release│
   │ (文档站演示) │                 │(在线注册表源)│
   └─────────────┘                 └─────────────┘
```

- **开发与构建依赖**：`brutx-ui-vue`、`brutx-vue`、`brutx-registry-vue` 均在构建时依赖 `brutx-shared-vue` 的源码。
- **运行时依赖**：生产发布的 npm 包 `brutx-ui-vue` 仅依赖生产运行时原语（如 `reka-ui`、`clsx`、`tailwind-merge`），内部构建工具与 AST 转换器被彻底隔离外部化。

### 2. 双轨分发流向

- **通道 A（npm 依赖通道）**：
  - 由 `packages/ui` 构建生成 `dist/`。
  - 发布到 npm：`brutx-ui-vue`。
  - 用户通过 `pnpm add brutx-ui-vue` 直接安装使用。
- **通道 B（CLI 源码交付通道）**：
  - 由 `packages/registry` 读取 `packages/ui/src` 源码，编译为 JSON 注册表并签发 SBOM。
  - 上传至 GitHub Releases 作为资产。
  - 用户通过 `npx brutx-vue add <component>` 拉取注册表，将组件源码写入本地项目。

## 三、 关键系统流程

### 1. 本地开发与代码生成

代码生成是各包构建的前置依赖：
- 根目录运行 `pnpm generate:tokens` 触发 `turbo run generate`，编译令牌至 UI 样式表与 CLI 模板。
- 组件目录与导出清单由 `packages/ui/scripts/generate-exports.ts` 投影，保持 `api-contract.ts`、`package.json` 的 `exports` 与物理文件同步。

### 2. 质量门禁与验证

- **日常开发**：按改动领域执行针对性检查（如 `pnpm --filter <pkg> test <path>`、`pnpm check:contracts`、`pnpm check:docs`）。
- **发布准备**：执行 `pnpm release:prepare`，完成工作区守卫、版本 bump、各包 CHANGELOG 更新与根 CHANGELOG 提交。
- **发布门禁**：执行 `pnpm release:check`（`pnpm release`），全量验证构建、单测、静态契约、真实消费者矩阵与发布状态机演练。
- **远程发布**：打 Tag 后推送到远程仓库，CI 工作流（`publish.yml`）通过状态机协调器完成发布与签名。

## 四、 源码修改导航

当你需要修改某项能力时，按以下入口进入：

| 变更诉求 | 主修改入口 | 协同检查点 |
| --- | --- | --- |
| **修改设计令牌或调色板** | [`packages/shared/src/design-tokens.ts`](../../packages/shared/src/design-tokens.ts) | 运行 `pnpm generate:tokens`，校验 `packages/ui/src/styles.css` 与 `packages/cli/src/styles/brutalist.css` |
| **新增或修改 UI 组件** | [`packages/ui/src/components/<name>/`](../../packages/ui/src/components) | 更新 `api-contract.ts`；变体提取到 `*-variants.ts`；编写单元测试与无障碍测试；更新 `apps/docs` 使用示例 |
| **调整公开导出或子路径** | [`packages/ui/api-contract.ts`](../../packages/ui/api-contract.ts) | 运行 `pnpm --filter brutx-ui-vue prebuild:exports`；运行 `pnpm check:exports` 与 `pnpm check:contracts` |
| **修改 CLI 命令或交互** | [`packages/cli/src/commands/`](../../packages/cli/src/commands) | 运行 `packages/cli` 单元测试与端到端测试；核对用户项目配置生成 |
| **优化注册表编译与 AST** | [`packages/registry/src/compiler/`](../../packages/registry/src/compiler) | 运行 `pnpm --filter brutx-registry-vue validate` 与 `bench` |
| **更新文档与指南** | [`apps/docs/`](../../apps/docs) 或 [`docs/guides/`](../../docs/guides) | 运行 `pnpm check:docs`、`pnpm --filter docs typecheck` 与 `pnpm build:docs` |

## 五、 修改检查点

每次提交涉及多包架构的修改时，须核对：
1. **单一事实来源**：设计令牌是否仅在 `shared` 中修改，无手动硬编码。
2. **导出与契约一致性**：公开符号与 exports 是否由 `api-contract.ts` 投影，运行 `pnpm check:contracts` 全绿。
3. **依赖方向**：未引入循环依赖与幽灵依赖，运行 `pnpm check:deps` 通过。
4. **文档与示例同步**：中英文文档网站与受测示例同步更新，运行 `pnpm check:docs` 通过。
