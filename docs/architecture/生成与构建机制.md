# 生成与构建机制

本文档阐明 BrutxUI 的自动化代码生成体系、设计令牌编译映射、Turbo 构建流水线与 Git 暂存区快照一致性校验机制。

---

## 一、 职责与边界：输入与生成映射

为了防止多包维护时的代码漂移并保障唯一信源，工程内部分关键产物由脚本自动投影生成。**自动生成的文件严禁手动直接编辑**。

| 唯一数据源（手写输入） | 负责编译/生成工具 | 目标生成产物（自动生成，勿手动修改） |
| --- | --- | --- |
| [`packages/shared/src/design-tokens.ts`](../../packages/shared/src/design-tokens.ts) | `pnpm generate:tokens`（底层由 `packages/ui` 与 `packages/cli` 生成器驱动） | `packages/ui/src/styles.css`（`:root` / `.dark` / `@theme` 变量块）、`packages/ui/src/preflight.css`（字体栈）、`packages/ui/src/lib/utils.ts`（`BRUTAL_COLOR_NAMES` 列表） |
| [`packages/shared/src/design-tokens.ts`](../../packages/shared/src/design-tokens.ts) | `pnpm generate:tokens`（CLI 令牌编译器） | `packages/cli/src/styles/brutalist.css`（令牌与预设标记块）、`packages/cli/src/lib/constants.ts`（`UTILS_TEMPLATE` 模板块） |
| [`packages/ui/api-contract.ts`](../../packages/ui/api-contract.ts) | `pnpm --filter brutx-ui-vue generate`（统一代码生成入口，执行契约投影） | `packages/ui/registry-manifest.json`、`packages/ui/exports-manifest.json` |
| [`packages/ui/api-contract.ts`](../../packages/ui/api-contract.ts) | `pnpm --filter brutx-ui-vue generate`（exports 生成管线） | `packages/ui/package.json` 中的 `exports` 字段 |
| [`packages/ui/api-contract.ts`](../../packages/ui/api-contract.ts) | `pnpm --filter brutx-ui-vue generate`（组件索引生成管线） | `packages/ui/src/components/*/index.ts`（各组件导出入口）及 `packages/ui/src/index.ts`（根入口） |
| [`packages/ui/api-contract.ts`](../../packages/ui/api-contract.ts)、[`packages/shared/src/component-metadata.ts`](../../packages/shared/src/component-metadata.ts)、组件源码与双语语义资源 | `pnpm --filter brutx-ui-vue docs:manifest`（组件 API 提取与分组） | `apps/docs/.vitepress/api-generated/catalog.json` 与 `{slug}.zh-CN.json`、`{slug}.en.json` |

`docs:api` 按 [`packages/ui/typedoc.json`](../../packages/ui/typedoc.json) 生成 TypeScript API Markdown；`docs:api:full` 在此基础上生成 Vue 组件、Composable、索引及类型汇总 Markdown；`docs:api:vue` 生成同一组 Vue Markdown 并跳过 TypeDoc。这些包内 Markdown 文档输出至 `packages/ui/docs/api`。VitePress 使用的结构化双语组件 API 数据仅由 `docs:manifest` 通过共享 collector 生成。

`docs:manifest` 在单次生成中为每个组件组提取一次原始 API，再分别合并各语言的语义内容。原始提取结果在本次生成内复用，双语校验与输出分别执行。

## 二、 令牌编译与设计系统分工

### 1. 单一事实来源
所有设计令牌（边框粗细、硬阴影偏移、基准色、圆角标尺、Z-Index 层级）统一定义在 `packages/shared/src/design-tokens.ts` 中。

### 2. 多端编译器协作
- **UI 组件库端**：通过正则与 AST 注入器，将令牌编译为 Tailwind CSS v4 标准的 `@theme` 指令与 `:root` / `.dark` 变量，直接驱动组件渲染。
- **CLI 脚手架端**：将相同的令牌注入为独立的 `brutalist.css` 模板，在用户运行 `brutx-vue init` 时动态注入到用户项目的全局样式表中。

## 三、 Turbo 编排与缓存机制

### 1. 任务依赖图谱

在 [`turbo.json`](../../turbo.json) 中，构建与生成任务编排如下：

```text
┌──────────────────────┐          ┌────────────────────────┐
│ generate             │          │ docs:manifest          │
│ cache: false         │          │ cache: false           │
└──────────┬───────────┘          └───────────┬────────────┘
           │                                  │
           ▼                                  │
┌──────────────────────┐                      │
│ UI build:artifact    │──────────────────────┴──▶ docs build:artifact
└──────────────────────┘
```

- **`generate` 任务**：设置为 `"cache": false`。确保任何令牌或契约改动都能实时生成最新文件并保留手写区域。
- **`docs:manifest` 任务**：独立设置为 `"cache": false`，由文档构建显式依赖。它读取组件契约、共享组件元信息、Vue 源码和语义资源，生成页面目录及按组件组和语言拆分的数据；令牌生成不会调用该任务。
- **`build:artifact` 任务**：依赖前置的 `generate` 任务。当源码未变动时复用 Turbo 本地/云端构建缓存。
- **源码测试依赖**：UI 普通测试和 SSR 依赖 `generate`；Registry 单测依赖 UI 生成入口；CLI 的包契约测试依赖 CLI `build:artifact`。文档构建不进入源码测试任务图。
- **运行环境缓存**：CI 将实际 `process.version` 写入 `BRUTX_RUNTIME_VERSION`，Turbo 通过 `globalEnv` 区分 Node 运行时；Actions 保存 `.turbo/cache`，缓存 key 同时区分任务域和 Node 主版本。生成写入任务保持实时执行。
- **浏览器构建缓存**：Browser 作业使用 Playwright 支持的 Ubuntu 24.04 镜像；在 `TURBO_TOKEN` 与 `TURBO_TEAM` 齐全时使用 Turbo 远端缓存，凭证缺失时通过 Actions 恢复和保存本地 Turbo 缓存。Playwright 浏览器二进制按操作系统、架构和锁文件独立缓存。缓存未命中时安装 Chromium 及系统依赖，命中时安装系统依赖。生产 tarball 的资源检查在一次 Chromium 进程中执行，各 profile 使用独立上下文。
- **CI 调度**：CI 始终触发，由 [`scripts/ci/change-scope.mjs`](../../scripts/ci/change-scope.mjs) 选择任务。PR 使用 merge-base 差异选取检查；main push 对该提交执行全量检查，确保被后续 push 替代的待运行项仍由包含其提交的完整验证覆盖；手动运行留空 `base_sha` 时执行全量检查，填写基线时按与运行提交的直接差异选择任务。`CI Gate` 要求选中任务成功，并拒绝失败、取消及选中任务意外跳过。
- **质量检查链**：`Quality` 承担包构建、类型、lint、validate 与产物消费检查；`Tooling and documentation checks` 独立承担生成物一致性、静态契约、工具测试、文档、提交规范及发布脚本检查。工具及规范链先物化 UI 生成入口，再执行源码契约与工具测试。两条链在隔离作业中并行，由 [`selectCiChecks()`](../../scripts/ci/evaluate-gate.mjs) 统一选择并汇入 Gate；纯文档和发布规范变更执行工具及规范链。
- **消费者并发**：`pnpm test:consumers --parallel --all` 共用一次候选包打包，以最多两个独立子进程执行 U1、C1、C3。各消费者的证据与结果路径独立，父进程统一汇总；失败时终止并回收同批子进程。省略 `--parallel` 时串行执行，默认场景仍为 U1/C1。
- **文档构建与部署**：main 全量 CI 的站点任务保留完整 Git 历史并上传站点产物；`Deploy Docs` 在成功 CI 完成后绑定其运行 ID 下载产物，直接发布到 Pages。来源必须为同仓库、当前 main 提交的 push；所有 main 提交均可接续此前取消运行中的文档变更。手动部署保留安装、文档健康检查、构建和发布入口。
- **Node 测试覆盖**：CI 统一使用 Node 22。UI 源码测试由两个 coverage 分片运行，汇总任务执行正式覆盖率阈值；UI 脚本契约由 tooling 承担。其他包单元测试与 UI SSR 在同一运行时执行；Gate 同时要求源码覆盖率与脚本契约检查成功。
- **覆盖率汇总准备**：汇总作业仅安装 UI 及其工作区依赖，直接合并分片记录并生成正式报告。源码执行所需的 UI 生成由分片承担；完整覆盖率阈值在汇总阶段执行。UI 公共测试环境中的 `axe-core` 在可访问性 helper 调用时加载。
- **文档开发服务**：`pnpm --filter docs dev` 先生成 API 数据，再启动 VitePress，并监听组件源码、公开契约、共享元信息、组件页面、双语语义资源和相关配置。变化经具名 debounce 后串行生成；生成期间的新输入排入下一轮，失败会明确输出错误。传给开发命令的 VitePress CLI 参数会原样转发，例如 `pnpm --filter docs dev -- --host 127.0.0.1 --port 5180`。
- **`brutx-registry-vue#build:artifact`**：同样保持 `"cache": false`，并依赖 `brutx-ui-vue#generate`，确保读取最新 UI 源码。

## 四、 暂存区快照检查（Staged Snapshot）

提交前的候选快照检查覆盖 UI、CLI 和组件 API 文档生成物：

### 1. `check:staged-snapshot` 机制
- 在提交前或 pre-commit 钩子中，运行 `node scripts/generation/check-staged-snapshot.mjs`。
- 脚本直接从 Git 暂存区（Index）物化隔离的候选目录，在候选目录中运行对应的只读生成检查；工作树中未暂存的源码不会进入生成器输入。
- UI、共享组件元信息及根依赖配置会触发 UI/CLI 检查；组件 API 契约、组件源码、文档页面、双语语义资源及生成器配置会额外触发 `docs:manifest:check`。
- 若生成输入已暂存而输出缺失或过期，候选快照检查会报告差异；检查不会修改真实 index 或工作树。

### 2. 自愈与提交引导
当快照检查失败时：
1. 运行 `pnpm generate:tokens`；组件 API 数据过期时运行 `pnpm --filter brutx-ui-vue docs:manifest`；
2. 运行 `git diff` 审视被自动更新的文件；
3. 将受影响的文件同批执行 `git add` 并重新提交。

| 操作 | 命令 | 说明 |

## 六、 手动执行 CI

`CI` 支持手动触发。`base_sha` 留空执行全量检查；填写明确的 Git 提交时，以该提交与运行提交的直接差异选取任务，用于复测领域变更的耗时。手动运行以 `CI Timing (selected checks)` 记录结果。PR 按 merge-base 差异选取检查，main push 执行全量检查；两者使用 `CI Gate (all checks passed)`。

```bash
gh workflow run ci.yml --ref <分支> -f base_sha=<基线提交>
```
