# 文档链接检查与自愈引擎改进方案

> 本方案针对 `scripts/docs/check-doc-links.mjs` 脚本进行系统性重构与深模块化升级。从第一性原理与终态无痕原则出发，全面复用 Monorepo 成熟的虚拟文件系统（`brutx-shared-vue/fs`）与 AST 转换范式（`brutx-shared-vue/ast`）；彻底废除全部历史静态映射表与别名配置，建立纯动态、无状态的 Basename 拓扑倒排自愈机制；采用原生系统调用穿透解决 Windows 11 环境下的跨平台路径大小写假阳性；通过基于 `MagicString` 的原位切片替换模型，保障文档原始排版 100% 无损与提取改写严格对称；实施生命周期分层降噪，并构建微秒级内存化测试防护网。

---

## 一、 背景与第一性原理

在 BrutxUI Vue 3 Monorepo 体系中，文档作为系统设计、视觉规范、架构决策与 AI Agent 上下文的单一事实源，承担着极其关键的枢纽职责。`scripts/docs/check-doc-links.mjs` 作为全量文档门禁（`pnpm check:docs`）的底层第一道防线，负责守护全仓 Markdown 链接的完整性与可移植性。

随着全工程完成 [虚拟文件系统统一](../../archive/2026/core/全工程虚拟文件系统统一与持久化深模块重构方案.md) 与 [AST解析统一](../../archive/2026/core/AST解析统一与源码工具链治理方案.md)，审视现行链接检查脚本，暴露出以下深层次的技术债务与设计断层：

### 1. 物理磁盘穿透与测试脆断（缺少 VFS 抽象）
现行脚本直接调用 `node:fs` 原生同步 API（`existsSync`、`readFileSync`、`writeFileSync`、`readdirSync`），与物理磁盘强绑定，逃逸了全工程统一的 `FileSystemAdapter` 契约。这导致编写自动化测试时必须在物理磁盘上反复创建与清理临时文件，在 Windows 11 下极易因文件句柄占用或盘符差异引发偶发性故障，无法进行微秒级内存沙箱演练。

### 2. 状态机脆弱与提取改写不对称（缺乏 AST/MagicString 保护）
- **代码围栏翻转错乱**：单行布尔翻转 `line.trim().startsWith('```')` 无法处理 CommonMark 规范中 4 个反引号围栏嵌套 3 个反引号示例（如 `carousel` 语法），导致代码块内部被误判为正文并提取出伪链接。
- **提取与改写不对称**：提取阶段用正则剔除了行内反引号，但在 `fix` 改写阶段却直接对整行文本执行 `line.replace(LINK_RE, ...)`，导致行内代码块中的链接展示示例（如 `` `[text](url)` ``）在提取时被跳过、在改写时却被破坏。
- **排版污染风险**：采用行级正则替换不仅易破坏内联 HTML 或复杂 Markdown 标记，而且缺乏区间重叠保护。

### 3. Windows 11 跨平台大小写假阳性（Case Sensitivity Blindspot）
开发环境运行在 Windows 11（NTFS 默认不区分大小写），Node.js 的 `existsSync` 在大小写拼写错误时依然返回 `true`。若开发者书写了 `[视觉系统](./visual_system.md)`（实际文件为 `VISUAL_SYSTEM.md`）或祖先目录大小写错误 `docs/Guides/...`，本地门禁显示全绿，但推送至 Linux CI 环境（ext4）后将直接导致 404 阻断。传统的单层 `readdir` 缓存无法穿透各级祖先目录，必须从 OS 真实路径返回的第一性原理予以根治。

### 4. 历史脚手架残留与静态映射负债（完全无需维护别名表）
现行脚本内残留了 110 余行的 `MIGRATE` 静态对象。实测核验表明：
- 当前全仓 72 个 Markdown 文档中，**没有任何一处活跃链接仍在引用这些旧路径**；
- 当初的 `MIGRATE` 是目录改造过程中的一次性脚手架过渡物；
- 遵循“终态无痕”与“开发早期 0.x 不背负历史包袱”原则，**不应当将硬编码转移至外部 JSON 别名表，而应彻底抛弃任何静态映射**。未来无论方案由 `docs/plans/` 归档到 `docs/archive/YYYY/` 还是在各领域子目录间微调，只要文件名保持不变，**Basename 倒排拓扑索引即可 100% 自适应动态重算相对路径**，实现真正的“零维护成本”。

### 5. 缺乏生命周期分层导致告警疲劳（Alert Fatigue）
当前运行 `--verbose` 时输出整整 66 条历史源码失效告警，全部来自 `docs/archive/` 与 `docs/reports/`。根据 `DOC_GOVERNANCE.md`，归档与扫描快照属于时间点静态记录，引用的历史源码在后续重构中删除属于正常现象。将历史快照与常青规范（`docs/guides/`、`docs/plans/`）平铺报警，严重掩盖了真正的常青坏链。

### 核心设计原则

1. **依赖倒置与纯内存沙箱**：核心引擎 `DocLinkEngine` 依赖 `FileSystemAdapter` 契约，生产环境使用 `DiskFileSystemAdapter`，自动化测试与 Dry-Run 演算全面注入 `MemoryFileSystemAdapter`。
2. **基于 `MagicString` 的排版无损自愈**：分词阶段记录 Link Token 的绝对字符区间 `[startOffset, endOffset]`，改写阶段通过 `MagicString.overwrite` 进行原位切片替换，确保 0 排版污染、100% 提取与改写对称。
3. **原生穿透大小写核验**：利用 `fs.realpathSync.native` 一次性穿透整条路径的全部祖先目录与末级文件名，根除跨平台假阳性，并直接利用原生真实路径提供大小写自愈。
4. **纯动态拓扑自愈（零配置文件、零历史别名）**：
   - 彻底剔除所有静态映射表，不维护任何 `aliases.json` 或迁移字典；
   - 唯一事实源即当前文件系统的物理拓扑，由内存中的 Basename 倒排拓扑索引实现 100% 动态推导；
   - 设立同名保留字黑名单（`README.md`、`index.md`、`SKILL.md` 等）与领域边界隔离，杜绝误定向。
5. **生命周期分级降噪**：常青规范死链阻断退出，历史快照源码失效做静默聚合。

### 2. 原生路径穿透的大小写守卫（抹平 Windows 11 假阳性）

摒弃只能校验单层文件名且需维护私有缓存的 `readdir` 方案，采用 Node.js 原生系统调用：

```typescript
import path from 'node:path';

export interface PathCaseVerification {
    exists: boolean;
    exactCase: boolean;
    realPath: string | null;
}

/**
 * 跨平台路径大小写全路径穿透校验
 * 利用 OS 原生 realpath 穿透中间祖先目录与末级文件名
 */
export async function verifyPathCase(
    fsAdapter: FileSystemAdapter,
    absPath: string
): Promise<PathCaseVerification> {
    const exists = await fsAdapter.pathExists(absPath);
    if (!exists) {
        return { exists: false, exactCase: false, realPath: null };
    }

    try {
        // 调用原生真实物理路径解析
        const realPath = await fsAdapter.realpath(absPath);
        const normalizedInput = path.normalize(absPath).replace(/\\/g, '/');
        const normalizedReal = path.normalize(realPath).replace(/\\/g, '/');

        // 在 Windows 上统一盘符大小写后进行严格字符等价校验
        const exactCase = normalizedInput.toLowerCase() === normalizedReal.toLowerCase()
            ? normalizedInput === normalizedReal
            : false;

        return {
            exists: true,
            exactCase,
            realPath: normalizedReal,
        };
    } catch {
        return { exists: false, exactCase: false, realPath: null };
    }
}
```

> [!TIP]
> 当 `exists === true` 但 `exactCase === false` 时，返回的 `realPath` 包含了文件系统在物理层注册的**完全正确的大小写形式**。自愈引擎可直接根据 `realPath` 重写相对链接，实现大小写缺陷的“零查表秒级自愈”。

### 3. 基于 `MagicString` 的原位切片替换分词器

为保证 100% 排版无损，链接提取阶段必须产出绝对字符偏移量 `SourceRange`；改写阶段使用 `MagicString` 进行原位替换：

```typescript
import MagicString from 'magic-string';
import type { SourceRange } from 'brutx-shared-vue/ast';

export interface ExtractedMarkdownLink {
    text: string;
    target: string;
    rawTarget: string;
    range: SourceRange;
    targetOffsetStart: number;
    targetOffsetEnd: number;
}

/**
 * 词法分词器：精确识别 CommonMark 规范代码围栏与行内代码，产出带物理偏移的 Link Token
 */
export function extractMarkdownLinks(content: string, filename: string): ExtractedMarkdownLink[] {
    const links: ExtractedMarkdownLink[] = [];
    const lines = content.split('\n');
    let currentOffset = 0;
    let activeFence: { marker: string; length: number } | null = null;

    for (let lineIndex = 0; lineIndex < lines.length; lineIndex++) {
        const line = lines[lineIndex];
        const trimmed = line.trim();

        // 1. CommonMark 围栏匹配（3+ 个 ` 或 ~）
        const fenceMatch = trimmed.match(/^(`{3,}|~{3,})/);
        if (fenceMatch) {
            const markerChar = fenceMatch[1][0];
            const markerLen = fenceMatch[1].length;

            if (!activeFence) {
                // 进入代码块
                activeFence = { marker: markerChar, length: markerLen };
                currentOffset += line.length + 1;
                continue;
            } else if (activeFence.marker === markerChar && markerLen >= activeFence.length) {
                // 必须使用同种字符且长度 >= 起始标记才闭合
                activeFence = null;
                currentOffset += line.length + 1;
                continue;
            }
        }

        if (activeFence) {
            currentOffset += line.length + 1;
            continue;
        }

        // 2. 正文分词：屏蔽行内代码块干扰（将行内 `...` 区间临时遮蔽但保持字符长度与偏移一致）
        const maskedLine = maskInlineCodeSpans(line);

        // 3. 扫描 Markdown 链接 [text](target)
        const linkRegex = /(!?)\[([^\]]*)\]\((<[^>]+>|[^)\s]+)(?:\s+["'][^"']*["'])?\)/g;
        let match: RegExpExecArray | null;

        while ((match = linkRegex.exec(maskedLine)) !== null) {
            const fullMatch = match[0];
            const text = match[2];
            let rawTarget = match[3];

            // 还原尖括号链接 <path>
            if (rawTarget.startsWith('<') && rawTarget.endsWith('>')) {
                rawTarget = rawTarget.slice(1, -1);
            }

            // 计算 target 字符串在整篇文档中的绝对起始与结束偏移量
            const matchIndexInLine = match.index;
            const targetIndexInMatch = fullMatch.indexOf(match[3]);
            const targetOffsetStart = currentOffset + matchIndexInLine + targetIndexInMatch;
            const targetOffsetEnd = targetOffsetStart + match[3].length;

            links.push({
                text,
                target: rawTarget,
                rawTarget: match[3],
                targetOffsetStart,
                targetOffsetEnd,
                range: {
                    startOffset: currentOffset + matchIndexInLine,
                    endOffset: currentOffset + matchIndexInLine + fullMatch.length,
                    startLine: lineIndex + 1,
                    startColumn: matchIndexInLine + 1,
                    endLine: lineIndex + 1,
                    endColumn: matchIndexInLine + fullMatch.length + 1,
                },
            });
        }

        currentOffset += line.length + 1;
    }

    return links;
}

/**
 * 原位无损重写：复用 packages/shared/src/ast/import-transformer.ts 范式
 */
export function rewriteLinksWithMagicString(
    content: string,
    replacements: readonly { start: number; end: number; replacement: string }[]
): string {
    if (replacements.length === 0) return content;

    const s = new MagicString(content);
    // 按起始偏移量降序排序，杜绝索引重叠破损
    const sorted = [...replacements].sort((a, b) => b.start - a.start);

    for (const item of sorted) {
        s.overwrite(item.start, item.end, item.replacement);
    }

    return s.toString();
}
```

### 6. 锚点解析器带清洗与 VitePress 扩展兼容

在提取标题前统一清洗内联 HTML 标签（如 `<Badge text="alpha" />`）与行内代码反引号，并同时支持 GitHub Slug 规范与 VitePress `{#custom-id}`：

```typescript
export function extractHeadingAnchors(markdownContent: string): Set<string> {
    const anchors = new Set<string>();
    const counts = new Map<string, number>();

    for (const line of markdownContent.split('\n')) {
        const match = line.match(/^#{1,6}\s+(.+)$/);
        if (!match) continue;

        let title = match[1].trim();

        // 1. 匹配并剥离 VitePress 自定义 id: ## 标题 {#custom-id}
        const customIdMatch = title.match(/\{#([\w-]+)\}$/);
        if (customIdMatch) {
            anchors.add(customIdMatch[1]);
            title = title.replace(/\{#[\w-]+\}$/, '').trim();
        }

        // 2. 剥离内联 HTML 标签与格式标记，确保与 VitePress 渲染器一致
        title = title.replace(/<[^>]+>/g, '').replace(/[`*_~]/g, '').trim();

        // 3. 计算 Unicode Slug (支持中文)
        const slug = slugify(title);
        const count = counts.get(slug) ?? 0;
        counts.set(slug, count + 1);
        anchors.add(count === 0 ? slug : `${slug}-${count}`);
    }

    return anchors;
}
```
