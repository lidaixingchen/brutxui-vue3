## 一、 背景与第一性原理

在 BrutxUI Vue 3 持续演进的过程中，部分早期基础设施与组件交互逻辑在经历了多轮迭代后，呈现出**生命周期双轨**、**语义抽象分歧**、**核心算法散落**与**受控/非受控状态不同步**的架构债务。依照深模块（Deep Module）、单一信源（Single Source of Truth, SSOT）与确定性状态流转原则，需对以下 4 个关键维度进行彻底重构与收拢：

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│                          4 项核心治理问题全景                               │
├─────────────────────────────────────────────────────────────────────────────┤
│ 1. 全局单例与异步业务生命周期治理 (State Lifecycle Management)               │
│    ├─ useTheme / useToast 已接入 createFallbackManager (宿主生命周期)        │
│    └─ useMessage 兼具「组件级引用」与「脱离宿主的独立异步展示时长 (duration)」 │
│       需建立兼顾组件卸载清理与活跃消息展示守卫的统一 Fallback 机制          │
│                                                                             │
│ 2. useDialog 与 useDialogGeometry 语义与职责内聚度解耦 (Separation)         │
│    ├─ useDialog: 全局/命令式弹层触发器（返回 show / open / close / isOpen）  │
│    └─ useDialogGeometry: 纯粹的 Headless 几何空间状态控制器 (拖拽/缩放/尺寸) │
│       将关闭拦截 (beforeClose) 与生命周期业务控制流剥离至组件层             │
│                                                                             │
│ 3. 色彩计算、Alpha 混合与 WCAG 对比度算法收拢 (Color & Contrast Logic)      │
│    ├─ 下沉 Hex/RGB/HSL 通道解析至 shared 唯一信源，杜绝跨包双轨正则         │
│    ├─ 引入 Alpha 混合算法 (Alpha Over Blending)，保障半透明色彩对比度精确性 │
│    └─ packages/ui 运行时工具层与 theme-contrast 门禁统一消费 shared 纯函数   │
│                                                                             │
│ 4. 组件受控/非受控双轨模式对称性与异步流转 (Controlled/Uncontrolled)         │
│    ├─ Tabs.vue 配置模式：绑定 activeValue 计算属性与 internalValue           │
│    ├─ Tabs.vue 插槽模式：直接绑定 :model-value="modelValue"，非受控状态断流 │
│    └─ 统一增加 defaultValue 支持，补齐异步 props.tabs 数据流同步与契约规范    │
└─────────────────────────────────────────────────────────────────────────────┘
```

## 二、 架构设计与核心契约

### 1. 全局单例与生命周期管理 (`useMessage` 接入活跃消息守卫机制)

#### 1.1 现状痛点与生命周期本质差异
`useTheme` 与 `useToast` 已经迁移至深模块 `createFallbackManager`。但对于全局命令式消息 `useMessage`：
1. **宿主生命周期 vs 异步业务生命周期**：
   `useTheme` / `useToast` 的状态依赖于 UI 树的存在；而命令式 `useMessage` 具有**脱离触发组件树的独立物理生命周期**（每条消息有物理停留时间 `duration` 且需完成离场动画）。
2. **提前误杀场景**：
   若简单套用普通引用计数，用户在弹窗或即将跳转的页面组件中调用 `useMessage().success('保存成功')` 后关闭弹窗或切换路由，当前组件卸载会触发 `refCount <= 0`，导致正在展示的消息被**瞬间抹杀、DOM 容器被提前强制卸载**。
3. **无组件上下文调用场景**：
   在 Axios 拦截器、Pinia Store 或全局路由守卫中调用 `useMessage().error(...)` 时，`getCurrentInstance()` 为 `null`，`refCount` 恒为 0。若无活跃消息守卫，后续任意临时组件卸载都会将全局消息系统全量销毁。

#### 1.2 架构设计：双重守卫与惰性 GC 机制
重构后的 `useMessage` 采用「主动销毁」与「带活跃消息守卫的被动清理」双轨机制：

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│                       useMessage 复合生命周期流转图                          │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   useMessage() ───▶ acquireMessageSystem()                                  │
│                            │                                                │
│         ┌──────────────────┴──────────────────┐                             │
│         ▼ (首次调用懒加载)                    ▼ (组件 setup 上下文)          │
│   ensureMounted()                       refCount++                          │
│   ├─ 挂载 MessageContainer 容器          onUnmounted:                        │
│   └─ 注册 beforeunload 自动注销          ├─ refCount--                      │
│                                          └─ 若 refCount <= 0:                │
│                                              ├─ 若 store 为空 ──▶ 立即 GC   │
│                                              └─ 若 store 非空 ──▶ 延迟 GC   │
│                                                                             │
│   addMessage(options)                                                       │
│   ├─ 写入 messageStoreRef                                                   │
│   ├─ 取消待执行的 GC 延迟定时器 (cancelGC)                                  │
│   └─ 启动 duration 定时器 ──▶ 倒计时结束 ──▶ removeMessage(id)              │
│                                                   │                         │
│                                                   ▼                         │
│                                     若 store 为空 且 refCount <= 0          │
│                                     └─ 触发 scheduleGC() ──▶ 卸载 DOM 容器  │
│                                                                             │
│   destroyBrutxUI() / destroyFallback() (显式主动清理)                        │
│   └─ 强制清空所有定时器 ──▶ 清空 Store ──▶ 卸载 DOM 容器 ──▶ 移除 beforeunload│
└─────────────────────────────────────────────────────────────────────────────┘
```

#### 1.3 契约规范
1. **显式主动销毁（Explicit Destroy）**：
   `destroyFallback`（供 `destroyBrutxUI` 调用）无条件强制清空所有消息定时器、清空 `messageStoreRef`、卸载 DOM 容器并重置 `refCount`，用于测试隔离与应用卸载。
2. **被动延迟清理（Passive Delayed Cleanup）**：
   - 当组件卸载触发 `refCount <= 0` 时，若 `messageStoreRef.value.length === 0`，启动 GC 延迟定时器（`MESSAGE_GRACE_PERIOD_MS`，默认 3000ms），到期后卸载 DOM 容器。
   - 若 `messageStoreRef.value.length > 0`（仍有活跃消息），容器保持存续；当最后一条消息完成展示并由 `removeMessage` 从 store 移除后，自动检查 `refCount <= 0` 并触发 GC。
   - 任何新消息的加入（`addMessage`）都会立即中断并取消挂起的 GC 定时器。
3. **状态只读保护**：
   `messageStore` 导出保持 `DeepReadonly<Ref<MessageItem[]>>` 契约，外部仅能通过 `useMessage` 返回的 action 方法或 `removeMessage` 修改。
4. **兼容性导出**：
   导出 `destroyFallback`，并将 `destroyMessageSystem` 标记为 `@deprecated` 别名保留。

### 2. Composable 命名规范与职责解耦 (`useDialogGeometry` 纯几何状态控制器)

#### 2.1 现状痛点与职责混杂
在 `packages/ui/src/composables` 中：
- `useDialog`：命令式弹窗入口（包装 `showDialog`，返回 `show/open/close/isOpen`）。
- 原 `useDialogEnhanced`：名称泛化，且内部混杂了**几何空间状态（Geometry）**与**业务控制流（Control Flow）**两类完全不同的关注点：
  - 几何关注点：`position`、`size`、`isDragging`、`isResizing`、`bounds`、`aspectRatio`、`onDragStart`、`onResizeStart`、`contentStyle`。
  - 业务控制流关注点：`beforeClose` 异步拦截、并发锁 `isClosing`、`handleClose`、`onOpen`、`onClose`、`onUpdateOpen`。

#### 2.2 架构解耦方案
将空间几何与业务控制流彻底解耦：
1. **纯粹的几何控制器 `useDialogGeometry`**：
   只负责管理 DOM 元素的位置、尺寸、拖拽手势、缩放手势、边界约束计算与 `contentStyle`。
2. **控制流收归组件层**：
   `beforeClose` 异步拦截、`isClosing` 并发防重、`handleClose` 及生命周期事件触发直接由 `DialogEnhanced.vue` 内部维护，使 composable 保持高内聚与零业务侵入。

#### 2.3 命名契约矩阵

| 类别 | 命名规范 | 典型职责与代表 Composable | 返回契约 |
| --- | --- | --- | --- |
| **命令式触发器 (Imperative)** | `use<Component>` | `useDialog`, `useMessageBox`, `useToast`, `useMessage` | `{ show, open, close, isOpen: Readonly<Ref<boolean>> }` 或 `{ success, error, ... }` |
| **局部交互/几何控制器 (Headless)** | `use<Component><Feature>` | `useDialogGeometry`, `useCanvasInteraction`, `useStepper`, `useTransferPanelSelection` | `{ position, size, isDragging, onDragStart, setPosition, setSize, contentStyle, ... }` |

#### 2.4 重构契约
1. 新建 `packages/ui/src/composables/useDialogGeometry.ts`，导出 `useDialogGeometry`、`UseDialogGeometryOptions`、`UseDialogGeometryReturn`。
2. 严格遵守只读契约：`position` 与 `size` 为 `DeepReadonly<Ref<{...}>>`，修改经 `setPosition` / `setSize` 执行；`isDragging` 与 `isResizing` 为 `Readonly<Ref<boolean>>`。
3. `DialogEnhanced.vue` 内部直接迁移至 `useDialogGeometry`，其自身的 `beforeClose` / `handleClose` 逻辑在组件 `<script setup>` 中实现。
4. 原 `useDialogEnhanced.ts` 重新导出 `useDialogGeometry` 并将旧 API 标记为 `@deprecated`。

### 3. 色彩解析、Alpha 混合与 WCAG 对比度算法单一信源 (`packages/shared/src/color-contrast.ts`)

#### 3.1 现状痛点
1. **算法散落与潜在双轨**：
   `packages/ui/src/lib/color.ts` 实现了完整的 HSV/RGB/HSL 解析，而 `packages/ui/src/lib/theme-contrast.test.ts` 内部私有手写了一套 Hex 解析与对比度公式，跨包工具无法复用。
2. **半透明色彩对比度失真（缺少 Alpha 混合）**：
   WCAG 2.1 相对亮度计算基于不透明色彩。当遇到带透明度的色彩（如 `#RRGGBBAA` 或 `rgba(r,g,b,a)`）时，若直接忽略 alpha，会导致半透明前景/背景的对比度计算结果严重失真。

#### 3.2 架构收拢方案

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│                       色彩与对比度单一信源流转图                            │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   packages/shared/src/color-contrast.ts (唯一数据源与纯计算实现)             │
│   ├─ parseColorChannels(color: string | RGBColor): [r, g, b, a]            │
│   ├─ blendAlpha(fg: RGBColor, bg?: RGBColor): RGBColor                      │
│   ├─ srgbToLinear(channel: number): number                                  │
│   ├─ getRelativeLuminance(color, underlay?): number                         │
│   ├─ calculateContrastRatio(c1, c2, underlay?): number                      │
│   ├─ CONTRAST_RATIO_THRESHOLDS = { AA: 4.5, AAA: 7.0, 'AA-large': 3.0 }     │
│   └─ isContrastCompliant(ratio, level?): boolean                            │
│                                                                             │
│         ▲                                         ▲                         │
│         │ (导入纯函数)                            │ (导入与重新导出)         │
│   theme-contrast.test.ts                 packages/ui/src/lib/color.ts       │
│   (全主题预设 WCAG AA 门禁)              (ColorPicker / 运行时工具层)       │
└─────────────────────────────────────────────────────────────────────────────┘
```

#### 3.3 数学定义与算法契约
1. **Alpha 混合公式（Alpha Over Blending）**：
   当色值包含 Alpha 通道 $\alpha \in [0, 1)$ 时，与底色背景（默认白色 `#ffffff`，或深色模式下背景色）合成等效不透明 RGB 通道：
   $$C_{\text{composite}} = \alpha \times C_{\text{fg}} + (1 - \alpha) \times C_{\text{bg}}$$
2. **WCAG 2.1 sRGB 线性化与相对亮度公式**：
   $$\text{linear}(C) = \begin{cases} \frac{C / 255}{12.92}, & \frac{C}{255} \le 0.04045 \\ \left(\frac{C / 255 + 0.055}{1.055}\right)^{2.4}, & \frac{C}{255} > 0.04045 \end{cases}$$
   $$L = 0.2126 \times R_{\text{linear}} + 0.7152 \times G_{\text{linear}} + 0.0722 \times B_{\text{linear}}$$
3. **对比度比率公式**：
   $$\text{Ratio}(L_1, L_2) = \frac{\max(L_1, L_2) + 0.05}{\min(L_1, L_2) + 0.05}$$
4. **输入宽容度**：
   纯函数解析器支持标准 Hex（`#RGB`, `#RGBA`, `#RRGGBB`, `#RRGGBBAA`）、`rgb(...)`/`rgba(...)`、`hsl(...)`/`hsla(...)` 以及 `{ r, g, b, a? }` 对象。
5. **依赖关系**：
   `packages/shared` 提供零外部依赖、无副作用的纯数学与解析工具；`packages/ui/src/lib/color.ts` 直接复用并重新导出这些工具，彻底消除两包间的重复正则。

### 4. Tabs 组件受控/非受控双轨模式对称性治理 (`Tabs.vue`)

#### 4.1 现状痛点
1. **插槽模式非受控状态断流**：
   在插槽模式（未传 `tabs` prop）下，模板直接绑定了 `:model-value="modelValue"`。若用户未传 `v-model`，`:model-value` 恒为 `undefined`，导致内部点击切换时状态无法自洽闭环。
2. **缺少 `defaultValue` 支持**：
   两套模式均不支持非受控初始默认值声明。
3. **异步数据源响应式断裂**：
   若 `tabs` 属性异步加载（如从 API 获取），初始化时 `tabs` 为空，若无响应式监听与重置，异步数据到达后非受控状态将丢失初始首项选择。

#### 4.2 双轨状态机流转设计

```text
               ┌──────────────────────────────────────────────┐
               │              props.modelValue?               │
               └──────────────────────┬───────────────────────┘
                                      │
                         ┌────────────┴────────────┐
                         ▼ 是                      ▼ 否 (非受控模式)
                  props.modelValue        ┌────────────────────────────────┐
                  (受控优先，只读直出)     │ internalValue.value (交互优先) │
                                           │ 或 props.defaultValue          │
                                           │ 或 props.tabs?.[0]?.value      │
                                           │ 或 undefined (插槽等待交互)   │
                                           └────────────────────────────────┘
                                                            │
                                                            ▼
                                                activeValue 计算属性
                                                            │
                                    ┌──────────────────────┴──────────────────────┐
                                    ▼                                             ▼
                        配置模式 (v-if="tabs...")                     插槽模式 (v-else)
                  <TabsRoot :model-value="activeValue">         <TabsRoot :model-value="activeValue">
```

#### 4.3 契约规范与核心实现
1. **接口定义**：
   ```ts
   interface TabsProps {
       modelValue?: string
       defaultValue?: string
       tabs?: TabItem[]
       orientation?: 'horizontal' | 'vertical'
       class?: string
   }
   ```
2. **状态机与响应式监听**：
   ```ts
   const internalValue = ref<string>(props.defaultValue ?? props.tabs?.[0]?.value ?? '')

   const activeValue = computed<string | undefined>(() => {
       if (props.modelValue !== undefined) return props.modelValue
       if (props.tabs && props.tabs.length > 0) {
           const current = internalValue.value
           const exists = current !== '' && props.tabs.some(tab => tab.value === current)
           return exists ? current : (props.defaultValue ?? props.tabs[0].value)
       }
       return internalValue.value || props.defaultValue || undefined
   })

   // 监听异步 tabs 变更：当 tabs 数据动态到达或选项列表重置时，同步更新非受控 internalValue
   watch(() => props.tabs, (tabs) => {
       if (props.modelValue !== undefined) return
       const current = internalValue.value
       const exists = current !== '' && !!tabs && tabs.some(tab => tab.value === current)
       if (!exists) {
           internalValue.value = props.defaultValue ?? tabs?.[0]?.value ?? ''
       }
   })

   function handleUpdateModelValue(value: string) {
       if (props.modelValue === undefined) {
           internalValue.value = value
       }
       emit('update:modelValue', value)
   }
   ```
3. **插槽模式非受控契约**：
   在插槽模式非受控使用时，推荐显式传入 `defaultValue`。若未传 `defaultValue`，`activeValue` 输出 `undefined`，`TabsRoot` 将由用户首次点击触发激活并自动受控于 `internalValue`。
4. **模板对称绑定**：
   配置模式与插槽模式中的 `TabsRoot` 均统一绑定 `:model-value="activeValue"` 与 `@update:model-value="handleUpdateModelValue"`。

### 1. 单元测试门禁
按最小化校验原则执行针对性单测验证：
